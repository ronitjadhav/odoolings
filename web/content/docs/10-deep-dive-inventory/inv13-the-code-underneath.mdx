## Why this matters

Twelve chapters clicked through Inventory. Every one of those clicks ends in a handful of
Python methods: a quant changes, a move changes state, a rule decides where goods come
from. When a customer says "it reserved the wrong bottle" or "the van never got its
filter", you open those methods, not the screens.

LibreFleet has spare parts and service orders, but its parts never leave a shelf. A
finished service order should take its parts from stock, from the van first, and send
for what the van lacks. That is a dozen lines, if they call the right method.

## Concepts

### The models, in one picture

<Mermaid

| Model | One sentence |
|---|---|
| `stock.quant` | how much of a product (lot, package, owner) sits in one location, and how much is reserved |
| `stock.move` | a demand to move a quantity of one product from one location to another |
| `stock.move.line` | the detail of a move: which lot, which package, from which exact sub-location |
| `stock.picking` | a transfer: the moves of one operation type, done together |
| `stock.picking.type` | an operation type: Receipts, Pick, Workshop Consumption |
| `stock.rule` / `stock.route` | where a product comes from when it is needed somewhere |
| `stock.reference` | the link between the documents of one flow, which replaced procurement groups in 19 |

### A move's life

A move goes `draft` → `confirmed` (or `waiting` for another move) → `partially_available`
→ `assigned` → `done`, or `cancel`. Each step is one method:

| Method | What it does |
|---|---|
| `_action_confirm()` | draft to confirmed; merges similar moves (`_merge_moves`), runs the rules for moves that are "make to order" |
| `_action_assign()` | reserves: finds quants and creates move lines; confirmed to assigned |
| `_action_done()` | takes the `picked` lines, moves the quants, writes `done`; splits off what was not done (`_split`) |
| `_action_cancel()` | cancels, and the next moves too if `propagate_cancel` |
| `_trigger_assign()` | after a move is done, tries to reserve the moves waiting for that product there |

On a transfer, **Validate** is `button_validate()`. It checks the transfer, calls
`_pre_action_done_hook()` (where the backorder and immediate-transfer wizards come from),
then `_action_done()`. The backorder dialog is `stock.backorder.confirmation`
(`process()`), the return dialog `stock.return.picking` (`action_create_returns()`).

### Quants: the stock itself

Quants are never edited by hand in code. Two methods change them:

- `_update_available_quantity(product, location, quantity, lot_id=..., package_id=..., owner_id=...)` adds or removes stock.
- `_update_reserved_quantity(...)` reserves or frees it.

`_gather(product, location)` finds the quants a move may take, in removal-strategy order,
sub-locations included. The Physical Inventory screen writes `inventory_quantity` under
the context key `inventory_mode`, and applies through `action_apply_inventory()`
(chapter 10).

### The rule engine

A need for a product somewhere is a **procurement**: a `Procurement` named tuple of
product, quantity, unit, location, name, origin, company and a `values` dict.
`stock.rule.run(procurements)` finds a rule for each one with `_get_rule()`. For the
needed location, then its parents, it tries the routes passed in `values`, then the
package type's, then the product's and its category's, then the warehouse's. Then it
calls `_run_<action>`: `_run_pull` makes a move, `_run_push` reacts to one, and other modules
add `_run_buy` (purchase) and `_run_manufacture` (mrp).

A pull rule builds its move with `_get_stock_move_values()`. To carry your own field from
`values` onto that move, list it in `_get_custom_move_fields()`: that is the hook this
chapter uses. Lead times add up in `_get_lead_days()`. Reordering rules call the same
engine from `stock.warehouse.orderpoint._procure_orderpoint_confirm()`.

With **Take From Stock, if unavailable, Trigger Another Rule** (`mts_else_mto`), a rule
takes what its source location has. For the rest it runs a new procurement at that source
location, so another rule can bring it there.

### Quantities and their context keys

`qty_available`, `free_qty` (on hand minus reserved), `virtual_available` (forecast),
`incoming_qty` and `outgoing_qty` are computed per product, and the context decides for
where and when:

| Context key | Restricts to |
|---|---|
| `location` | a location and its children |
| `warehouse_id` | a warehouse's locations |
| `strict` | with `location`: that location only, not its children |
| `lot_id`, `owner_id`, `package_id` | one lot, owner or package |
| `from_date`, `to_date` | moves in that window (for history) |

`strict` changes the result but is not in the field's `depends_context`, so within one
transaction a cached value can answer for the other setting. The tour below shows it.

### Valuation hooks

`stock_account` adds two: `_set_value()` computes a move's `value` (chapter 12's order of
sources), and `_should_create_account_move()` decides whether a move posts a journal
entry. Override them, never the quants, to change what stock is worth.

The service order gets a warehouse to draw from, its moves, and the call to the rule
engine when it becomes Done:

```python title="addons/librefleet_stock/models/service_order.py"
from odoo import _, api, fields, models
from odoo.exceptions import UserError


class ServiceOrder(models.Model):
    _inherit = "librefleet.service.order"

    warehouse_id = fields.Many2one(
        "stock.warehouse",
        string="Parts From",
        help="The warehouse whose rules supply the parts when the order is done.",
    )
    move_ids = fields.One2many("stock.move", "librefleet_order_id", string="Stock Moves")
    picking_count = fields.Integer(compute="_compute_picking_count")

    @api.depends("move_ids.picking_id")
    def _compute_picking_count(self):
        for order in self:
            order.picking_count = len(order.move_ids.picking_id)

    def write(self, vals):
        finishing = self.filtered(lambda o: o.stage != "done") if vals.get("stage") == "done" else self.browse()
        res = super().write(vals)
        finishing._consume_parts()
        return res

    def _consume_parts(self):
        """Ask the stock rules for every stocked part, as a sale order asks for a delivery."""
        workshop = self.env.ref("librefleet_stock.location_workshop")
        procurements = []
        for order in self:
            lines = order.line_ids.filtered(lambda line: line.part_id.product_id.is_storable and line.qty > 0)
            if not lines:
                continue
            if not order.warehouse_id:
                raise UserError(_("Set Parts From on %s before marking it done.", order.reference))
            for line in lines:
                product = line.part_id.product_id
                procurements.append(self.env["stock.rule"].Procurement(
                    product, line.qty, product.uom_id, workshop,
                    order.reference, order.reference, order.warehouse_id.company_id,
                    {"warehouse_id": order.warehouse_id, "librefleet_order_id": order.id,
                     "partner_id": order.customer_id.id},
                ))
        if procurements:
            self.env["stock.rule"].run(procurements)

    def action_view_pickings(self):
        self.ensure_one()
        action = self.env["ir.actions.act_window"]._for_xml_id("stock.action_picking_tree_all")
        action["domain"] = [("id", "in", self.move_ids.picking_id.ids)]
        action["context"] = {"create": False}
        return action
```

Hooking `write` catches every way to Done: the Mark Done wizard and the clickable status

and the rules of the chosen warehouse decide how the parts get there. Nothing here
creates a transfer by hand.

## Gotchas

- **Never write quants directly.** `_update_available_quantity` and moves keep quants,
  reservations and history consistent; a `write` on `quantity` breaks all three.
- **`strict` is not in the cache key.** Two quantity reads in one transaction, with and
  without `strict`, can return the same number. Invalidate between them, or read them in
  separate requests.
- **A field on the procurement does not follow the chain.** `_get_custom_move_fields()`
  copies it onto the move the rule creates, not onto the moves of the procurements that
  move triggers. Propagate it in `_prepare_procurement_values()` if you need it there.
- **Hook the state change, not the button.** A wizard, a status bar click, an import or
  an automated action can all change `stage`. Overriding `write` catches them all;
  overriding one button misses the rest.
- **No rule, an error.** `stock.rule.run` raises "No rule has been found to replenish"
  when nothing matches. Here, an air filter without the van's resupply route would have
  stopped Mark Done.
- **Data that names your own records breaks elsewhere.** The van, its sequence and its
  route exist only in this database, so the module ships the Workshop location and lets
  the user build the rest in the UI.
