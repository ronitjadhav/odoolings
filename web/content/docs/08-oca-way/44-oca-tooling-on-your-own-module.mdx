**Checkpoint:** `code/checkpoints/ch44`

## Why this matters

Chapter 43 showed you what a properly-tooled OCA module looks like from the outside:
badges, a generated README, a declared maturity level. This chapter builds that same
setup and points it at your own code.

LibreFleet has never had a linter near it, and that's normal. No real project starts with
tooling in place. Every team adopts it partway through, points it at code nobody was
watching for style, and fixes what comes back. That's today's hands-on, not a contrived
example: the findings below are what `pre-commit`, the runner that drives all these
checks, genuinely found the first time it ran against this exact codebase.

One objection first, because most developers have it and nobody says it out loud:
**linting reads as style policing.** A tool is about to reformat twelve of your files over
quote marks and whitespace, and none of that makes the software do anything new.

If that feels like a wasted afternoon, here is the answer. The reformatting is not the
point; it is the part nobody should ever argue about again. Handing quote style to a
machine buys you review conversations about substance instead of taste, which is why
chapter 45's reviewers can be brief.

The part that *is* the point is smaller and easy to miss in the noise. One of the findings
below is that a `ValidationError` message isn't wrapped for translation, which means a
French-speaking user reads an English error forever. That is a real bug in a real
codebase, it has nothing to do with style, and no general-purpose Python linter could
possibly have caught it.

## Concepts

### What each tool actually checks

That points at the shape of the whole setup: **two layers, and they know different
things.**

`ruff` knows Python, so it catches what would be a mistake in any Python project
anywhere. `pylint-odoo` knows *Odoo*, so it catches what is only a mistake here: a string
that needs translating, a wrong manifest key, a write inside a compute. The first layer is
portable. The second is why this chapter exists.

<CardGrid cols={2}>
  <Card tone="sage" icon={<Icon name="tool" />} title="ruff">
    Python formatting and a large, fast rule set (unused imports, bug-prone patterns,
    import order). Runs in milliseconds; most of what it finds it fixes itself with
    `--fix`.
  </Card>
  <Card tone="sand" icon={<Icon name="tool" />} title="pylint-odoo">
    A pylint plugin with Odoo-specific rules ruff can't express: manifest keys,
    translation usage, ORM anti-patterns like writing inside a compute. This is the
    OCA-specific layer.
  </Card>
  <Card tone="violet" icon={<Icon name="tool" />} title="prettier">
    Formats the non-Python files: XML views, JS, JSON. The OWL work from chapter 39
    on is exactly what this catches.
  </Card>
  <Card tone="plain" icon={<Icon name="tool" />} title="pre-commit">
    The runner that wires all three (and more) into one command, `pre-commit run`,
    triggered automatically on `git commit` once installed. Each hook gets its own
    isolated environment; you don't install ruff or pylint-odoo yourself.
  </Card>
</CardGrid>

pre-commit itself is a Python tool (`pip install pre-commit`, a one-time setup step
same as Docker or git). Everything each individual hook needs, pre-commit fetches and
builds the first time you run it.

### The config, hook by hook

`.pre-commit-config.yaml` lives at your workspace root, next to `docker-compose.yml`:

```yaml
default_language_version:
  python: python3
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v6.0.0
    hooks:
      - id: check-xml
      - id: check-merge-conflict
      - id: end-of-file-fixer
        exclude: /README\.rst$
      - id: trailing-whitespace
        exclude: /README\.rst$
      - id: mixed-line-ending
        args: ["--fix=lf"]
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.13.0
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
  - repo: https://github.com/OCA/pylint-odoo
    rev: v9.3.15
    hooks:
      - id: pylint_odoo
        args: ["--rcfile=.pylintrc"]
  - repo: https://github.com/oca/maintainer-tools
    rev: c08659518fb287683074f0a6aacda984815ac7b1
    hooks:
      - id: oca-gen-addon-readme
        args:
          - --addons-dir=addons
          - --branch=19.0
          - --org-name=YOUR-GITHUB-USER
          - --repo-name=odoolings-starter
          - --if-source-changed
```

Each `repo:` entry is a separate git repository that pre-commit clones and runs hooks
from, pinned to a `rev` the same way a manifest pins a dependency version.

This is a trimmed version of what a real OCA repo runs. `OCA/fleet`'s actual config also
wires up eslint, its node toolchain, and `whool`, none of which LibreFleet needs yet.
Every hook here is real, though, and does the same job on your module that it does on
theirs.

Two more files it leans on, both at the workspace root too. `.ruff.toml`:

```toml
target-version = "py312"

[lint]
extend-select = ["B", "I"]

[lint.per-file-ignores]
"__init__.py" = ["F401", "I001"]
"__manifest__.py" = ["B018"]
```

And `.pylintrc`. It switches on pylint-odoo's Odoo-specific checks explicitly, since its
default is to check nothing until you opt in, and it declares the project facts the
manifest checks verify against:

```ini
[MASTER]
load-plugins=pylint_odoo
score=n

[ODOOLINT]
manifest-required-authors=Odoolings readers
manifest-required-keys=license
license-allowed=AGPL-3,GPL-2,GPL-2 or any later version,GPL-3,GPL-3 or any later version,LGPL-3
valid-odoo-versions=19.0

[MESSAGES CONTROL]
disable=all
enable=dangerous-default-value,development-status-allowed,license-allowed,
    manifest-author-string,manifest-required-author,manifest-required-key,
    manifest-version-format,method-required-super,missing-return,
    print-used,sql-injection,translation-required
```

<Callout type="info" title="In the field">
  Real OCA repos actually ship two rcfiles: a full `.pylintrc` with every optional
  check enabled (loaded in your editor, so nothing is hidden from you) and a shorter
  `.pylintrc-mandatory` with only the checks that block a merge (what pre-commit
  actually runs). We collapsed that into one file here to keep today's setup
  readable; once you're contributing for real in chapter 45, you'll meet the split.
</Callout>

### readme fragments, not README.rst

Chapter 43 showed you the generated file. The source you actually maintain is three
small markdown files under `readme/`:

<Files className="bg-(--tone-sky)">
  <Folder name="addons/librefleet" defaultOpen>
    <File name="__manifest__.py" />
    <Folder name="readme" defaultOpen>
      <File name="DESCRIPTION.md" />
      <File name="CONTRIBUTORS.md" />
      <File name="ROADMAP.md" />
    </Folder>
    <File name="README.rst" />
  </Folder>
</Files>

`oca-gen-addon-readme` (the last hook in the config above) reads those fragments plus
your manifest (`name`, `author`, `license`, `development_status`) and writes
`README.rst`, badges and all. Edit the fragments, run pre-commit, the README updates
itself. Never the reverse.

### Manifest conventions this chapter adds

Two things LibreFleet's manifest has been missing since chapter 8:

- **`development_status`**: chapter 43 covered the values. LibreFleet is real code
  built across a tutorial and still growing, so `"Beta"` is the honest call, declared
  explicitly rather than left to the silent default.
- **A version bump**, same rule as every chapter since 8: real code changed, so the
  patch number moves.

### Module naming, revisited

Chapter 8 picked `librefleet` specifically to avoid colliding with core's `fleet`
module. That's the OCA naming rule in miniature: technical names share one global
namespace, so real projects prefix theirs (a client trigram, a product name) the same
way we did. Nothing to change here, just confirming chapter 8's call still holds.

```text

- exit code: 20

addons/librefleet/models/service_order.py:107: [translation-required, ServiceOrder._check_no_overlap] String parameter on "ValidationError" requires translation. Use self.env._('An order must end after it starts (check the schedule).')

```

Fifteen ruff F401 hits, all on `__init__.py` files doing `from . import vehicle`. That is
exactly the registration pattern chapter 9 taught: importing a module by name to run it,
never to use the name.

Ruff can't tell that apart from a genuinely unused import without help, which is what
`.ruff.toml`'s `per-file-ignores` for `__init__.py` is for. Add it and the 15 errors
disappear. `ruff-format`'s 12 reformatted files are just whitespace and quote-style
normalization: harmless, and worth committing as-is.
</Step>

<Step>
### Fix what pylint-odoo actually found

Two are real: `ValidationError` messages need to route through translation, or a
French-speaking user sees the error in English forever. Odoo 19's idiom is
`self.env._()`, a method now, not the old bare `_()` import:

```python
# addons/librefleet/models/service_order.py, _check_no_overlap
raise ValidationError(
    self.env._("An order must end after it starts (check the schedule).")
)
...
raise ValidationError(
    self.env._("%s is already booked during that window.")
    % order.vehicle_id.license_plate
)
```

```python
# addons/librefleet/models/vehicle.py, _check_year
raise ValidationError(
    self.env._("Model year %s is out of range (1900 to next year).")
    % vehicle.year
)
```

The third, `missing-return` on `_compute_access_url`, is a false positive worth
understanding rather than silencing blindly.

The check exists because forgetting `return super().create(...)` is a real, easy bug: the
override's result silently becomes `None` instead of the created record. But a
`@api.depends` compute is never supposed to return anything, it assigns fields in a loop,
so the check has no way to tell "correctly returns nothing" from "forgot to return."

The fix is the documented escape hatch, `no-missing-return` in `.pylintrc`'s
`[ODOOLINT]` section:

```ini
no-missing-return=__init__,_register_hook,setUp,setUpClass,tearDown,tearDownClass,_compute_access_url
```

Run `pre-commit run --all-files` again: clean.
</Step>

## Gotchas

- **`ruff`'s F401 on `__init__.py` isn't wrong, it just can't see intent.** The
  `per-file-ignores` line is the documented fix, not a workaround; real OCA repos
  carry the exact same line.
- **`oca-gen-addon-readme` does nothing if `readme/` doesn't exist yet.** No error,
  no README, just silence. If you add the hook before writing fragments, you'll
  wonder why nothing happened; it needs `readme/DESCRIPTION.md` at minimum.
- **`missing-return` false-positives on any `super()`-calling method with no
  `return`, not just CRUD overrides.** Computes are the common case; the fix is
  naming the method in `no-missing-return`, never adding a pointless `return`.
- **README.rst carries a source digest for a reason.** Hand-edit it and the next
  fragment change (or a teammate's) silently discards your edit, no warning beyond
  the comment you probably didn't read.
