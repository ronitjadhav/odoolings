**Goal:** build the habit of checking OCA before writing anything custom, and know how
to judge what you find. · **Time:** ~1.5 h · **Checkpoint:** none, this chapter is
research, not code.

## Why this matters

Chapter 2 drew the map: Odoo SA, integrators, the OCA, each source good for something
different. From here on you live in the OCA corner of it. Part 8 is about working the
OCA way, and that starts before you write a single line: an experienced integrator
developer's first move on a new requirement isn't "how do I build this," it's "has
someone already built this, and is it any good." Skipping that step is how projects
end up with three different in-house modules doing what one well-maintained OCA
repository already does, each one now your team's problem to maintain forever.

LibreFleet is vehicle-workshop and service-booking software. The OCA has a real
`fleet` repository covering exactly this domain. Today you go find it, and use it as
the case study for the two skills this chapter is actually about: finding a module,
and judging it before you trust it.

## Concepts

### Three places to look, and when each wins

Chapter 2 named these; here's when to reach for which.

| Source | Best for |
|---|---|
| <Icon name="store" /> [apps.odoo-community.org/modules](https://apps.odoo-community.org/modules) | Searching *across* every OCA repo and branch at once. You don't need to know which repo owns your domain first. |
| <Icon name="source" /> [github.com/OCA](https://github.com/OCA) | Once you know the repo: browsing branches, issues, PR history, reading source in context. |
| <Icon name="store" /> [apps.odoo.com](https://apps.odoo.com) | Third-party modules the OCA doesn't cover, paid add-ons, and a wider (much more variable quality) net. |

The catalog site is the one piece chapter 2 didn't cover, because chapter 2 was
teaching you the map, not yet sending you shopping. It's OCA's own search engine, and
it's worth bookmarking: `odoo-community.org/apps` redirects there. Search it by
keyword the way you'd search apps.odoo.com, except every result is peer-reviewed,
CI-tested, and AGPL-3 or LGPL-3, never a mystery license.

<Callout type="info" title="In the field">
  Camptocamp's rule of thumb, and most integrators': before estimating a feature,
  fifteen minutes on the OCA catalog. Reusing a maintained module isn't cutting
  corners, it's the professional move. A custom module you write today is one your
  team maintains through every yearly migration forever; an OCA module gets migrated
  by the community whether you touch it or not.
</Callout>

### Judging maturity: the `development_status` field and the README badges

Finding a module is easy. Trusting it takes one more habit: read its declared
maturity before you read a line of code.

The manifest key is `development_status`, one of four values:

- **`Alpha`**: working, but the API or data model may still change.
- **`Beta`**: the default when the key is *absent entirely*. Most OCA modules never
  declare it, which means "declared Beta" and "silent about it" look identical, so
  don't over-read a bare Beta as a red flag by itself; check activity (recent commits,
  open issues) instead.
- **`Production/Stable`**: the author is telling you this module is trusted in real
  deployments.
- **`Mature`**: `Production/Stable` for long enough that the API is considered settled.

Every OCA module ships a `README.rst`, auto-generated by a tool called
`oca-gen-addon-readme` from smaller fragments the maintainers actually write
(`readme/DESCRIPTION.md`, `readme/CONTRIBUTORS.md`, `readme/ROADMAP.md`, ...). The
generated file opens with a comment telling you not to bother editing it by hand:

```text
..
   This file is generated by oca-gen-addon-readme.
   !! This file is generated by oca-gen-addon-readme !!
   !! changes will be overwritten. !!
   !! source digest: sha256:... !!
```

That digest lets the tool detect a hand-edit versus a source-fragment edit: touch
the generated file directly and the digest goes stale, and the next `pre-commit` run
in that repo (chapter 44 lives here) flags it. If you ever contribute an OCA README
fix, it's the `readme/` fragment you edit, never `README.rst`.

Below that comment sits a row of badges, and one of them is the maturity level
rendered as a color, linking to the OCA's own explanation of what each level means.
The rest of the row is worth knowing at a glance too: a license badge, a GitHub badge
linking straight to that module's folder on its branch, a Weblate "Translate me" badge
(chapter 45; OCA translations happen there, never by hand-editing a `.po` file in a
PR), and a Runboat "Try me" badge that spins up a live instance of that exact module
with no install step on your end.

### Reading OCA source as study material

The OCA holds itself to real review standards: CI, peer review, `pre-commit` linting,
a PSC (Project Steering Committee, chapter 2) signing off on what merges. That makes
its modules some of the best real-world code you can read, and unlike Odoo's own core,
it's written by working integrators solving the exact kind of ticket you'll get.

`OCA/fleet`, the repository covering vehicle management, is LibreFleet's direct real-
world parallel. Its `19.0` branch holds modules like `fleet_vehicle_service_kanban`,
`fleet_vehicle_service_services`, `fleet_vehicle_inspection`, and
`fleet_vehicle_log_fuel`, small, single-purpose additions on top of Odoo's core
`fleet` module. That's an OCA convention worth internalizing on sight: many small
modules that each do one thing and declare narrow `depends`, rather than one large
module doing everything. It composes better and migrates easier, one small diff at a
time instead of one large one.

## Hands-on

1. Open [apps.odoo-community.org/modules](https://apps.odoo-community.org/modules) and
   search "fleet". Find `OCA/fleet` among the results, and note what else turns up,
   since a real search rarely returns exactly one hit.
2. On [github.com/OCA/fleet](https://github.com/OCA/fleet), switch to the `19.0`
   branch and skim the module list. Which of these could LibreFleet plausibly use one
   day, and which duplicate ground you've already built?
3. Open `fleet_vehicle_service_kanban`'s `__manifest__.py`. Find its
   `development_status` key and its value.
4. Open that same module's `README.rst` on GitHub. Find the maturity badge, the
   Runboat badge, and the generated-file warning comment near the top.
5. Now open `fleet_vehicle_service_services`'s manifest. No `development_status` key:
   that's the silent Beta default from the Concepts section, in the wild.
6. Compare both manifests' `author` field. Notice the pattern: a company name (the
   contributor who wrote it) plus "Odoo Community Association (OCA)", not one
   individual and not "OCA" alone. Contributions come from integrators, credited by
   name, under a shared umbrella.

## Verify

There's no odoolings check for a research chapter, so verify it in your head: given a
feature LibreFleet still needs (say, a vehicle inspection checklist), you should be
able to name where you'd search first, how you'd tell a trustworthy hit from a risky
one without reading a single line of its code, and where you'd go read that code once
you decided it was worth trusting.

## Gotchas

- **`README.rst` is generated. Don't hand-edit it, ever**, in your own future
  contributions. The `source digest` comment exists specifically to catch this; fix
  the `readme/` fragment instead and regenerate.
- **Undeclared `development_status` isn't a red flag by itself.** It just means
  Beta, the default, which describes most of the OCA. Judge activity and issues, not
  only the badge.
- **The Apps store and the OCA catalog are not the same search.** apps.odoo.com
  includes modules of wildly varying quality with no shared review process;
  apps.odoo-community.org only ever returns OCA modules.
- **Repos are named by domain, modules by feature.** `OCA/fleet` holds a dozen
  `fleet_*` modules. Searching GitHub for a module name directly will often miss the
  repo that actually contains it.

## Exercises

1. ⭐ Pick a business domain LibreFleet doesn't touch (say, HR or accounting) and find
   one `Production/Stable` module for it on the OCA catalog. Read its README badges.
2. ⭐⭐ Compare `development_status` across five modules in two different OCA repos.
   Tally Alpha/Beta(-including undeclared)/Production-Stable/Mature. Beta usually
   dominates: that's normal, not a quality signal on its own.
3. ⭐⭐⭐ Find one `OCA/fleet` module that overlaps with something LibreFleet already
   does (or plans to). Write three sentences: would you have adopted it instead of
   building your own, and what would that decision have cost you either way?
