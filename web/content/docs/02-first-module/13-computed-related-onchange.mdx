**Goal:** give LibreFleet live money totals, a customer that follows the vehicle's
owner, and a parts price that fills itself in. · **Time:** ~2.5 h ·
**Checkpoint:** `code/checkpoints/ch13`

## Why this matters

Half the fields on any real Odoo screen were never typed by anyone: order totals,
margins, counters, the customer on an invoice. They're derived, and the framework's
dependency system keeps them correct while data changes around them. Do this well
and your app feels alive; do it badly and you ship the worst class of bug there is,
numbers that are *silently wrong*. This chapter builds all three derivation tools
into LibreFleet and then breaks one on purpose so you recognize the failure forever.

Here is the thing that makes this chapter harder than it should be, and it is worth
saying before the code arrives. **All three tools look identical from the outside.**
Computed, related and onchange each put a value into a field that the user never typed,
so on screen they are indistinguishable, and a reader reasonably wonders why Odoo needs
three of them at all.

The question that separates them is not what they do, it is **who owns the value once
it is there**:

- A **computed** field is owned by the framework, forever. It recalculates whenever its
  inputs change, and you cannot type over it.
- A **related** field is owned by the record it points at. Change the source and every
  copy follows.
- An **onchange** value is owned by the **user**, the instant it appears. Odoo suggests
  it, then lets go.

That last one is the whole reason onchange cannot be a business rule, and it is why this
chapter's final experiment is able to sidestep one.

## Concepts

Keep this table in view while you read the three sections below. It is the same three
tools, lined up on the questions that actually decide which one a ticket needs:

| | Computed | Related | Onchange |
|---|---|---|---|
| Where the value comes from | a method you write, from other fields | a path to another record | a method you write, at typing time |
| Who owns it afterwards | the framework, forever | the record it points at | the user, immediately |
| Can the user type over it | no | no | yes, that is the point |
| Fires outside a form (shell, RPC, import) | yes | yes | **no** |

The bottom row is the one that causes production bugs, and this chapter ends by proving
it on a real record.

### Computed fields: value = f(other fields)

A <Term k="computed field">computed field</Term> declares a method that fills it and, through `@api.depends`, the
exact fields its value is built from:

```python
subtotal = fields.Float(compute="_compute_subtotal", store=True)

@api.depends("qty", "price_unit")
def _compute_subtotal(self):
    for line in self:
        line.subtotal = line.qty * line.price_unit
```

Two contracts to respect. The compute method receives a <Term k="recordset">recordset</Term> and must
assign a value to *every* record in it, hence the loop. And `depends` is not
documentation: it is the trigger wiring. When `qty` changes, the ORM marks
`subtotal` stale and recomputes it at the right moment, cascading into anything
that depends on `subtotal` in turn. Dotted paths (`line_ids.subtotal`) let a parent
watch its children.

### Store or don't store

- **Non-stored** (the default): no column, computed on read. Ideal for cheap
  derivations. The cost: you can't (yet) search or group on it, since there's
  nothing in SQL to query.
- **`store=True`**: a real column, recomputed *on write* whenever a dependency
  changes. Searchable, groupable, readable by raw SQL and reports, but now
  correctness depends entirely on the completeness of `depends`.

LibreFleet uses both deliberately: line `subtotal` is stored (reports and sums will
want it), while the order's `parts_total`, `labor_total` and `margin` stay
non-stored (cheap to derive, always fresh). You'll see the difference as the
presence and absence of columns in psql.

### Related fields: a path, not a formula

A <Term k="related field">related field</Term>, `customer_id = fields.Many2one(related="vehicle_id.owner_id", store=True)`, is a
computed field the framework writes for you: follow the path, mirror the value. The
blueprint stores this one, which buys a real column that search, group-by and the
future portal can use, and the dependency system still updates it when the owner
changes. That's worth staring at: change the *partner on the vehicle*, and every
stored copy on every order fixes itself.

### Onchange: a UI suggestion, nothing more

An <Term k="onchange">`@api.onchange("part_id")`</Term> runs **in the form view only**, while the user edits,
on a draft record that isn't saved yet. It's perfect for prefilling: pick a part,
get its list price as the suggested `price_unit`, still editable for a discount.
Its sharp edge: code paths (shell, RPC, imports, other modules) never trigger it.
An onchange is UX sugar, not a business rule; anything that must *always* hold
belongs in computes, defaults or constraints (chapter 14).

<Callout type="info" title="In the field">
  Modern Odoo code increasingly replaces onchange with "computed editable" fields
  (`compute=` plus `readonly=False`, letting users override the computed value),
  which fire on every path, not just forms. You'll convert this chapter's onchange
  in the stretch exercise; knowing both idioms is mandatory for reading real
  modules.
</Callout>

## Hands-on

<Steps>

<Step>
### The stored line subtotal

Three edits, all in `models/service_order.py` unless noted.

Widen the import line at the top of the file, you'll need `api` for the
`@api.depends` decorator below:

```python title="addons/librefleet/models/service_order.py"
from odoo import api, fields, models     # was: from odoo import fields, models
```

On the `ServiceOrderLine` class, right after `price_unit`, add the field and its
compute method (the exact code from the Concepts section above):

```python
    subtotal = fields.Float(compute="_compute_subtotal", store=True)

    @api.depends("qty", "price_unit")
    def _compute_subtotal(self):
        for line in self:
            line.subtotal = line.qty * line.price_unit
```

Then show it on screen: in `views/service_order_views.xml`, find the inline list
that already has `part_id`, `qty` and `price_unit`, and add one line right after
`price_unit`:

```xml
                                <field name="price_unit"/>
                                <field name="subtotal"/>
```

Nothing else to add for it to render read-only, that's the default for computed
fields, no `readonly="1"` needed.
</Step>

<Step>
### The order totals

On the order model:

```python
    parts_total = fields.Float(compute="_compute_totals")
    labor_total = fields.Float(compute="_compute_totals")
    margin = fields.Float(compute="_compute_totals",
                          help="What the order earns: parts revenue plus the flat "
                               "fee, minus what the parts cost the workshop.")

    @api.depends("line_ids.subtotal", "line_ids.qty",
                 "line_ids.part_id.standard_cost", "service_type_id.flat_fee")
    def _compute_totals(self):
        for order in self:
            order.parts_total = sum(order.line_ids.mapped("subtotal"))
            order.labor_total = order.service_type_id.flat_fee
            parts_cost = sum(
                line.qty * line.part_id.standard_cost for line in order.line_ids)
            order.margin = order.parts_total + order.labor_total - parts_cost
```

One method may fill several fields (they recompute together anyway). Read the
`depends` list like an audit: subtotals, quantities, part costs, the fee. Miss one
and the totals lie *sometimes*, which is worse than always. In the form, a "Money"
group shows the three:

```xml
<group string="Money">
    <field name="parts_total"/>
    <field name="labor_total"/>
    <field name="margin" groups="librefleet.group_librefleet_manager"/>
</group>
```

`groups=` on a single `<field>` is the same view-level trim chapter 11's menu items
used, just aimed at one field instead of a whole menu: technicians see Parts Total and
Labor Total, but Margin, the workshop's actual cut, only renders for managers.
</Step>

<Step>
### The customer that follows the owner

On the order, right under `vehicle_id`:

```python
    customer_id = fields.Many2one(
        related="vehicle_id.owner_id", store=True, string="Customer")
```

Add it to the order list and form. Then the counter on the vehicle, in
`models/vehicle.py`. That file still has chapter 12's import line, and you are about to
use a decorator it does not import, so widen it first:

```python title="addons/librefleet/models/vehicle.py"
from odoo import api, fields, models     # was: from odoo import fields, models
```

Miss that and the module will not load at all: `@api.depends` becomes
`NameError: name 'api' is not defined` while Odoo is importing your package, which reads
as the whole module being broken rather than one missing word. Then the field itself:

```python
    service_count = fields.Integer(compute="_compute_service_count")

    @api.depends("service_order_ids")
    def _compute_service_count(self):
        for vehicle in self:
            vehicle.service_count = len(vehicle.service_order_ids)
```

Now put it on the vehicle form, because two later chapters need it to be there. In
`views/vehicle_views.xml`, add it to the "Usage" group as the last field, after
`mileage_km`:

```xml
                        <group string="Usage">
                            <field name="year"/>
                            <field name="mileage_km"/>
                            <field name="service_count"/>
                        </group>
```

Do not skip that line. Chapter 16 builds an extension view whose xpath searches the form
for `service_count`, and a locator that matches nothing is a hard error: the upgrade
aborts with `Element '<xpath expr="//field[@name='service_count']">' cannot be located in
parent view`, and every record in that file fails to load, not just the one patch.
Chapter 17 then *moves* this field into a smart button on purpose, which is how it teaches
that anchoring an xpath on a field someone can move is fragile. Both of those need the
plain field here first.

(Chapter 17 is where this stops being a bare integer and becomes the stat button every
Odoo form has; the field and its compute are the hard part, and they are four lines.)
</Step>

<Step>
### The onchange

On the line model:

```python
    @api.onchange("part_id")
    def _onchange_part_id(self):
        if self.part_id:
            self.price_unit = self.part_id.list_price
```

Bump the version to `19.0.1.5.0`, upgrade, restart:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial -u librefleet --stop-after-init
...
INFO tutorial odoo.models: Prepare computation of librefleet.service.order.line.subtotal
...
INFO tutorial odoo.modules.loading: Module librefleet loaded in 0.13s, 279 queries (+279 other)
```

That one line is the whole backfill, and only one line, not six, is exactly the point:
`subtotal` is the only field of the bunch declared `store=True`, so it is the only one
with a real column that existing rows need a value written into. `parts_total`,
`labor_total` and `margin` have no `store=True` at all, they are computed fresh on every
read, so there is nothing to backfill, no column, no log line, just live arithmetic.
`customer_id` is `store=True` too, but as a `related` field its column gets its initial
value copied in directly rather than through this same compute-and-log path, so it
updates correctly without a matching line of its own.
</Step>

### Prove onchange's limit

Still in the shell, create a line the way an import or another module would:

```console
>>> env["librefleet.service.order.line"].create({
...     "order_id": 1,
...     "part_id": env["librefleet.part"].search([("code", "=", "BP-201")]).id,
...     "qty": 2,
... }).price_unit
0.0
```

Part chosen, price zero: the onchange never ran, because nobody was typing in a
form. This is not a bug, it's the definition, and it's why business rules don't
live in onchange. Roll back to discard the broken line.
</Step>

### Break-it lab: the missing depends

Delete the `@api.depends("qty", "price_unit")` line above `_compute_subtotal`
(keep the method), upgrade, and change a quantity:

```console
>>> line = env["librefleet.service.order.line"].browse(1)
>>> line.qty = 3
>>> env.cr.commit()
>>> line.qty, line.subtotal
(3.0, 24.5)
```

Quantity three, subtotal for one, no error anywhere, and psql confirms the lie is
durably stored:

```console
$ docker compose exec db psql -U odoo -d tutorial -c "select qty, price_unit, subtotal from librefleet_service_order_line where id=1;"
 qty | price_unit | subtotal
-----+------------+----------
   3 |       24.5 |     24.5
```

Now restore the decorator and upgrade, and note something important: **the stale
value stays stale** until a dependency actually changes (read it back: still 24.5).
Fixing the code doesn't fix the data; touching `qty` again does. On a production
database that's a targeted recompute script, not a shrug. Set `qty` back to 1 and
commit, which both heals and restores the checkpoint state.
</Step>

## Gotchas

- **A missing depends is silent, durable corruption.** No traceback, no warning,
  just stored numbers that stop tracking reality (you built it, you saw it).
  Review `depends` lists in every code review like they're money, because they
  are.
- **Fixing depends doesn't heal existing data.** Recompute happens on dependency
  *changes*; historic rows keep their stale values until touched. Production fixes
  pair the code change with a one-off recompute.
- **Onchange only fires in forms.** Imports, shell, RPC and other modules bypass
  it, so never park validation or pricing *policy* there; it's a typing assistant.
- **Compute methods must assign on every record.** Skip one (an `if` without an
  `else`) and you get "Compute method failed to assign" errors on exactly the
  records your test data didn't cover.
- **Non-stored *computed* fields can't be searched, grouped, or aggregated.** There is
  no column and no expression Postgres could evaluate, so if a filter, group-by, or a
  pivot/graph measure matters, store the field or give it a `search=` method. Chapter
  19 hits this exact wall with `margin`. Note the word *computed*: a non-stored
  **related** field is different, because `related="a.b"` hands the ORM a path it can
  rewrite into a JOIN, so those stay searchable without being stored. The rule is not
  "unstored means unsearchable", it is "Postgres has to be able to get there".
