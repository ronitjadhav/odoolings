**Goal:** give LibreFleet real user groups and access rules, and understand why the
model refused every caller without them. · **Time:** ~2 h · **Checkpoint:** `code/checkpoints/ch10`

## Why this matters

Chapter 9 left a WARNING in the upgrade log and a model only the superuser could
touch. That wasn't an oversight to rush past: it's the framework teaching you its
posture. In Odoo, nobody can do anything with a model until a rule says they can,
and "nobody" includes the admin account.

Most tutorials bolt security on at the end. Integrators learn it first, because on a
real project the question is never "can we show this data" but "to exactly whom".
Getting groups right early also means every later chapter, views and wizards and
reports, is built and tested against realistic permissions rather than superuser
fantasy.

A chapter about permissions this early can feel like paperwork standing between you and
the interesting part. So here is the answer up front. **Security in Odoo is not a lock
you add to finished work. It is the thing that makes the work visible at all.**

Right now `librefleet.vehicle` exists, has columns, and holds the records you created in
chapter 9. Yet no ordinary user can so much as read it: not your colleague, not a
technician, not even the admin account. Chapter 11 puts LibreFleet on screen with menus
and views, and without what you write today those menus would open onto an error message.

So this chapter is not a detour before the features. It is the step that lets the next
chapter's features exist. Two files do it: one names the **teams**, the other hands out
their **badges**.

## Concepts

### Deny by default

An Odoo model ships with zero permissions. Until an access rule grants a group the
right to read it, a regular user calling it over RPC (remote procedure call, how the
web client asks the server to do anything) gets a real `AccessError`:

```text
AccessError: You are not allowed to access 'Workshop Vehicle' (librefleet.vehicle) records.

No group currently allows this operation.

Contact your administrator to request access if necessary.
```

Specific, not vague: it names the model by its `_description` (chapter 9's field
doing real work) and says plainly that no group grants the operation. You met the
shape of this in chapter 9, where the shell skipped it entirely by running as the
superuser; now you'll grant the missing right instead of wondering why "the model
doesn't exist."

### Groups, and how Odoo 19 organizes them

Permissions are never granted to individual users, always to **<Term k="group">groups</Term>**
(`res.groups`), and users join groups. Since Odoo 19, groups are organized under a
**<Term k="privilege">privilege</Term>** (`res.groups.privilege`, the "Workshop" row you'll see on the user
form), and privileges sit in a module category. LibreFleet follows the standard
two-level pattern almost every app uses:

- **Workshop / User**: technicians. Can see the fleet and keep it updated.
- **Workshop / Manager**: full control. Declares `implied_ids` pointing at User,
  which means every Manager automatically has everything a User has; you only ever
  grant the *extra* rights to Manager.

<Mermaid
  label="The Workshop privilege holds two groups, User and Manager; Manager implies User, tina is a User and admin a Manager, and each group's access rules grant it operations on librefleet.vehicle"
  chart={`flowchart TB
    P["res.groups.privilege<br/>Workshop"] --> U["res.groups<br/>Workshop / User"]
    P --> M["res.groups<br/>Workshop / Manager"]
    M -. "implied_ids:<br/>Manager has all of User" .-> U
    T["user tina"] --> U
    A["user admin"] --> M
    U -- "ACL: read, write" --> V[("librefleet.vehicle")]
    M -- "ACL: read, write,<br/>create, unlink" --> V`}
/>

<Callout type="info" title="On Odoo 18 this differs">
  The privilege level is new in 19. On 18 and earlier, a group carries a
  `category_id` straight to the module category, the group's member list is the
  `users` field (19: `user_ids`), and the groups field on `res.users` is `groups_id`
  (19: `group_ids`). The concepts are identical; only the wiring moved.
</Callout>

### Access rules: the CSV

Model-level permissions live in `ir.model.access` records, by convention loaded from
`security/ir.model.access.csv`. People shorten this to an **<Term k="access rights (ACL)">ACL</Term>**
(access control list), and this chapter uses both names for the same thing. One line
grants one group four booleans on one model: **read, write, create, unlink**. Two
properties matter more than the syntax:

- **Additive.** A user's effective rights are the union of all their groups' lines.
  There is no "deny" line; you subtract by *not granting*, never by overriding.
- **Model-wide.** An ACL answers "may tina write vehicles at all?". "May she write
  *this* vehicle?" is a different mechanism, **<Term k="record rule">record rules</Term>** (`ir.rule`), which
  filter per record with a domain. LibreFleet's record rule ("technicians may only
  write service orders assigned to them") arrives in chapter 12, once service orders
  exist to filter.

### Superuser, admin, and testing as somebody real

Chapter 9's shell worked without any ACL because `odoo shell` runs as the
**<Term k="superuser">superuser</Term>** (`__system__`, uid 1), which skips permission checks entirely. The
`admin` account is *not* that: it's an ordinary user born into the administration
groups, and your new model's ACLs don't mention those.

That is why this chapter's XML explicitly adds admin to Workshop / Manager. It is also
why the honest way to test security is <Term k="with_user()">`with_user()`</Term>, which re-runs your code as a
real user, checks included.

## Hands-on

Two files, two different jobs. The XML file below creates the *teams*, Workshop / User
and Workshop / Manager, who exists. The CSV file after it hands out *badges* to those
teams: who can read, write, create, or delete vehicles. Build them in that order, because
the CSV's badges name teams that only exist once the XML has run.

<Steps>

<Step>
### Define the groups

New directory `security/`:

```console
$ mkdir addons/librefleet/security
```

First file, `addons/librefleet/security/librefleet_security.xml`:

```xml
<?xml version="1.0" encoding="utf-8"?>
<odoo>

    <record id="privilege_librefleet" model="res.groups.privilege">
        <field name="name">Workshop</field>
        <field name="category_id" ref="base.module_category_services"/>
    </record>

    <record id="group_librefleet_user" model="res.groups">
        <field name="name">User</field>
        <field name="sequence">10</field>
        <field name="privilege_id" ref="privilege_librefleet"/>
        <field name="implied_ids" eval="[(4, ref('base.group_user'))]"/>
        <field name="comment">Technicians: see the whole fleet and keep vehicle data up to date.</field>
    </record>

    <record id="group_librefleet_manager" model="res.groups">
        <field name="name">Manager</field>
        <field name="sequence">20</field>
        <field name="privilege_id" ref="privilege_librefleet"/>
        <field name="implied_ids" eval="[(4, ref('group_librefleet_user'))]"/>
        <field name="user_ids" eval="[(4, ref('base.user_admin'))]"/>
        <field name="comment">Workshop managers: full control, including configuration.</field>
    </record>

</odoo>
```

This is your first real data XML, so start with the shape before the specifics:
`<record id="..." model="...">` creates one row in that model's table, and each
`<field name="...">value</field>` inside it sets one column by its technical field
name. That's the whole idea, no special syntax yet, it's the same "set a field on a
record" you already did from Python in chapter 9, just written as tags instead of
`env["model"].create({...})`.

The fields this file actually sets, in plain terms:

| Field | What it means here |
|---|---|
| `category_id` | which section of Settings this privilege is filed under (Services). Cosmetic, doesn't affect permissions. |
| `sequence` | display order among sibling groups: User is 10, Manager is 20, so User lists first. Also cosmetic. |
| `privilege_id` | which privilege this group belongs to. Both groups point at the same `privilege_librefleet` record above, that's what makes them "Workshop / User" and "Workshop / Manager" instead of two unrelated groups. |
| `comment` | the description shown on the group's own page in Settings → Users & Companies → Groups. For humans; no code reads it. |

And three things that are real syntax, not just field names:

- Every `<record>` gets an **<Term k="XML id (external id)">XML id</Term>** (`id="group_librefleet_user"`), a stable
  handle other files and modules use to point at the record. `ref("...")` resolves
  one; ids from other modules need the module prefix (`base.group_user`).
- `eval="[(4, ref(...))]"` is the ORM's command syntax for x2many fields, and every
  command is a small integer, not an arbitrary one: `0` would create a brand-new
  related record, `6` would replace the whole set, and `4` links to one that
  already exists, which is all you want here. Chapter 12 names the rest of the
  family and their readable `Command.link(...)`-style spellings; for now, `4`
  just means "link, don't create".
- The Manager group adds `base.user_admin` to `user_ids`. Skip that line and even
  admin stays locked out of your app; core modules do exactly the same.
</Step>

<Step>
### Grant the permissions

`addons/librefleet/security/ir.model.access.csv`:

```csv
id,name,model_id:id,group_id:id,perm_read,perm_write,perm_create,perm_unlink
access_librefleet_vehicle_user,librefleet.vehicle user,model_librefleet_vehicle,group_librefleet_user,1,1,0,0
access_librefleet_vehicle_manager,librefleet.vehicle manager,model_librefleet_vehicle,group_librefleet_manager,1,1,1,1
```

Three of these columns have "id" in the name, and they are not the same kind of id:

- **`id`** is a brand-new XML id for *this access rule itself*, same idea as the
  `id="..."` attribute on an XML `<record>`. Nothing points at it here, but
  something could.
- **`model_id:id`** and **`group_id:id`** are references to *other* records' XML
  ids, the model's and the group's. The `:id` suffix is CSV's way of saying "look
  this value up as an external id" instead of taking it as literal text, the same
  job `ref("...")` does in XML. That's why `model_librefleet_vehicle` works: it's
  an XML id the ORM generated automatically for the model when chapter 9's upgrade
  registered it (pattern: `model_` + `_name` with dots as underscores), not a
  string you invented.

With that sorted out, read the two rows as a matrix: technicians read and update
vehicles (a mileage correction after a service is their daily job), only managers
register new vehicles or delete them. The four `perm_*` booleans are exactly the
ones the Concepts section named above.
</Step>

<Step>
### Declare both files, in the right order

In the manifest, bump the version and fill `data`:

```python
    "version": "19.0.1.2.0",
    "data": [
        "security/librefleet_security.xml",
        "security/ir.model.access.csv",
    ],
```

The list is loaded top to bottom, and the CSV references the groups, so the XML must
come first. Hold that thought until the break-it lab. The module now looks like this,
and `data` is what ties the two new files to it:

<Files className="bg-(--tone-sky)">
  <Folder name="addons/librefleet" defaultOpen>
    <File name="__init__.py" />
    <File name="__manifest__.py" />
    <Folder name="models">
      <File name="__init__.py" />
      <File name="vehicle.py" />
    </Folder>
    <Folder name="security" defaultOpen>
      <File name="ir.model.access.csv" />
      <File name="librefleet_security.xml" />
    </Folder>
    <Folder name="static/description">
      <File name="icon.png" />
    </Folder>
  </Folder>
</Files>

Upgrade:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial -u librefleet --stop-after-init
...
INFO tutorial odoo.modules.loading: loading librefleet/security/librefleet_security.xml
INFO tutorial odoo.modules.loading: loading librefleet/security/ir.model.access.csv
INFO tutorial odoo.modules.loading: Module librefleet loaded in 0.06s, 76 queries (+76 other)
```

Chapter 9's WARNING about missing access rules is gone. (The query count moves a
little between runs, ours has shown 76 and 78 on otherwise identical upgrades; don't
worry if yours differs.)

That upgrade ran in its own process, separate from your long-running web server. You
might expect to need a restart before the server notices, the way a pure Python
change does without `dev=all` (chapter 6). It doesn't: every request, HTTP or RPC,
starts by checking a small signaling table (`orm_signaling_registry`) for a change
another process made, and reloads the registry first if so. Security data is exactly
the kind of change this catches, so the very next request after the upgrade already
sees it, no restart needed.
</Step>

<Step>
### Create a technician to test with

You need a user who is *only* a technician. From `odoo shell`:

```console
$ docker compose exec odoo odoo shell -c /etc/odoo/odoo.conf -d tutorial --no-http
>>> tina = env["res.users"].create({
...     "name": "Tina Technician",
...     "login": "tina",
...     "password": "technician",
...     "group_ids": [(4, env.ref("librefleet.group_librefleet_user").id)],
... })
>>> tina.group_ids.mapped("full_name")
['Workshop / User']
>>> env.cr.commit()
```

There's `env.ref()` again: the Python side of XML id resolution.
</Step>

<Step>
### Feel the permissions with `with_user`

Still in the shell (or a new one), replay tina's workday:

```console
>>> Vehicle = env["librefleet.vehicle"].with_user(tina)
>>> Vehicle.search([]).mapped("display_name")
['ZH 468 202', 'BE 30 447']
>>> Vehicle.browse(1).mileage_km = 84900.0        # back from a service run
>>> env.cr.commit()
>>> Vehicle.create({"license_plate": "GE 11 222"})
AccessError: You are not allowed to create 'Workshop Vehicle' (librefleet.vehicle) records.

This operation is allowed for the following groups:
	- Workshop/Manager

Contact your administrator to request access if necessary.
```

Read, allowed. Write, allowed. Create, refused, and the error even names the group
that could (notice your chapter 9 `_description` doing its job in that message).
The server log tells the same story from its side:

```text
INFO tutorial odoo.addons.base.models.ir_model: Access Denied by ACLs for operation: create, uid: 5, model: librefleet.vehicle
```

And the escape hatch you should distrust on sight: <Term k="sudo()">`Vehicle.sudo()`</Term> returns to
superuser and would happily create the record. Try it, see it work, then quit
*without* committing. `sudo()` has legitimate uses (chapter 15 sets the rules), but
every one of them deserves a comment explaining itself.
</Step>

<BreakIt />
### Break-it lab: the bug that only bites on fresh installs

Swap the two lines in the manifest's `data` list so the CSV loads first, then
upgrade. Expecting an explosion?

```text
INFO tutorial odoo.modules.loading: loading librefleet/security/ir.model.access.csv
INFO tutorial odoo.modules.loading: loading librefleet/security/librefleet_security.xml
INFO tutorial odoo.modules.loading: Module librefleet loaded in 0.05s, 78 queries (+78 other)
```

It *works*. Your database already contains the group records from the previous
upgrade, so the CSV's references resolve against them no matter the file order. Now
run the same code as a brand-new install, the way your client's production server
will meet it:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d freshtest -i librefleet --stop-after-init
...
CRITICAL freshtest odoo.service.server: Failed to initialize database `freshtest`.
Exception: Module loading librefleet failed: file librefleet/security/ir.model.access.csv could not be processed:
No matching record found for external id 'group_librefleet_user' in field 'Group'
No matching record found for external id 'group_librefleet_manager' in field 'Group'
```

Same module, dead on arrival. This class of bug (data order, missing file, renamed
XML id) hides perfectly in the database you develop on, because that database
remembers every version you ever loaded:

<Mermaid
  label="Whether the misordered access CSV breaks the module depends only on whether the group's XML id already exists in the database: harmless on a dev box that loaded it before, fatal on a fresh install"
  chart={`flowchart TD
    CSV["ir.model.access.csv loads,<br/>looks up group_librefleet_user"]
    CSV --> Q{"Does that XML id<br/>already exist in this database?"}
    Q -- "yes: your dev database,<br/>loaded it in an earlier upgrade" --> OK["resolves fine,<br/>the bug stays invisible"]
    Q -- "no: a fresh install,<br/>the database starts empty" --> FAIL["No matching record found<br/>for external id 'group_librefleet_user'"]`}
/>

The antidote is cheap and worth making a habit: before shipping, install into a
throwaway database exactly as above. Restore the manifest order, rerun the fresh
install to see it pass, then clean up:

```console
$ docker compose exec odoo odoo db -c /etc/odoo/odoo.conf drop freshtest
```

## Gotchas

- **Restarting after a data or security change is folklore, not a requirement.** The
  registry's own signaling table gets checked on every request, so the very next one
  after a separate process's `-u` already sees it. What actually needs a restart (or
  `dev=all`'s autoreload) is a pure Python change, chapter 6's rule, not this one.
- **The data-order bug is invisible on your database.** Once an XML id exists in the
  DB, later loads resolve it regardless of file order. Only a fresh install tells
  the truth; test one before every release.
- **ACLs are additive, so there is no "deny" line.** If a user seems to have too
  much power, some group they're in grants it; hunt the union, don't try to
  subtract. Settings → Technical → Access Rights filters by model.
- **Don't paste the WARNING's suggested line as-is.** The chapter 9 hint granted
  read to `base.group_user`: *every internal user in the company*. It's a syntax
  example, not a security design. Decide who needs what first.
- **admin is not the superuser.** Adding ACLs for your new groups does nothing for
  admin until admin joins one of them (the `user_ids` line). If admin "can't see
  the app you just secured", that line is missing.
