## Why this matters

Every chapter since 9 has quietly used recordsets: computes loop over `self`,
constraints call `search_count`, the shell sessions call `search` and `create`. This
chapter stops using them by imitation and takes them apart. It's the highest-leverage
hour in Part 2: once recordsets click, you can read any Odoo code (core, OCA, your
colleagues') and the framework stops feeling magic. It's also where you learn the two
tools that separate maintenance work from incidents: `with_user` to test as somebody
else, and `sudo` used deliberately instead of sprinkled until the error goes away.

Before any of it, one wrong idea to put down, because almost everybody arrives holding it
and it is the source of the errors in this chapter. **A recordset looks like a list of
records, and it is not one.** It iterates like a list, slices like a list and has a
length like a list, so the intuition survives for a surprisingly long time before it
fails.

What it actually is: **one object pretending to be many.** A model name, a tuple of ids,
and a cache, all in a single object. The consequence to hold on to is that when you loop
over a recordset of ten orders, you do not get ten order objects. You get the same kind
of object ten times, each holding one id. That is why `for line in self` is the shape of
every compute you have written since chapter 13, and it is why the rule in the next
section exists at all rather than being an arbitrary restriction.

type along; the outputs shown are real:

## Concepts

### One object to rule them all

A **<Term k="recordset">recordset</Term>** is an ordered collection of records of one model. It might hold zero
records, one, or many, and *every* ORM surface hands you one:

- `env["librefleet.vehicle"]` is an **empty** recordset of that model (and the thing
  you call model-level methods on).
- `search()` returns a recordset of whatever matched, in `_order`.
- `browse(ids)` wraps ids you already have in a recordset, without touching the
  database.
- Inside a model method, `self` is a recordset (that's why computes and constraints
  loop).
- Reading a many2one gives a recordset of 0 or 1 records; one2many and many2many give
  recordsets of any size.

Under the hood a recordset is just three things: an environment (`env`), a model name,
and a tuple of record ids. That's why they're cheap to create, slice and combine; no
data is loaded until you actually read a field.

### Singleton vs multi: the one rule that bites

Reading a *scalar* field (`char`, `integer`, `selection`...) requires a recordset of
**exactly one** record, a *<Term k="singleton">singleton</Term>*. Read it on two records and Odoo refuses,
because "the stage of these two orders" has no single answer:

```console
>>> orders = env["librefleet.service.order"].search([])
>>> orders
librefleet.service.order(2, 1)
>>> orders.stage
ValueError: Expected singleton: librefleet.service.order(2, 1)
```

That `Expected singleton` error is the most common traceback new Odoo developers
produce. The fixes are always one of: loop (`for order in orders:`), aggregate
(`orders.mapped("stage")`), or narrow down (`orders[0]`). Relational fields are the
exception, multi-record access just unions the targets:

```console
>>> orders.mapped("stage")
['draft', 'draft']
>>> orders.vehicle_id
librefleet.vehicle(2, 1)
```

In your own methods, when the logic only makes sense for one record, say so up front
with `self.ensure_one()`: it raises that same error early, with your method's name in
the traceback instead of some confusing line further down.

### The environment: who, where, with what settings

Every recordset carries its `env`, and the env answers three questions:

| Attribute | Question it answers | Example value in the shell |
|---|---|---|
| `env.user` / `env.uid` | who is acting? | `__system__`, uid `1` |
| `env.cr` | which open database transaction? | one per shell session, until you `commit()` or `rollback()` |
| `env.context` | with which settings? | `{'lang': 'en_US', 'tz': False, 'uid': 1}` |

Plus two conveniences you'll use constantly: `env["model.name"]` to get a model's
empty recordset, and `env.ref("module.xml_id")` to fetch the record behind an XML id:

```console
>>> env.user.login, env.uid, env.company.name
('__system__', 1, 'My Company')
>>> env.ref("librefleet.seq_librefleet_service_order").code
'librefleet.service.order'
```

Notice who you are in the shell: `__system__`, uid 1, the **<Term k="superuser">superuser</Term>**. The shell
skips authentication entirely, and uid 1 bypasses access rights and record rules.
Convenient for admin work, and exactly why "it worked in the shell" proves nothing
about what a real user can do. You'll fix that with `with_user` below.

The **<Term k="context">context</Term>** is a read-only dict of settings that travels with every call:
language, timezone, and flags that change ORM behavior. You never mutate it; you
derive a new recordset carrying a modified copy:

```python
records.with_context(active_test=False)   # new recordset, extended context
records.with_user(some_user)              # new recordset, acting as that user
records.sudo()                            # new recordset, superuser mode on
```

All three return a *new* recordset with the same ids and a different env. The original
is untouched.

### Search happens in SQL, filtered happens in Python

Both give you a subset, and choosing well is a performance habit worth building on
day one:

<Mermaid
  label="search pushes a domain into Postgres and only matching rows travel back, while filtered loops in Python over records already in memory"
  chart={`flowchart LR
    subgraph P["Postgres does the work"]
      S["search(domain)"] --> SQL["SELECT ... WHERE ..."]
    end
    subgraph M["Python does the work"]
      F["records.filtered(fn)"] --> RAM["loops records already<br/>loaded in memory"]
    end
    SQL --> R1["only matching rows travel"]
    RAM --> R2["fine on a page of records,<br/>wasteful on a whole table"]`}
/>

**`search`** sends a domain to Postgres: only matching rows come back, indexes get
used, and it scales to millions of records. **`filtered`** runs a Python function over
records you already have: perfect for narrowing a small in-memory set without another
round-trip, wasteful (or fatal) as a substitute for a proper domain on a big table.
The rule of thumb: filter in SQL when you *fetch*, filter in Python when you already
*hold*.

### Domains, properly

A domain is a list of `(field, operator, value)` triples. Conditions are **ANDed by
default**; prefix operators combine them differently: `"|"` (OR), `"&"` (explicit
AND), `"!"` (NOT), each consuming the next two (or one, for `!`) terms. The operators
you'll actually use:

| Operator | Meaning |
|---|---|
| `=`, `!=`, `>`, `>=`, `<`, `<=` | comparison |
| `in`, `not in` | membership in a list |
| `like` / `ilike` | substring match, case-sensitive / insensitive (`%` wildcards allowed) |
| `=like` / `=ilike` | pattern match where *you* place every wildcard |
| `child_of` / `parent_of` | hierarchy walks (categories, companies) |
| dotted paths | `("vehicle_id.owner_id.name", "ilike", "garage")` follows relations |

You've been writing domains since chapter 12; the part people miss is the prefix
notation. `["|", A, B]` is "A or B"; `["|", A, "&", B, C]` is "A or (B and C)". When a
domain grows past two branches, format it vertically and comment it, future-you will
be grateful.

### Writing: create, write, unlink, archive

Four verbs change data, and each has a batch-shaped best practice:

- **`create(vals_list)`** takes a *list of dicts* and returns a recordset of the new
  records. One call creating fifty records is dramatically cheaper than fifty calls;
  that's also why overridable `create` methods take `vals_list` (you'll write one
  today).
- **`write(vals)`** on a recordset applies the same values to every record in it, in
  one operation. `record.field = value` is sugar for a one-field write.
- **`unlink()`** deletes every record in the set. Gone means gone (subject to
  `ondelete` rules from chapter 12).
- **Archiving** is the soft alternative: set `active = False` and the record
  vanishes from every default search but keeps existing (chapter 9 gave vehicles an
  `active` field for exactly this). To see archived records, extend the context:
  `with_context(active_test=False)`.

### sudo and with_user: power tools, sharp edges

`with_user(user)` re-runs everything as that user: their groups, their access rights,
their record rules. It's how you *test* security without logging out and back in, and
how cron jobs act on behalf of specific users.

`sudo()` flips the superuser bit (`env.su`) on a derived recordset: access rights and
record rules stop applying, while `env.user` stays whoever it was. Legitimate uses are
narrow and real: a controller that must read config the visitor can't, a cron touching
records nobody owns. The dangers are just as real: sudo silently succeeds where a
permission error *should* have stopped you, it spreads (records fetched through a
sudo'd recordset are sudo'd too), and it turns a reader's "why can this user do that?"
into archaeology. House rule you'll see at every serious integrator: sudo the
*smallest possible operation*, never the whole method, and leave a comment saying why.

## Hands-on

<Steps>

<Step>
### Anatomy of a recordset

In the shell, meet the three faces of the same object:

```console
>>> Vehicle = env["librefleet.vehicle"]
>>> Vehicle
librefleet.vehicle()
>>> orders = env["librefleet.service.order"].search([])
>>> orders
librefleet.service.order(2, 1)
>>> orders.ids
[2, 1]
```

Empty recordset, then a two-record one. The ids come back as `(2, 1)` because chapter
12 gave the model `_order = "scheduled_start desc, id desc"` and order 2 is scheduled
later. Recordsets behave like sequences:

```console
>>> len(orders)
2
>>> orders[0]
librefleet.service.order(2,)
>>> orders[0].reference
'SO/2026/0002'
>>> orders[::-1]
librefleet.service.order(1, 2)
```

And like sets, with `|` (union), `&` (intersection), `-` (difference), `in`:

```console
>>> both = Vehicle.browse(1) | Vehicle.browse(2)
>>> both
librefleet.vehicle(1, 2)
>>> both - Vehicle.browse(1)
librefleet.vehicle(2,)
>>> Vehicle.browse(1) in both
True
```

`browse` deserves one experiment: it doesn't check the database, it just wraps ids.
Browse something that doesn't exist and nothing complains until you look:

```console
>>> ghost = Vehicle.browse(999)
>>> ghost
librefleet.vehicle(999,)
>>> ghost.exists()
librefleet.vehicle()
```

`exists()` is the guard: it returns the subset of records that are really in the
database. Any code that receives ids from outside (a controller, an import, a cron
argument) should pass them through `exists()` before trusting them.
</Step>

<Step>
### Trip over the singleton rule, on purpose

```console
>>> orders.stage
ValueError: Expected singleton: librefleet.service.order(2, 1)
>>> orders.mapped("stage")
['draft', 'draft']
>>> orders.vehicle_id
librefleet.vehicle(2, 1)
```

Scalar field on two records: refused. `mapped` collects the values; relational access
unions the targets. You'll hit this error for real within a week of writing Odoo code;
now you'll recognize it in one second.
</Step>

<Step>
### The search toolbox

Work through these and predict each result before running it:

```console
>>> SO = env["librefleet.service.order"]
>>> SO.search([("stage", "=", "draft")]).mapped("reference")
['SO/2026/0002', 'SO/2026/0001']
>>> SO.search([], order="reference", limit=1).reference
'SO/2026/0001'
>>> SO.search_count([])
2
>>> env["librefleet.vehicle"].search([("license_plate", "ilike", "zh")]).mapped("license_plate")
['ZH 468 202']
>>> SO.search(["|", ("stage", "=", "done"), ("reference", "=", "SO/2026/0001")]).mapped("reference")
['SO/2026/0001']
```

Note `order=` and `limit=` doing their work in SQL, `search_count` skipping the fetch
entirely (it becomes a `SELECT count(*)`), and the `"|"` prefix taking the next two
conditions. `ilike` matched `zh` against `ZH 468 202` case-insensitively.
</Step>

<Step>
### filtered, mapped, sorted, grouped

The in-memory quartet, on the orders you already hold:

```console
>>> orders = SO.search([])
>>> orders.mapped("vehicle_id.license_plate")
['BE 30 447', 'ZH 468 202']
>>> orders.filtered(lambda o: o.margin > 0).mapped("reference")
['SO/2026/0002', 'SO/2026/0001']
>>> orders.sorted("reference", reverse=True).mapped("reference")
['SO/2026/0002', 'SO/2026/0001']
>>> {k.license_plate: v.mapped("reference") for k, v in orders.grouped("vehicle_id").items()}
{'BE 30 447': ['SO/2026/0002'], 'ZH 468 202': ['SO/2026/0001']}
```

`mapped` takes a dotted path and follows relations (deduplicating recordset results on
the way). `filtered` takes a function (or a field name: `orders.filtered("notes")`
keeps records where the field is truthy). `sorted` takes a field name or a key
function. `grouped` buckets a recordset into a dict in one pass: each key is a value of
the field you grouped on, and each value is a recordset of the records sharing it.
Group on a many2one and the keys are whole *vehicle records*, which is why the
comprehension above can write `k.license_plate` for the key and `v.mapped("reference")`
for the group. All four operate on what's already in memory; none of them touches
Postgres. Notice `margin` computing on
demand inside `filtered`: chapter 13's non-stored computes work transparently here.
</Step>

<Step>
### Create in batch, write in batch

Three new vehicles, one call, then one write that hits all three:

```console
>>> new = Vehicle.create([
...     {"license_plate": "SHELL-001", "model_name": "Toyota Hilux", "year": 2021},
...     {"license_plate": "SHELL-002", "model_name": "VW Caddy", "year": 2019},
...     {"license_plate": "SHELL-003", "model_name": "Ford Transit", "year": 2015},
... ])
>>> new
librefleet.vehicle(16, 17, 18)
>>> new.write({"notes": "Checked in bulk from the shell"})
True
>>> new.mapped("notes")
['Checked in bulk from the shell', 'Checked in bulk from the shell', 'Checked in bulk from the shell']
```

Two things worth noticing. `create` took a list and returned a recordset of all three.
And the new ids jumped to 16–18 even though you only ever saw two vehicles: every
failed create from chapter 14's constraint experiments consumed a primary-key id.
Postgres id sequences leak on rollback exactly like `ir.sequence` does; gaps in ids
are as normal as gaps in order references.
</Step>

### Archive one, delete one, and meet active_test

`new` still holds the three vehicles in the order you created them, so `new[1]` is
SHELL-002 and `new[2]` is SHELL-003. Archive the first of those, delete the second,
then go looking for all three:

```console
>>> new[1].active = False
>>> new[2].unlink()
True
>>> Vehicle.search([("license_plate", "like", "SHELL")]).mapped("license_plate")
['SHELL-001']
>>> Vehicle.with_context(active_test=False).search([("license_plate", "like", "SHELL")]).mapped("license_plate")
['SHELL-001', 'SHELL-002']
>>> env.cr.commit()
```

The plain search shows only SHELL-001: archived records are invisible to every default
search, which is precisely their point (chapter 9's Gotcha, now demonstrated).
`active_test=False` in the context reveals SHELL-002. SHELL-003 is nowhere: unlink is
permanent. The `commit()` matters, as always in the shell, and this exact state
(SHELL-001 active with its note, SHELL-002 archived, SHELL-003 gone) is what
`odoolings` will verify.
</Step>

<BreakIt />
### Become tina: record rules in action (break-it lab)

Chapter 10's record rule says technicians may only *write* orders they're assigned
to. The shell's superuser never feels that rule; `with_user` does:

```console
>>> tina = env["res.users"].search([("login", "=", "tina")])
>>> as_tina = SO.with_user(tina)
>>> as_tina.search([]).mapped("reference")
['SO/2026/0002', 'SO/2026/0001']
```

Both orders! Look back at the rule in `security/librefleet_security.xml`: it sets
`perm_read` to `False`, so it filters writes but not reads. Tina can see the whole
board and edit only her own work, a deliberate design. Now break it: write to the
order she's assigned to (order 1, from chapter 12), then to the other one:

```console
>>> as_tina.search([("reference", "=", "SO/2026/0001")]).write({"notes": "brake pads ordered"})
True
>>> as_tina.search([("reference", "=", "SO/2026/0002")]).write({"notes": "tina was here"})
odoo.exceptions.AccessError: Uh-oh! Looks like you have stumbled upon some top-secret records.

Sorry, Tina Technician (id=5) doesn't have 'write' access to:
- Service Order (librefleet.service.order)
```

That AccessError is the security model doing its job (Odoo's error copy included).
Now watch `sudo()` defeat it, which is the part to remember viscerally:

```console
>>> as_tina.sudo().search([("reference", "=", "SO/2026/0002")]).write({"notes": "sudo bypasses the record rule"})
True
>>> sneaky = as_tina.sudo()
>>> sneaky.env.user.login, sneaky.env.su
('tina', True)
>>> env.cr.rollback()
```

Same user (`env.user` is still tina), superuser bit on, rule gone, write accepted, no
warning anywhere. In a real module this line would be a security bug: any code path
tina can trigger now edits orders she was explicitly fenced off from. Roll it back and
remember the house rule: sudo the smallest operation, comment why, and never use it to
make an AccessError "go away" without understanding what the error protected.
</Step>

### Move the sequence draw into create

Chapter 14 left a known wart: the callable default draws a number the moment a form
opens, so every abandoned "New" burns one. Production modules (look at `sale.order` in
core someday) draw the number **in `create`**, when the record is actually saved. Two
edits in `models/service_order.py`:

- **Replace the `reference` field** with the version below. Only the default changes:
  chapter 14's `default=lambda self: ... next_by_code(...)` becomes the plain string
  `"New"`, so opening a form no longer touches the sequence at all.
- **Add a `create` method** to the `ServiceOrder` class, below the field declarations
  and above `_compute_totals`. By convention the methods that create, write and delete
  records sit there, between the fields and the computes.

```python
    reference = fields.Char(
        required=True, copy=False, readonly=True, default="New",
        help="Human-readable order number, assigned from the sequence "
             "when the order is saved.")

    @api.model_create_multi
    def create(self, vals_list):
        for vals in vals_list:
            if vals.get("reference", "New") == "New":
                vals["reference"] = self.env["ir.sequence"].next_by_code(
                    "librefleet.service.order") or "New"
        return super().create(vals_list)
```

That `create` method is your first **override**, so slow down on it. Every model
already inherits a `create` from Odoo's base `Model` class; writing a method with the
same name in your own class means yours is the one that runs, which is what gives you
a chance to edit `vals_list` before anything is stored. `super()` is plain Python for
"the version I just replaced", so `super().create(vals_list)` hands the now-numbered
values to Odoo's real create, which does the standard work (defaults, constraints from
chapter 14, computes from 13) and returns the new recordset. Leave that line out and
no record is ever written.

The rest reads with this chapter's eyes. `@api.model_create_multi` declares the
batch-friendly signature: `vals_list` is a *list* of dicts, exactly what you passed in
step 5, and the loop stamps a number on each entry that doesn't already have one. The
decorator also keeps single-record callers working: hand `create()` one plain dict and
it wraps that dict in a one-item list before your method sees it, so your loop is
always safe. The `vals.get(...) == "New"` guard leaves imported or copied values alone
if a caller supplied a real reference, and it is why the field keeps `default="New"`:
a form sends that literal along on save, and the guard reads it as "no number yet".

## Gotchas

- **`Expected singleton` is a recordset holding more than one record.** The read
  `record.field` needs exactly one. Loop, `mapped`, or index; and open your own
  single-record methods with `self.ensure_one()` so the error names the real culprit.
- **The shell is the superuser.** uid 1 skips access rights and record rules, so "it
  works in the shell" says nothing about real users. Test permissions with
  `with_user`, always.
- **`sudo()` spreads.** Records reached through a sudo'd recordset are sudo'd too:
  `order.sudo().vehicle_id.owner_id` walks two relations with security off. Derive
  sudo for one operation, not at the top of a method.
- **`filtered` on what you should have `search`ed.** Filtering a whole table in
  Python loads the whole table. Domain in SQL to fetch, Python to narrow what you
  already hold.
- **`browse` never validates.** It happily wraps ids that don't exist and fails only
  on field access. Ids from any external source go through `.exists()` first.
- **Forgetting `env.cr.commit()` in the shell.** The session is one transaction;
  quit without committing and everything you "did" evaporates. (Deliberate rollback
  is equally useful: experiment freely, `env.cr.rollback()`, clean slate.)
