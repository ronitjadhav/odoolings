title: "14. Constraints, Defaults & Sequences"
description: Make bad data impossible with SQL and Python constraints, fill sensible values automatically with defaults, and give records real numbers with sequences.
---

**Goal:** stop LibreFleet from ever storing a duplicate plate, an impossible model
year, or a double-booked vehicle, and give every service order a proper reference
number. · **Time:** ~2 h · **Checkpoint:** `code/checkpoints/ch14`

## Why this matters

Chapter 13 was about numbers that compute themselves. This one is about the values a user
*does* type, and the promise that they will never be nonsense.

Two workshops can't share one license plate. A car built in the year 1200 is a typo. One
vehicle can't be on two lifts at once. Every real Odoo module is ringed with these
guarantees, because the alternative (trusting the form, trusting the importer, trusting
next year's intern) is how databases rot.

You will build both kinds of guard Odoo gives you, one enforced by Postgres and one by
Python, learn exactly which paths each covers, and then hand every order a clean sequence
number the way every invoice and sale order in Odoo gets one.

## Concepts

### Two places to enforce a rule

Odoo lets you validate data at two different layers, and choosing correctly is the
whole skill:

- **<Term k="constraint (SQL)">SQL constraints</Term>** live in the database. Postgres itself refuses the write, so
  *nothing* gets past them: not a buggy method, not a raw SQL script, not a
  concurrent transaction racing yours. The catch is that SQL only speaks a few
  dialects of "no": `UNIQUE`, `CHECK (simple expression)`, foreign keys. On Odoo 19
  you declare them with `models.Constraint`.
- **<Term k="constraint (Python)">Python constraints</Term>** (`@api.constrains`, a decorator naming the fields to watch)
  run in the ORM, in your own code. They can express anything Python can: look at other
  records, follow relations, compare datetimes, call a method. They raise
  `ValidationError` with a friendly message. Their limit mirrors SQL's strength: they
  only fire on ORM writes (form, import, RPC, shell, other modules), never on raw SQL,
  and only re-run when a field they *declare* actually changes.

<Mermaid
  label="How a write reaches Python constraints only on the ORM path, while SQL constraints catch every path at the database"
  chart={`flowchart TD
    W["A write arrives"] --> P{"which path?"}
    P -- "ORM: form, import,<br/>RPC, shell, code" --> PY["@api.constrains<br/>runs in Python"]
    P -- "raw SQL" --> SKIP["Python checks skipped"]
    PY --> DB[("Postgres commit")]
    SKIP --> DB
    DB --> SQL{"models.Constraint<br/>UNIQUE / CHECK"}
    SQL -- "violated" --> REJECT["write refused,<br/>nobody bypasses this"]
    SQL -- "ok" --> DONE["stored"]`}
/>

The rule of thumb: **if a guarantee must hold no matter what, it belongs in SQL.**
Uniqueness is the classic case. If the rule needs judgment (does this booking overlap
another one? is this year plausible?), it belongs in Python. Many models use both.

<Callout type="info" title="On Odoo 18 this differs">
  Odoo 18 and earlier declare SQL constraints as a `_sql_constraints` list of
  `(name, definition, message)` tuples. Odoo 19 replaced that with the
  `models.Constraint` pseudo-field, and warns if you use the old list:
  `Model attribute '_sql_constraints' is no longer supported`. The database result is
  identical; only the Python spelling changed. You'll meet plenty of `_sql_constraints`
  in existing code, so recognize both.
</Callout>

### Defaults: the value before the user types

A field's <Term k="default value">`default`</Term> supplies its starting value on a brand-new record. Two forms:

```python
stage = fields.Selection([...], default="draft")        # static
reference = fields.Char(default=lambda self: _next())    # callable, computed per record
```

A static default is a constant. A callable default is a function Odoo calls once per new
record, so it can be dynamic: today's date, the current user, the next number from a
sequence.

Defaults are suggestions with teeth. They fill the field, but the user (or code) can still
change the value before saving. Unlike chapter 13's onchange, they fire on every creation
path.

### Sequences: real numbers, centrally managed

You never want application code inventing `"SO/2026/0001"` with string formatting and a
`SELECT max(...)`, because two users creating orders at once would collide.

Odoo ships a <Term k="sequence (ir.sequence)">sequence</Term> (`ir.sequence`) for exactly this: a named counter with a prefix,
padding, and per-period reset, safe under concurrency. You define one as a data record and
pull numbers with `next_by_code("your.code")`.

One property surprises everyone once: **sequences are not transactional.** Drawing a
number advances the counter immediately, even if your transaction later rolls back. That
is deliberate, and it is what makes them collision-free without locking.

The consequence is that sequences have *gaps*, and gaps are normal. An auditor demanding
gapless invoice numbers needs a different, locking strategy. For an internal order
reference, simply expect them.

## Hands-on

<Steps>

<Step>
### A unique license plate (SQL constraint)

In `models/vehicle.py`, import `ValidationError` (you'll need it in step 2) and
declare the constraint at the top of the class:

```python
from odoo import api, fields, models
from odoo.exceptions import ValidationError


class Vehicle(models.Model):
    _name = "librefleet.vehicle"
    _description = "Workshop Vehicle"
    _rec_name = "license_plate"

    _license_plate_unique = models.Constraint(
        "unique(license_plate)",
        "That license plate is already registered on another vehicle.",
    )
```

The attribute name (`_license_plate_unique`) becomes the constraint's name in
Postgres; the first string is raw SQL added with `ADD CONSTRAINT`; the second is the
message users see when they hit it. That's the whole declaration, and Postgres does
the enforcing.
</Step>

<Step>
### A believable model year (Python constraint)

Uniqueness is a job for SQL. "Is this year plausible?" needs a comparison against
*this* year, so it's Python. Add to the vehicle model:

```python
    @api.constrains("year")
    def _check_year(self):
        current_year = fields.Date.today().year
        for vehicle in self:
            if vehicle.year and not (1900 <= vehicle.year <= current_year + 1):
                raise ValidationError(
                    "Model year %s is out of range (1900 to next year)."
                    % vehicle.year)
```

Three habits worth copying:

- **The decorator lists the fields that trigger the check** (`year`), so it only re-runs
  when `year` changes, not on every write. That list works exactly like chapter 13's
  `@api.depends`: trigger wiring, not documentation. That is why the rest of this chapter
  calls it the constraint's depends list, even though the decorator is spelled
  `constrains`.
- **It loops over `self`**, because constrains, like computes, receive a recordset.
- **It skips the empty case** (`if vehicle.year`), so a blank year does not trip the rule.
  `0` and `False` are legitimately "no year given".
</Step>

<Step>
### The sequence and the reference field

Create `data/ir_sequence.xml`:

```xml
<?xml version="1.0" encoding="utf-8"?>
<odoo>
    <!-- noupdate: create once, never overwrite on upgrade, so the running
         next-number is preserved (chapter 34 goes deeper on noupdate). -->
    <data noupdate="1">
        <record id="seq_librefleet_service_order" model="ir.sequence">
            <field name="name">LibreFleet Service Order</field>
            <field name="code">librefleet.service.order</field>
            <field name="prefix">SO/%(year)s/</field>
            <field name="padding">4</field>
            <field name="company_id" eval="False"/>
        </record>
    </data>
</odoo>
```

Four things in that record:

- **`code`** is the handle you look the sequence up by.
- **`prefix`** supports date tokens, so `%(year)s` bakes the year in, and **`padding`**
  zero-pads the counter to four digits.
- **An empty `company_id`** makes this a shared sequence. (`eval="False"` writes the
  Python value `False`, not the text "False".) `next_by_code` only considers sequences
  belonging to your current company or to no company at all, and LibreFleet has no reason
  to number orders per company.
- **`noupdate="1"`** matters most. Without it, every module upgrade would rewrite the
  record and reset its counter to 1, renumbering your live orders. You want this created
  once and then left alone.

Register the file in `__manifest__.py`, after the security files and before the views:

```python
    "data": [
        "security/librefleet_security.xml",
        "security/ir.model.access.csv",
        "data/ir_sequence.xml",
        "views/vehicle_views.xml",
        ...
```

Now the field. In `models/service_order.py`, add `reference` as the first field on the
`ServiceOrder` class, and point the model's display name at it. Chapter 12 set
`_rec_name = "vehicle_id"` because a plate was the best label an order had; an order
number is better, so edit that existing line instead of adding a second one:

```python
    _rec_name = "reference"

    reference = fields.Char(
        required=True, copy=False, readonly=True,
        default=lambda self: self.env["ir.sequence"].next_by_code(
            "librefleet.service.order") or "New",
        help="Human-readable order number, assigned from a sequence.")
```

The callable default draws the next number when an order is created. `copy=False` means
duplicating an order gets a fresh number instead of a clashing one, and `readonly=True`
because nobody hand-edits an order number. The `or "New"` is a safety net for the one
moment the sequence does not exist yet, which you are about to see.

Now put it on screen. Both edits are in `views/service_order_views.xml`.

In the order's list view, make `reference` the first column, ahead of `vehicle_id`:

```xml
            <list>
                <field name="reference"/>
                <field name="vehicle_id"/>
```

In the form view, put it in an `<h1>` as the first thing inside `<sheet>`, so the order
number reads as the record's title:

```xml
                <sheet>
                    <h1><field name="reference" readonly="1"/></h1>
```
</Step>

### Upgrade, and watch the backfill quirk

Bump the manifest to `19.0.1.6.0`, then upgrade and restart the running server so it
loads the new Python (Python changes need the restart; the upgrade alone runs in a
throwaway process):

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial -u librefleet --stop-after-init
$ docker compose restart odoo
```

Look at what the two orders you already have got for a reference:

```console
$ docker compose exec db psql -U odoo -d tutorial -c "select id, reference from librefleet_service_order order by id;"
 id | reference
----+-----------
  1 | New
  2 | New
```

Both say `New`, not `SO/2026/0001`. That is the safety net firing.

When Odoo added the new required column it backfilled existing rows using the field
default. But database tables are built *before* the data files load, so the sequence did
not exist yet and `next_by_code` returned nothing. Brand-new orders from here on will
number correctly; the legacy two need a one-time backfill.
</Step>

<Step>
### Backfill the legacy orders

Open a shell. Steps 5, 7 and 8 all happen in this one session, so leave it running
until the end of the chapter:

```console
$ docker compose exec odoo odoo shell -c /etc/odoo/odoo.conf -d tutorial --no-http
```

Now hand the existing orders real numbers:

```console
>>> SO = env["librefleet.service.order"]
>>> for rec in SO.search([], order="id"):
...     rec.reference = env["ir.sequence"].next_by_code("librefleet.service.order")
>>> env.cr.commit()
>>> [(r.id, r.reference) for r in SO.search([], order="id")]
[(1, 'SO/2026/0001'), (2, 'SO/2026/0002')]
```

This is the shape of a real data migration: new field, existing rows, a short script to
bring history in line. In production it would live in a migration step (chapter 49); here
the shell is fine.

Note `next_by_code` is how you pull a number outside a create, which is exactly what the
default does under the hood.
</Step>

<Step>
### No double-booked vehicles (a Python constraint that searches)

The overlap rule is the most interesting kind of constraint: it cannot judge a record in
isolation, it has to look at *other* orders.

It goes in `models/service_order.py`, and that file has never raised an exception before,
so widen its imports first:

```python title="addons/librefleet/models/service_order.py"
from odoo import api, fields, models
from odoo.exceptions import ValidationError
```

Miss that line and the module will not load at all: `ValidationError` becomes a
`NameError` while Odoo is importing your package. Then the constraint itself, on the
`ServiceOrder` class:

```python
    @api.constrains("scheduled_start", "scheduled_end", "vehicle_id", "stage")
    def _check_no_overlap(self):
        for order in self:
            if not (order.scheduled_start and order.scheduled_end):
                continue
            if order.scheduled_end <= order.scheduled_start:
                raise ValidationError(
                    "An order must end after it starts (check the schedule).")
            if order.stage == "cancelled":
                continue
            clash = self.search_count([
                ("id", "!=", order.id),
                ("vehicle_id", "=", order.vehicle_id.id),
                ("stage", "!=", "cancelled"),
                ("scheduled_start", "<", order.scheduled_end),
                ("scheduled_end", ">", order.scheduled_start),
            ])
            if clash:
                raise ValidationError(
                    "%s is already booked during that window."
                    % order.vehicle_id.license_plate)
```

`search_count` takes a domain and answers with a number: how many records match, never the
records themselves, which is all this check needs.

The domain is chapter 12's list of `(field, operator, value)` conditions, and conditions
sitting side by side in one list are ANDed. So a row is only counted when all five hold:
it is some *other* order (`("id", "!=", order.id)`, so an order can never clash with
itself), on the same vehicle, not cancelled, starting before this one ends, and ending
after this one starts.

Those last two are the whole overlap test: two windows overlap exactly when each one
starts before the other finishes. `stage` is in the trigger list too, so cancelling an
order re-runs the check and un-cancelling re-validates it.

Bump the manifest to `19.0.1.7.0`, upgrade, and restart.
</Step>

<Step>
### See all three guards fire

From the shell, try to break each rule. First the unique plate (order 1's vehicle is
`ZH 468 202`):

```console
>>> env["librefleet.vehicle"].create({"license_plate": "ZH 468 202"})
psycopg2.errors.UniqueViolation: duplicate key value violates unique constraint "librefleet_vehicle_license_plate_unique"
DETAIL:  Key (license_plate)=(ZH 468 202) already exists.
```

That is Postgres talking, not Odoo. In the shell you get the raw database error. In the
*UI*, Odoo catches it and shows your friendly message ("That license plate is already
registered on another vehicle."). Same guard, two audiences.

**Now do something that looks like housekeeping and is not.** A failed SQL statement
poisons the whole Postgres transaction, so until you clear it every further command
answers with the same complaint:

```console
>>> env.cr.rollback()
```

Skip it and the next two experiments report `psycopg2.errors.InFailedSqlTransaction:
current transaction is aborted, commands ignored until end of transaction block` instead
of the errors you were trying to see. That is a confusing five minutes if you do not know
why. Chapter 9's gotcha said the same thing; this is the chapter where it costs you
something.

Now the year and the overlap, both pure Python, each followed by its own rollback for the
same reason:

```console
>>> env["librefleet.vehicle"].create({"license_plate": "NEW-CAR", "year": 1850})
odoo.exceptions.ValidationError: Model year 1850 is out of range (1900 to next year).
>>> env.cr.rollback()
>>> env["librefleet.service.order"].create({
...     "vehicle_id": 1,
...     "scheduled_start": "2026-07-16 08:30:00",
...     "scheduled_end": "2026-07-16 09:30:00"})
odoo.exceptions.ValidationError: ZH 468 202 is already booked during that window.
>>> env.cr.rollback()
```

The overlap create collides with order 1's existing 08:00–09:00 window on the same
vehicle.

Be precise about what those rollbacks did, because it is easy to read them as undoing the
failures. They did not. A Python `ValidationError` already prevented its write, and the
`UniqueViolation` was refused by Postgres.

What the rollbacks cleared is the *transaction state* the first failure left behind. Your
two orders and two vehicles are untouched throughout, but not because anything "rolled
itself back" for you.
</Step>

### Break-it lab: watch a sequence leak numbers

Sequences give out numbers that a rollback can't take back. Watch the counter itself
rather than the references on your orders, because that makes the leak impossible to
miss. `number_next_actual` is the field on `ir.sequence` holding the number the
sequence will hand out next:

```console
>>> seq = env["ir.sequence"].search([("code", "=", "librefleet.service.order")])
>>> seq.number_next_actual
46
>>> o = env["librefleet.service.order"].create({
...     "vehicle_id": 1,
...     "scheduled_start": "2026-09-01 08:00:00",
...     "scheduled_end": "2026-09-01 09:00:00"})
>>> o.reference
'SO/2026/0046'
>>> env.cr.rollback()
>>> seq.number_next_actual
47
```

**Your numbers will not be 46 and 47, and that is the point.** Do not try to match them.
Read whatever your own counter says, then check it went up by exactly one. Mine is at 46
because this database has had orders created, `odoolings` run, and step 7's experiments
done to it. Yours has its own history, and any chapter promising you a specific reference
number is lying about a counter it cannot see.

What matters is the arithmetic: the number was drawn, the rollback threw the *record*
away, and the counter did not go back. That number is gone forever.

Step 7 already demonstrated this without saying so. Its overlap create failed on a Python
constraint, yet the callable default had already drawn a number before the constraint ever
ran, so that attempt spent one too.

Every abandoned draft, every failed save, every validation error after the number was
drawn leaves a gap. That is why you never treat a sequence as a count of records, and why
the callable-default approach draws a number the instant a form opens: a user who opens
"New" and closes it burns one.

If gap-free numbering ever becomes a hard requirement, the usual fix is to draw the number
in an overridden `create` at save time instead of in the default, which you will be ready
for after chapter 15. Roll back so no test order survives.
</Step>

## Gotchas

- **A Python constraint that isn't in its own `depends` won't re-run.**
  `@api.constrains("year")` only fires when `year` changes. If your rule reads three
  fields, list all three, or a write to the unlisted one slips a bad combination past
  you.
- **Constrains skip raw SQL, SQL constraints skip nothing.** `@api.constrains` runs in
  the ORM only. A `psql` UPDATE or a `cr.execute` bypasses it entirely. If a rule must
  survive even hand-written SQL, it has to be a `models.Constraint`, not Python.
- **New Python behaviour reaches the server by reload, not by `-u`.** The upgrade
  command runs in a separate, short-lived process, so it never touches the code the
  long-running server holds in memory. What updates that is `dev_mode = all`'s
  `reload` (chapter 6): the server watches your addons folder and restarts itself when
  a `.py` file changes, logging `autoreload: python code updated`. It is filesystem
  events, though, so it can miss a change (bind mounts on Docker Desktop are the usual
  culprit). If a new `@api.constrains` stubbornly refuses to fire, stop debugging the
  constraint and run `docker compose restart odoo` first. Rule of thumb: new columns
  need the upgrade, new behaviour needs a reload, and a manual restart is the reliable
  version of a reload.
- **Sequences have gaps and that's fine.** They advance non-transactionally, so
  rollbacks, cancelled drafts, and errors all leak numbers. Never derive a count or an
  "expected next" from a sequence, and never promise gapless numbering without a
  locking strategy built for it.
- **A callable default draws its sequence number when the form opens, not on save.**
  Open "New", walk away, and you've burned a number. Acceptable for an internal
  reference; if it isn't, move the draw into `create` (chapter 15).
- **`noupdate="1"` protects sequence counters across upgrades.** Leave it off and the
  next upgrade resets the counter, renumbering live records. Config-style data that
  users or the system mutate at runtime almost always wants `noupdate`.

4. ⭐⭐⭐ Break-it, then fix-it: stop forms from burning numbers. Move the number
   draw out of the callable default and into an overridden
   `create` (`@api.model_create_multi`) so a number is only spent when an order is
   actually saved (an abandoned "New" form then costs nothing; a rollback after a
   successful save still leaks, sequences always do). Confirm from the shell that
   `default_get` no longer draws a number and a real create still numbers correctly.
   Chapter 15 walks through exactly this refactor if you get stuck. The
   [sequence docs](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html#odoo.fields.Field)
   and the core `sale.order` source are your references; this is the standard
   production pattern.
