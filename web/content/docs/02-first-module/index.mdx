## The two tables worth memorising

Part 2 handed you eleven separate mechanisms across eight chapters, each with its own
"except when" clause. Side by side, the pattern behind all of them is one question:
**which code paths does this thing actually sit on?** Everything below was measured in
this tutorial's own environment, not taken from the docs.

### Guards: who refuses bad data

| Mechanism | Enforced by | Form | Code, RPC, import | Raw SQL | Bypassed by |
|---|---|---|---|---|---|
| ACL (`ir.model.access`) · ch10 | the ORM | yes | yes | no | `sudo()` |
| Record rule (`ir.rule`) · ch12 | the ORM | yes | yes | no | `sudo()` |
| Field `groups=` · ch20 | the ORM | yes | yes | no | `sudo()` |
| `@api.constrains` · ch14 | your Python, in the ORM | yes | yes | no | raw SQL, and silence if the field that changed is not named in the decorator |
| `models.Constraint` · ch14 | Postgres itself | yes | yes | **yes** | nothing |

Read the last column downward and the design rule falls out: everything the ORM enforces
is a boundary **against users, not against code**, because any code path holding a
`sudo()` recordset walks straight through it. Only the Postgres row is absolute. That is
why "if a guarantee must hold no matter what, it belongs in SQL" (ch14) is a statement
about *paths*, not about taste.

One mechanism is deliberately missing from that table. A menu item's `groups=` (ch11)
**hides** a menu; it protects nothing. The data is exactly as safe as its ACL, and a
hidden menu with a permissive ACL is a UI convenience the reader can defeat with a URL.

### Values: what fills a field, and when

| Mechanism | Runs when | Real column? | Searchable | Runs from code, RPC, import? |
|---|---|---|---|---|
| `default=` · ch14 | the record is created | it writes a real value | n/a | yes, on every create path |
| `onchange` · ch13 | a user edits a form | no | n/a | **no, never** |
| `related=` · ch13 | on read | no, unless `store=True` | yes, the ORM rewrites it into a JOIN | yes |
| computed, non-stored · ch13 | on read | no | no, unless you add `search=` | yes |
| computed, `store=True` · ch13 | when a declared dependency changes | yes | yes | yes |

The onchange row is the one that catches people: it is a typing assistant, so a CSV
import or an RPC call produces records it never touched. If a value must always be
right, it belongs in a compute or a default, never in an onchange.

And the two "searchable" answers that look inconsistent are not: Postgres has to be able
to *get there*. A stored field is a column, a related field is a path it can JOIN along,
and a non-stored computed field is neither, which is the wall ch19 hits with `margin`.

## Boss challenge: prove it

The review quiz checks what you remember. The [boss challenge](/docs/02-first-module/boss2-garage-inventory)
checks what you can *build*: a complete mini-module from a one-page spec, no steps, no
looking back, verified by `odoolings check boss2`. Clear it and you have genuinely
finished Tier 1's core.

## Where you stand

With Part 2 done you can create a module, model data, secure it, show it, relate it,
compute on it, and guard it. Part 3 makes it *pleasant*: view inheritance, list and
form polish, search filters, the kanban pipeline, and your first wizard.
