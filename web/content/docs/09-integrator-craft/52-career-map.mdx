## Concepts

### Reading core source effectively: the toolkit you already have

Every technique here is one this tutorial already used on you, named explicitly
now so you reach for it on purpose:

- **Measure, don't guess.** Chapter 7 counted 73 modules on `OCA/server-tools`'s
  `16.0` branch against 34 on `19.0`, real numbers from a real `git clone`, not an
  estimate. Chapters 18 and 19 did the same for a core view attribute, "141 hits
  vs 0" settled an argument a doc excerpt couldn't have.
- **Read the manifest and README before the code.** Chapter 43's habit: maturity,
  dependencies, and what a module claims to do, before you're deep in
  implementation detail that may not even matter to your question.
- **Verify behavior in a shell, not just in docs.** Chapter 50's whole method:
  `--log-sql` and `odoo shell` tell you what actually happens; a tutorial (this
  one included) can be stale the moment a version ships.
- **Cross-reference OCA's take on the same problem.** Chapters 43 and 44 read
  `OCA/fleet` as real, reviewed, production-grade prose about the same domain
  LibreFleet lives in. Core solves it one way; a community module solving the same
  shape of problem is a second, differently-constrained opinion worth having.

### Certification: what it actually measures, with real numbers

Confirmed directly from Odoo's own certification listing:

| Detail | Real value |
|---|---|
| Format | 120 questions, multiple choice |
| Time | 90 minutes |
| Pass mark | 70% |
| Scoring | +1 correct, −0.5 wrong, 0 unanswered |
| Scope | version-specific: 19, 18, 17 each offered separately |

That negative marking is worth knowing before you sit one: guessing blind costs you,
leaving a question blank doesn't.

Two more things about it. The certification is explicitly **nominative**, meaning it is
tied to one account and cannot be transferred. And it is a **functional** exam:
sales/inventory/accounting/CRM configuration knowledge, not a developer/technical track
under that same name.

If you're hiring or being hired for development work specifically, this tutorial's own bar
(a real merged OCA PR, chapter 45) is the more direct signal. The certification and a
contribution history measure different things, not competing versions of the same thing.

### The October rhythm, and how this tutorial itself commits to it

From this project's own planning record, a real, standing decision: **Odoo has no
LTS, one major version per year, the last three supported at any time**, and this
tutorial's own author re-verifies its entire baseline every October when a new
major ships. That's not a one-off task, it's routine, budgeted-for maintenance,
the same posture chapter 49 asked you to bring to migrating any module. Apply it
to yourself:

## Verify

No odoolings check, no LibreFleet state to assert. The real verification is
whatever you already built: a real PR (chapter 45), a real extracted module
(chapter 46), a real measured query count (chapter 50). If you can point at those,
you're past the point this tutorial was built to get you to.

## Gotchas

- **A certification is version-locked.** An Odoo 18 certificate doesn't quietly
  become 19 knowledge; the framework moved, chapter 49's whole subject.
- **The certificate and a contribution history measure different things.** Don't
  substitute one for the other when the question is "can this person actually
  write Odoo code."
- **"No LTS" surprises people coming from other ecosystems.** Budget the yearly
  re-learning cost as routine maintenance, not a crisis each October.
