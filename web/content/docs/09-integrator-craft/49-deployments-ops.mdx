**Checkpoint:** none, concept-level: nothing here touches LibreFleet.

## Why this matters

`code/docker-compose.yml` has run this entire tutorial: one Postgres container, one
Odoo container, hot reload on, hardcoded credentials, a single process. That's
exactly right for learning and exactly wrong for a business's actual traffic. This
chapter is concept-level on purpose, per the plan that shaped it: you won't stand up
nginx today, you'll know what it's for and why the pieces exist, which is the level
integrator work actually needs day to day; the ops team (or the client's, or
odoo.sh's) usually owns the rest.

Which invites the reasonable objection: if somebody else owns it, why spend an hour and a
half here? Because **their configuration produces symptoms that get filed as your bug.**
That is the honest reason, and it is worth keeping in mind as you read, because it turns
each concept below from ops trivia into a diagnosis you will need:

- A report that works locally and "randomly fails" in production is often a request being
  killed at a CPU limit, not code that broke.
- An automated action that "never runs" is sometimes a cron thread count, not your action.
- Attachments that "vanished" after a restore are usually a database restored without its
  filestore, which is not a data-loss bug in Odoo.

None of those tickets arrive labelled as infrastructure. They arrive pointing at your
module, and knowing these pieces is how you hand them back with an explanation instead of
spending two days in your own code.

## Concepts

### What our own setup quietly skips

`code/odoo.conf` says so directly: `admin_passwd = admin`, a comment reading
"dev-only credentials, hardcoded on purpose. Never reuse this file in
staging/prod." `docker-compose.yml` runs one Odoo process, no reverse proxy, a
single Postgres container with no backup job. Every gap below is something that
file is deliberately not doing.

### Workers: the prefork model

```console
$ docker compose exec odoo odoo server --help
```

Real flags this tutorial's `odoo.conf` never sets:

| Flag | Real default | What it controls |
|---|---|---|
| `--workers` | `0` (prefork disabled) | Worker processes handling HTTP requests |
| `--max-cron-threads` | `2` | Concurrent cron jobs |
| `--limit-time-cpu` | `60` | Max CPU seconds per request before the worker is killed |
| `--limit-time-real` | `120` | Max wall-clock seconds per request |
| `--limit-memory-soft` | `2048MiB` | Per-worker memory ceiling, worker recycled after the current request |

`--workers=0`, our default, means one process handling one request at a time,
which is exactly right for a lone developer clicking around and exactly wrong for
concurrent users. Production sets a real worker count (a common starting rule of
thumb is `2 × cpu_count + 1`, a convention, not a law) so multiple requests run in
parallel processes instead of queueing behind each other.

### The gevent worker (what "longpolling" used to mean)

A normal HTTP worker handles a request and returns. The live chatter notifications,
Discuss, the bus, all of it depends on connections held open far longer than any
normal request, exactly what would starve a small worker pool if handled the same
way. Odoo runs those on a separate process instead: `--gevent-port` names the port
it listens on. Older docs and tutorials call this "longpolling"; Odoo's own
`--help` output now just calls it the gevent worker, same job, current name.

### Reverse proxy and `--proxy-mode`

```console
$ docker compose exec odoo odoo server --help | grep -A2 "proxy-mode"
--proxy-mode        Activate reverse proxy WSGI wrappers (headers
                     rewriting) Only enable this when running behind a
                     trusted web proxy!
```

nginx (or any reverse proxy) sits in front in production: terminates TLS, routes
normal traffic to the HTTP workers and bus traffic to the gevent port, and adds
`X-Forwarded-*` headers so Odoo knows the real client IP and scheme instead of the
proxy's own. `--proxy-mode` is what makes Odoo trust those headers, which is
exactly why the warning says "only... behind a *trusted*" one: enabling it without
an actual proxy in front lets anyone forge those headers.

### Filestore and backups: two things that must travel together

Attachments, PDF reports, product images, none of that lives in a Postgres row.
Confirmed live, one directory per database:

```console
$ docker compose exec odoo ls /var/lib/odoo/.local/share/Odoo/filestore/
functional  tutorial  ...
```

A bare `pg_dump` backs up every table and forgets every one of those files. Odoo's
own `db dump` command exists specifically so you don't have to remember that
separately:

```console
$ docker compose exec odoo odoo db dump tutorial backup.zip
```

Real contents of the zip it produces, confirmed by actually opening it:

```text
dump.sql  filestore/  manifest.json
```

The database and the filestore, one file, one command. `db load` reverses it, and
does, verified end to end:

```console
$ docker compose exec odoo odoo db load tutorial_restored backup.zip
...
INFO ? odoo.service.db: RESTORE DB: tutorial_restored
```

### Staging that can't accidentally act like production: `neutralize`

```console
$ docker compose exec odoo odoo neutralize -c /etc/odoo/odoo.conf -d <db>
INFO ? odoo.cli.neutralize: Starting <db> database neutralization
INFO ? odoo.modules.neutralize: Neutralization finished
```

Confirmed what it actually changes, on a real duplicate database:

```console
$ psql ... -c "select key, value from ir_config_parameter where key like '%neutraliz%';"
 database.is_neutralized | true
```

A production copy pulled down for staging or testing still has every real customer's
email address and every configured outgoing mail server. `neutralize` is the tool
for the actual risk that creates: a staging environment quietly emailing real
customers, or firing a real webhook, because nobody remembered to disable those by
hand.

### odoo.sh vs a Docker platform

Two real, different answers to "where does this run," worth knowing apart rather
than treating as interchangeable:

### Multi-company and localization awareness

Chapter 27 already found two real traps here, worth carrying forward rather than
re-deriving: `account.account.code` is computed and **company-dependent**, reading
it under the wrong active company silently returns `False` rather than erroring,
and a bare `search([])` in a script or shell session crosses company boundaries
that the equivalent UI action would never cross. Every ops script (a report, a bulk
fix, a migration helper) needs the same discipline chapter 27 taught firsthand:
`with_company()` or an explicit `company_id` domain, always, the moment more than
one company might exist in the database you're pointed at.

```console
$ docker compose exec odoo odoo db duplicate tutorial tutorial_staging
$ docker compose exec odoo odoo neutralize -c /etc/odoo/odoo.conf -d tutorial_staging
$ docker compose exec db psql -U odoo -d tutorial_staging \
    -c "select value from ir_config_parameter where key = 'database.is_neutralized';"
```

```console
$ docker compose exec odoo odoo db drop tutorial_staging
```

## Gotchas

- **`--workers=0` isn't a bug in the tutorial setup, it's the right call for one
  developer.** Don't "fix" it here; know when a real deployment needs it changed.
- **`pg_dump` alone forgets the filestore, silently.** The backup succeeds, looks
  complete, and is missing every attachment and generated PDF until someone
  restores it and finds out.
- **An un-neutralized staging copy has real customers' real email addresses.**
  The risk isn't hypothetical, it's the reason the command exists.
- **A bare `search([])` crosses company boundaries a UI action never would**
  (chapter 27's own finding). Any ops script touching a multi-company database
  needs to scope explicitly, every time.
- **"Longpolling" and "gevent worker" are the same thing, old and current name.**
  Don't be thrown by which term a given doc or tutorial uses.
