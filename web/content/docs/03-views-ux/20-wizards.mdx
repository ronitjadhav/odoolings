**Goal:** build a `TransientModel` wizard that gates the last stage transition
behind real validation, closing the loophole chapter 17 left open on purpose.
· **Time:** ~2.5 h · **Checkpoint:** `code/checkpoints/ch20`

## Why this matters

Chapter 17 gave service orders a clickable statusbar and said, plainly, that
clicking enforces nothing: any user who can write the record can click any stage,
no checks, no side effects, and that "chapter 20's buttons and wizard add the
guardrails." This is that chapter. A wizard exists for exactly one reason: some
transitions need a moment of confirmation, extra input, or a validation pass before
they commit, and a raw field write can't ask for any of that. Marking a service order
done is the perfect candidate: it's the point where the workshop is telling itself
"this job made money" or explicitly overriding that check, and that's a decision
worth a small form, not a click.

One thing about wizards catches nearly everyone, so here it is before you meet any
code. A wizard *looks* like a popup, so you expect to build it the way you'd build a
dialog anywhere else: a bit of markup, two buttons, done. That isn't what a wizard is.
**A wizard is a model.** It has a `_name`, it has fields, it gets a real table in
Postgres, and it needs access rights like anything else.

Picture it as a scratch pad. Your real models are the ledger the workshop keeps
forever; a wizard is a pad Odoo tears off, hands you to scribble on, and bins once
you're done with it. Real paper, real ink, just not kept.

That sounds like heavy machinery for a dialog, and it's the opposite: it's the reason
the pattern is worth learning at all. Because a wizard is an ordinary model, every
single thing you already know still works on it. Fields behave like fields. Defaults,
`related=`, `groups=` and the form-view XML from chapter 16 all work unchanged. There
is no second, popup-shaped API to learn, because the popup is just a form on a model,
and a form on a model is the only kind of form Odoo has.

## Concepts

### TransientModel: a model that cleans up after itself

**Transient** is just a long word for temporary, and Odoo means it literally: these
rows really are created in a real table, and really are deleted later.

A <Term k="wizard">wizard</Term> is a model like any other, `_name`, fields, methods, security, except it
inherits `models.TransientModel` instead of `models.Model`. The difference is
lifecycle: transient records aren't meant to live forever. Odoo runs a scheduled
<Term k="vacuum">vacuum</Term>, a cleanup job on a timer, that deletes old transient rows automatically (a
default cutoff measured in
hours, configurable per model via `_transient_max_hours`), so a wizard's table never
accumulates years of throwaway "I opened this popup once" records the way a real
business model's table would. Everything else about a `TransientModel`, fields,
`api.depends`, security, is identical to what you already know.

So the scratch pad from a moment ago is exact, right down to the bin: every popup a
user opens writes a row, and nobody ever has to clean up after them.

### A wizard's three-part shape

<Mermaid
  label="A wizard's three-part shape: a button opens a popup act_window, the user fills the wizard form, and its own button validates and writes back to the record that opened it"
  chart={`flowchart LR
    A["button on the order form\n(type=object)"] --> B["method returns an\nact_window, target=new"]
    B --> C["wizard form opens as\na popup, order_id defaulted\nfrom context"]
    C --> D["user fills the wizard,\nclicks its own button"]
    D --> E["wizard method validates,\nwrites to the real record"]`}
/>

You've built every piece of this before, separately. Chapter 17 taught you a button
that calls a Python method and returns an action dict; chapter 15 taught you
`default_<field>` in a context dict. A wizard just chains them: a button on the real
record's form opens a popup (`target="new"`) whose form is a different model
entirely, pre-filled from context, and that popup's own button runs the validation
and writes back to the record that opened it.

Step C in that diagram is the part nobody guesses right, so it's worth stating on its
own. **The popup has no idea which record opened it.** It is a form on a different
model, and a fresh scratch pad starts blank; there is no hidden pointer back to the
order, and Odoo will not supply one. If the wizard is going to act on that order, you
have to hand the order over, and the context dict is the envelope you hand it in. That
is the entire job of the `default_order_id` you'll write in a moment: it is not
convenience pre-filling, it's the only thing connecting the popup to the record it
came from.

### Where validation actually belongs

There's a fair objection to answer first: you already know how to stop a bad write.
Chapter 14 gave you `@api.constrains`. Why not put the margin rule there and skip the
popup entirely?

Because of what the two can *say*. **A constraint can only say no. A wizard can ask a
question first.** A constraint has no way to offer a manager an override, and nowhere
to put a completion note the order has no field for. It sees the finished write and
votes on it. That is exactly what you want for a rule about data, and not enough for a
decision somebody is making on purpose.

With that in hand, you've now met three places a stage change can be gated, and this is
the moment to line them up:

| Mechanism | Enforces? | Where you met it |
|---|---|---|
| Clickable statusbar | Nothing. Any write, no questions asked. | Chapter 17 |
| `@api.constrains` | Yes, but only after the write already happened, and it rolls the whole transaction back on failure | Chapter 14 |
| Wizard button | Yes, and it can ask for more information (a note, an override) before ever attempting the write | This chapter |

A constraint is the right tool when the rule is about *data*, no matter how it got
written (chapter 14's no-overlapping-bookings rule fires whether you changed the
date from the form, an import, or the shell). A wizard is the right tool when the
rule is about *process*, a specific action a user takes on purpose, that benefits
from a confirmation step and maybe some extra input first.

## Hands-on

<Steps>

<Step>
### Write the wizard model

A new top-level `wizards/` directory, alongside `models/`. Create
`wizards/__init__.py`:

```python
from . import service_order_approve
```

And `wizards/service_order_approve.py`:

```python
from odoo import fields, models
from odoo.exceptions import UserError


class ServiceOrderApproveWizard(models.TransientModel):
    _name = "librefleet.service.order.approve.wizard"
    _description = "Approve & Complete Service Order"

    order_id = fields.Many2one("librefleet.service.order", required=True, readonly=True)
    margin = fields.Float(related="order_id.margin", readonly=True)
    override_negative_margin = fields.Boolean(
        string="Complete anyway (negative margin)",
        groups="librefleet.group_librefleet_manager")
    note = fields.Text(string="Completion Note")

    def action_confirm(self):
        self.ensure_one()
        order = self.order_id
        if order.stage != "in_progress":
            raise UserError(
                "Only an order that is in progress can be marked done.")
        if order.margin < 0 and not self.override_negative_margin:
            raise UserError(
                "This order loses money (margin %.2f). A manager must tick "
                "the override to complete it anyway." % order.margin)
        if self.note:
            order.notes = "%s\n\nCompletion note: %s" % (order.notes or "", self.note)
        order.stage = "done"
        return {"type": "ir.actions.act_window_close"}
```

Two business rules, both things a raw statusbar click could never ask about: the
order must actually be `in_progress` (you can't "complete" a draft), and a
money-losing order needs a manager's explicit override. The last line returns
`{"type": "ir.actions.act_window_close"}`, the "nothing more to show" action: that
return value is what closes the popup and drops the user back on the order form once
the write went through. `related="order_id.margin"`
gives the wizard a read-only mirror of the order's margin for free, no separate
compute needed. `override_negative_margin` carries `groups=`, the same
group-restriction mechanism chapter 10 taught you for regular model fields, and it
works exactly the same way here: only Workshop Managers see the field in the form,
*and*, worth confirming for yourself below, only they're allowed to write to it at
all, at the ORM level, not just hidden in the UI.

Read back over that file and notice how little of it is new. A `_name`, some fields, a
method that raises `UserError`, a `related=` mirror, a `groups=` restriction: you have
written every one of those against a normal model already. The only unfamiliar token in
the whole file is `TransientModel` on line one.

</Step>

<Step>
### Give the wizard its own form

A model with no view is unreachable, and that is as true of a scratch pad as of
anything else. So the wizard needs a form view: the same `ir.ui.view` record shape you
have written since chapter 16, just pointed at the wizard model. Create
`wizards/service_order_approve_views.xml`:

```xml
<record id="view_librefleet_service_order_approve_wizard_form" model="ir.ui.view">
    <field name="name">librefleet.service.order.approve.wizard.form</field>
    <field name="model">librefleet.service.order.approve.wizard</field>
    <field name="arch" type="xml">
        <form string="Approve &amp; Complete">
            <field name="order_id" invisible="1"/>
            <group>
                <field name="margin"/>
                <field name="override_negative_margin" invisible="margin &gt;= 0"/>
                <field name="note"/>
            </group>
            <footer>
                <button string="Mark Done" name="action_confirm" type="object"
                        class="btn-primary"/>
                <button string="Cancel" special="cancel" class="btn-secondary"/>
            </footer>
        </form>
    </field>
</record>
```

`invisible="margin &gt;= 0"` (the escaped `>=`, XML doesn't allow a bare `>`) hides
the override checkbox entirely on the common path, a healthy job made money, nobody
needs to see a checkbox that never applies. `special="cancel"` is the standard way
to close a wizard popup without running any action. Two other bits of this form are
wizard shapes you haven't met: everything inside `<footer>` is lifted out by the
client and rendered as the popup's own button bar (which is why the buttons sit there
rather than in a `<header>`), and `order_id` is declared `invisible="1"` instead of
being left out, because the popup still has to carry the order it was opened from
even though there is nothing for the user to do with it.
</Step>

<Step>
### The button that opens it

On `librefleet.service.order`, add the method the button calls:

```python
    def action_open_approve_wizard(self):
        self.ensure_one()
        return {
            "type": "ir.actions.act_window",
            "name": "Approve & Complete",
            "res_model": "librefleet.service.order.approve.wizard",
            "view_mode": "form",
            "target": "new",
            "context": {"default_order_id": self.id},
        }
```

<Term k='target="new"'>`target="new"`</Term> is what makes this open as a popup instead of navigating away from
the order. `default_order_id` in the context does the same job chapter 15 and 17's
smart buttons already showed you: the wizard's `order_id` field gets pre-filled the
moment the form opens, no `default_get` override needed.

In `views/service_order_views.xml`, add the button to the header and, this is the
part that actually closes chapter 17's loophole, remove `done` from
`statusbar_visible`:

```xml
<header>
    <button string="Mark Done" name="action_open_approve_wizard"
            type="object" class="btn-primary"
            invisible="stage != 'in_progress'"/>
    <field name="stage" widget="statusbar"
           options="{'clickable': true}"
           statusbar_visible="draft,confirmed,in_progress"/>
</header>
```

The button only shows once an order is `in_progress`. And `done` is gone from the
visible-steps list: a user can still click their way through draft, confirmed and
in_progress (chapter 17's original tradeoff stands for those, nothing about them
needs a wizard), but there is no clickable step left that jumps straight to done.
The statusbar widget always displays whatever the field's *current* value is, even
one absent from `statusbar_visible`, so once an order reaches done it still shows
correctly; the field just stops offering it as somewhere to click *into*.
</Step>

<Step>
### Two warnings you'll actually see

Watch the upgrade output closely (or check it in the shell afterward) and you'll spot
something new, and it's actually two distinct warnings, not one:

```console
UserWarning: librefleet.service.order: inconsistent 'compute_sudo' for computed
fields parts_total, labor_total, margin. Either set 'compute_sudo' to the same
value on all those fields, or use distinct compute methods for sudoed and
non-sudoed fields.
UserWarning: librefleet.service.order: inconsistent 'store' for computed fields,
accessing parts_total, labor_total may recompute and update margin. Use distinct
compute methods for stored and non-stored fields.
```

This is chapter 19's `store=True` on `margin` catching up with you. All three fields,
`parts_total`, `labor_total`, `margin`, still shared one `_compute_totals` method,
but only `margin` got a real column. Odoo 19 now warns explicitly, twice, that mixing
stored and non-stored (and, separately, sudoed and non-sudoed) fields in a single
compute method is a bad pattern, because each pairing has genuinely different
behavior under the hood.

`compute_sudo` decides *whose* access rights the compute method runs under: `True`
recomputes as superuser, bypassing record rules and field-level `groups=`; `False`
recomputes as whichever user triggered it, so the compute can fail or see less data
than a superuser would. You never set it on any of these three fields, so each
one fell back to the default Odoo uses when you leave it out, which is that field's
own `store` value. That default is not documented anywhere prominent, but it is one
line of core you can go and read: `attrs['compute_sudo'] = attrs.get('compute_sudo',
store)`, in `odoo/orm/fields.py`. `margin` is `store=True`, so it
silently got `compute_sudo=True`; `parts_total` and `labor_total` are not stored, so
they silently got `compute_sudo=False`. One method, three fields, two different
privilege levels, which is exactly the inconsistency both warnings are naming.

Note that nothing is broken. Both are warnings, the module runs, the numbers are right.
What Odoo is objecting to is that one method is quietly operating at two privilege
levels, which is fine until the day it isn't.

</Step>

<Step>
### Split the compute method, and watch both warnings go

One fix resolves both warnings at once: splitting the compute method by storage also
gives each half a consistent `compute_sudo`, since that attribute defaults per field
and both fields in each half share the same default. In `models/service_order.py`,
repoint the three fields at two new compute methods and delete chapter 13's
`_compute_totals` (nothing references it once the fields name the new methods):

```python
    parts_total = fields.Float(compute="_compute_parts_labor")
    labor_total = fields.Float(compute="_compute_parts_labor")
    margin = fields.Float(compute="_compute_margin", store=True,
                          help="What the order earns: parts revenue plus the flat "
                               "fee, minus what the parts cost the workshop.")
```

```python
    @api.depends("line_ids.subtotal", "service_type_id.flat_fee")
    def _compute_parts_labor(self):
        for order in self:
            order.parts_total = sum(order.line_ids.mapped("subtotal"))
            order.labor_total = order.service_type_id.flat_fee

    @api.depends("parts_total", "labor_total",
                 "line_ids.qty", "line_ids.part_id.standard_cost")
    def _compute_margin(self):
        for order in self:
            parts_cost = sum(
                line.qty * line.part_id.standard_cost for line in order.line_ids)
            order.margin = order.parts_total + order.labor_total - parts_cost
```

Two methods now: one computes the two non-stored fields, one computes the stored
one. Notice `_compute_margin`'s `@api.depends` includes `"parts_total"` and
`"labor_total"` directly, a computed field can depend on another computed field,
same as any stored field, so the dependency chain still cascades correctly when a
line's quantity changes. Bump to `19.0.1.15.0`, upgrade, and confirm both warnings
are gone:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial -u librefleet --stop-after-init
```

No warnings this time, and a quick psql check confirms the actual numbers didn't

### Break-it lab: is `groups=` on a field a real security boundary, or just UI polish?

You might reasonably assume `groups=` on a field only hides it from the form, the
way many admin tools work, and that anyone with API access could still set it. Test
that assumption directly, as tina, a Workshop User, not a manager:

```console
>>> tina = env["res.users"].search([("login", "=", "tina")])
>>> order.stage = "in_progress"
>>> as_tina = order.with_user(tina)
>>> act = as_tina.action_open_approve_wizard()
>>> env[act["res_model"]].with_user(tina).with_context(**act["context"]).create(
...     {"override_negative_margin": True})
odoo.exceptions.AccessError: You do not have enough rights to access the field "override_negative_margin" on Approve & Complete Service Order (librefleet.service.order.approve.wizard). Please contact your system administrator.

Operation: write
User: 5
Groups: allowed for groups 'Workshop / Manager'
```

The answer is no, `groups=` on a field is enforced at the ORM level, an `AccessError`,
not merely stripped from the rendered view. Tina cannot set that field through the
UI *or* through a raw RPC call bypassing it entirely. This is a genuinely reassuring
result: a field-level `groups=` restriction is a real access-control boundary, the
same category of guarantee as the ACLs from chapter 10, not cosmetic hiding you could
defeat with a well-aimed API call.

Now notice what "the same category as an ACL" cuts both ways on. Open a wizard as Tina
and try the same write twice, once plainly and once through `sudo()`:

```console
>>> act = as_tina.action_open_approve_wizard()
>>> W = env[act["res_model"]].with_user(tina).with_context(**act["context"])
>>> w = W.create({})
>>> w.write({"override_negative_margin": True})
odoo.exceptions.AccessError: ...
>>> w.sudo().write({"override_negative_margin": True})
True
```

(Note we write to `w`, the wizard, not to `as_tina`: `override_negative_margin` only
exists on the wizard model, so aiming it at the order raises
`ValueError: Invalid field 'override_negative_margin' in 'librefleet.service.order'`.)

The plain write is refused and the sudo'd one succeeds. `sudo()` spreads (chapter 15),
and a sudo'd recordset walks through field `groups=` exactly as it walks through an ACL,
because it *is* the same machinery. So hold both halves of the result at once:

- Against a **user**, including one hand-crafting RPC calls, `groups=` is a real
  boundary. That is what the lab just proved.
- Against **code**, it is not a boundary at all. Any method that reaches for `sudo()`,
  yours or a third party's, can write the field without noticing it was restricted.

That is not a flaw, it is the definition of `sudo()`, and it is why the audit question on
a real project is never "is this field restricted?" but "which code paths sudo their way
to it?". Chapter 38 writes the test that pins that down.
</Step>

## Gotchas

- **A wizard is a normal model with a different lifecycle, not a different
  language.** Fields, `api.depends`, security, all identical to what you already
  know. The only new thing is `TransientModel` and the automatic vacuum that comes
  with it.
- **`groups=` on a field stops users, not code.** You proved both halves: a non-manager
  gets an `AccessError` over RPC, and the same write succeeds through `sudo()`. It is the
  same machinery as an ACL, so it inherits the same escape hatch. Restricting a field
  protects it from people; only reviewing who calls `sudo()` protects it from your own
  codebase.
- **Mixing stored and non-stored fields in one compute method is now flagged.**
  Odoo 19 warns (doesn't yet error) when a single `_compute_*` method assigns to
  fields with different storage. Split them, one compute method per storage
  category, and let stored fields depend on non-stored ones via a plain
  `@api.depends` entry.
- **`target="new"` is what makes an action a popup.** Forget it and the wizard's
  action dict still works, technically, but navigates the user away from the order
  instead of floating a small form over it.
- **Removing a stage from `statusbar_visible` doesn't hide records already in it.**
  The widget always renders the field's actual current value; the attribute only
  controls which *other* stages appear as clickable stepping stones. It stops new
  jumps, it doesn't hide history.
