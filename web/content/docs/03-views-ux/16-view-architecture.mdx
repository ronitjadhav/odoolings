**Goal:** understand exactly how Odoo assembles the UI it shows you, and modify a view
without touching its source. · **Time:** ~2 h · **Checkpoint:** `code/checkpoints/ch16`

## Why this matters

Chapter 3 planted the idea that the UI is data; Part 2 had you writing views as XML
records without dwelling on what happens to them. Now it becomes the whole subject,
because **view inheritance is the single most-used skill in professional Odoo work**.
Client wants a field on the sales order form? Extension view. Hide a button for one
group? Extension view. Nearly every integrator ticket that says "can we see X on the Y
screen" resolves to twenty lines of the XML you'll write in this chapter. Part 4
extends core apps with exactly this mechanism; here you learn it safely inside
LibreFleet, including how it breaks.

## Concepts

### A view is a row in ir.ui.view

Every list, form, kanban and search screen is described by a record of `ir.ui.view`,
holding among other things: the `model` it renders, its `type` (list, form...), its
<Term k="arch (view architecture)">`arch`</Term> (the XML you've been writing), a `priority`, a `mode`, and optionally an
`inherit_id`. Your module's XML files don't "declare" views in some special sense;
they just load records into this table, like any other data file.

Look at LibreFleet's own rows (this is your database, after chapter 15):

```console
$ docker compose exec db psql -U odoo -d tutorial -c "select id, name, type, priority, mode, inherit_id from ir_ui_view where model = 'librefleet.vehicle' order by id;"
 id  |          name           | type | priority |  mode   | inherit_id
-----+-------------------------+------+----------+---------+------------
 253 | librefleet.vehicle.list | list |       16 | primary |
 254 | librefleet.vehicle.form | form |       16 | primary |
(2 rows)
```

Two views, both `primary`, both at the default priority of 16. `mode` has exactly two
values: `primary` means "a view in its own right", and `extension` means "a bundle of
patches applied on top of another view". You never type it yourself, Odoo derives it
when the record is created: a view with an `inherit_id` becomes an `extension`, one
without stays `primary`. `priority` is a plain integer that defaults to 16. Those two
columns are this chapter's levers.

### How Odoo picks and builds the view you see

When the web client asks for, say, the form view of `librefleet.vehicle`, the server:

<Mermaid
  label="How Odoo assembles a form view: pick the lowest-priority primary view, collect its extensions, and apply their patches in priority order"
  chart={`flowchart TD
    A["client requests form view<br/>(no explicit view_id)"] --> B["pick the PRIMARY view of that<br/>model and type with the<br/>LOWEST priority"]
    B --> C["collect its extension views<br/>(mode=extension, inherit_id set)"]
    C --> D["apply each extension's patches<br/>to the arch, in priority order"]
    D --> E["combined arch sent to the client"]`}
/>

Two consequences worth engraving:

- **<Term k="extension view">Extensions</Term> never replace, they patch.** An extension view is a list of edits
  (add this after that, change this attribute) applied to its parent's arch at
  request time. The parent's record is untouched; uninstall the extension and the
  original is back, unchanged.
- **<Term k="view priority">Priority</Term> is a golf score.** Among <Term k="primary view">primary views</Term>, the *lowest* number wins the
  default slot. Base views sit at 16, so a view with priority 8 hijacks the default,
  and one at 99 never wins the contest. It can still be reached: a window action
  (chapter 11) has a `view_id` field pointing at one specific `ir.ui.view` record, and
  when that field is set, the action opens that view instead of the priority winner.

### The patch language

An extension view's `arch` contains locator elements, each wrapping the nodes to
insert (or the attributes to change):

```xml
<xpath expr="//field[@name='service_count']" position="after">
    <field name="active"/>
</xpath>
```

XPath is a small query language for pointing at a node inside an XML document, and this
`expr` reads left to right: `//` means "anywhere below the root, at any depth", `field`
is the tag to look for, and `[@name='service_count']` keeps only the tags whose `name`
attribute is `service_count`. Put together: the `service_count` field, wherever it sits
in the parent's form. Odoo evaluates the expression against the parent's arch and takes
the first node it finds; `position` says what to do there:

| position | Effect |
|---|---|
| `after` / `before` | insert your nodes as siblings of the match |
| `inside` | append your nodes as children of the match (the default) |
| `replace` | remove the match, put your nodes in its place |
| `attributes` | keep the node, change only attributes via `<attribute>` children |

For the common case of locating a field by name, there's a shorthand that reads
better than XPath and does the same thing:

```xml
<field name="mileage_km" position="attributes">
    <attribute name="string">Odometer (km)</attribute>
</field>
```

Any locator that matches nothing is a hard error at load time, and that's a feature:
you find out at upgrade, not silently in production. You'll trigger it on purpose
below.

<Callout type="warn" title="Gotcha">
  Use `position="replace"` as the last resort. Every extension that replaces a node
  deletes it for all other extensions too, including ones installed later by modules
  you've never heard of. Integrators have a name for the resulting support tickets:
  "module A broke module B". Prefer `attributes` (with `invisible="1"`) to hide
  things, and keep replace for nodes your own module created.
</Callout>

### Primary inheritance, the other mode

`mode="primary"` with an `inherit_id` is the rarer cousin: it produces a *new
standalone view* that starts from a copy of the parent and applies patches, leaving
the parent's own default rendering alone. Core uses it when a specialized flavor of a
form is needed for one particular action. You'll recognize it when you meet it while
reading core; for day-to-day extension work, the default `extension` mode is what you
want.

## Hands-on

The reception desk has two requests: show the archive toggle on the vehicle form
(chapter 15 taught archiving, but there's no way to do it from the UI yet), and call
the mileage field what everyone calls it, the odometer. You'll do both without
touching `vehicle_views.xml`.

<Steps>

<Step>
### Write the extension view

Create `views/vehicle_views_inherit.xml`:

```xml
<?xml version="1.0" encoding="utf-8"?>
<odoo>

    <record id="view_librefleet_vehicle_form_reception" model="ir.ui.view">
        <field name="name">librefleet.vehicle.form.reception</field>
        <field name="model">librefleet.vehicle</field>
        <field name="inherit_id" ref="view_librefleet_vehicle_form"/>
        <field name="arch" type="xml">
            <xpath expr="//field[@name='service_count']" position="after">
                <field name="active"/>
            </xpath>
            <field name="mileage_km" position="attributes">
                <attribute name="string">Odometer (km)</attribute>
            </field>
        </field>
    </record>

</odoo>
```

`inherit_id` points at the base form through its XML id (same-module `ref`, no
`librefleet.` prefix needed), which makes this an extension view automatically. The
arch holds two patches: one XPath locator inserting `active` after the service
counter, one shorthand locator relabeling `mileage_km` for this form only (the field
itself, and every other view, keeps its model-level label).

Two edits in `__manifest__.py`. First, add the new file to `data`, right after
`vehicle_views.xml`, so the base form record already exists when Odoo resolves this
file's `ref`:

```python
        "views/vehicle_views.xml",
        "views/vehicle_views_inherit.xml",
```

Second, bump the version, as with every change to the module:

```python
    "version": "19.0.1.9.0",
```

Then upgrade:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial -u librefleet --stop-after-init
```
</Step>

<Step>
### Add the competing list view

Reception also wants a stripped-down vehicle list. In the same file, before
`</odoo>`, add a *second standalone list view* for the model:

```xml
    <record id="view_librefleet_vehicle_list_reception" model="ir.ui.view">
        <field name="name">librefleet.vehicle.list.reception</field>
        <field name="model">librefleet.vehicle</field>
        <field name="priority" eval="99"/>
        <field name="arch" type="xml">
            <list>
                <field name="license_plate"/>
                <field name="owner_id"/>
                <field name="service_count"/>
            </list>
        </field>
    </record>
```

No `inherit_id`, so it's a full view in its own right, competing for the default slot
through priority. `eval="99"` is how that number gets set: `eval` runs the attribute as
Python, so the field receives the integer 99 rather than text. At 99 the view
deliberately loses to the original's 16, and that is the point. Nobody's Vehicles menu
changes today, you gain a second primary view to run step 4's experiment against, and
it matches how real modules ship an alternative screen: parked at a high priority,
opened only by an action that names it with `view_id`. It lives in the same
already-registered file, so no new manifest entry and no version bump, just:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial -u librefleet --stop-after-init
```

Then check the table:

```console
$ docker compose exec db psql -U odoo -d tutorial -c "select id, name, type, priority, mode, inherit_id from ir_ui_view where model = 'librefleet.vehicle' order by id;"
 id  |               name                | type | priority |   mode    | inherit_id
-----+-----------------------------------+------+----------+-----------+------------
 253 | librefleet.vehicle.list           | list |       16 | primary   |
 254 | librefleet.vehicle.form           | form |       16 | primary   |
 261 | librefleet.vehicle.form.reception | form |       16 | extension |        254
 262 | librefleet.vehicle.list.reception | list |       99 | primary   |
(4 rows)
```

Everything this chapter claimed, visible in one query: the extension with its
`inherit_id`, the standalone at priority 99.
</Step>

<Step>
### Watch the combination happen

<Term k="get_view">`get_view`</Term> is the method the web client itself calls, and it hands back a dict
whose `arch` key holds the finished XML. Open a shell against the tutorial database:

```console
$ docker compose exec odoo odoo shell -c /etc/odoo/odoo.conf -d tutorial --no-http
```

Then ask it for the combined form arch:

```console
>>> arch = env["librefleet.vehicle"].get_view(view_type="form")["arch"]
>>> 'name="active"' in arch
True
>>> import re
>>> re.search(r'<field name="mileage_km"[^>]*>', arch).group(0)
'<field name="mileage_km" string="Odometer (km)"/>'
```

The base record's arch in the database still has neither change (check it in the psql
`arch_db` column if you're curious); the merge happened at request time. That's why
this mechanism is safe: nothing was edited, something was *composed*.
</Step>

<Step>
### Rig the priority contest, then unrig it

Still in the shell, make the reception list win and watch the default flip live. The
tell is `service_count`: the base list shows `license_plate`, `owner_id`, `model_name`,
`year` and `mileage_km`, and only reception's list shows `service_count`, so whether
that name turns up in the combined arch tells you which of the two views won:

```console
>>> Vehicle = env["librefleet.vehicle"]
>>> "service_count" in Vehicle.get_view(view_type="list")["arch"]
False
>>> reception = env.ref("librefleet.view_librefleet_vehicle_list_reception")
>>> reception.priority = 8
>>> "service_count" in Vehicle.get_view(view_type="list")["arch"]
True
>>> reception.priority = 99
>>> "service_count" in Vehicle.get_view(view_type="list")["arch"]
False
>>> env.cr.rollback()
```

Priority 8 beats 16, so every plain vehicles action in the whole database would now
open reception's list; back at 99, order is restored. No file changed, no upgrade ran:
priority is data, and the winner is recomputed on every request. (The rollback keeps
your database matching the checkpoint; the file's `eval="99"` is the state that
ships.)
</Step>

<Step>
<BreakIt />
### Break-it lab: the locator that matches nothing

Sabotage the xpath in your extension view, replacing `service_count` with a field
that doesn't exist:

```xml
<xpath expr="//field[@name='does_not_exist']" position="after">
```

Upgrade and read the failure carefully:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial -u librefleet --stop-after-init
...
odoo.tools.convert.ParseError: while parsing /mnt/extra-addons/librefleet/views/vehicle_views.xml:18
Error while parsing or validating view:

Element '<xpath expr="//field[@name=&#39;does_not_exist&#39;]">' cannot be located in parent view

View error context:
{'file': '/mnt/extra-addons/librefleet/views/vehicle_views.xml',
 'line': 1,
 'name': 'librefleet.vehicle.form.reception',
 'view': ir.ui.view(259,),
 'view.model': 'librefleet.vehicle',
 'view.parent': ir.ui.view(184,),
 'xmlid': 'view_librefleet_vehicle_form'}
```

Your ids will not match this transcript, because Postgres hands them out per database
as records are created, so read the names rather than the numbers. And read this one
carefully, because its `file` and `line` lie to you a little. They point
at `vehicle_views.xml`, the *base* form's file, not `vehicle_views_inherit.xml` where
your broken xpath actually lives. That's because the base form isn't `noupdate`, so
every upgrade rewrites its record, and that write is what triggers Odoo to recombine
it with every extension and validate the result, while `vehicle_views.xml` is still
the file the loader is nominally "in". The `name`, `view` and `view.parent` keys don't
lie, though: `name` is your extension's own name, `view` is its record id, and
`view.parent` is the base form it failed to patch. When file and line point somewhere
that looks innocent, trust those three instead; they name the real culprit every time.
You will meet this shape again whenever a version migration renames a field your xpath
anchored on (chapter 47's bread and butter). Restore `service_count`, upgrade, and
confirm the module loads clean.
</Step>

</Steps>

## Gotchas

- **Your xpath is a contract with the parent's structure.** Anchor on stable,
  semantic nodes (a named field) rather than positional paths (`/form/sheet/group[2]`),
  because the parent WILL be reorganized someday and positional paths break silently
  or, worse, match the wrong node.
- **Only the first match is patched.** An `expr` matching several nodes applies to
  the first one. If a field appears twice in a form (it happens: once visible, once
  invisible), be more specific or you'll edit the wrong occurrence.
- **`replace` is a shared-space hazard.** You delete that node for every other
  extension too. Hide with attributes instead; replace only what your module owns.
- **Upgrade, not restart, for view changes.** Views are data, so `-u librefleet`
  reloads them and the running server serves the new combination immediately, the
  exact mirror image of Python changes (restart, no upgrade) from chapter 14.
- **A view can be edited in the database and diverge from your file.** Settings →
  Technical → Views lets anyone edit arch live. The next upgrade overwrites it with
  your file (views are not `noupdate`), which surprises whoever "fixed" it in the UI.
  In the field: never hot-edit views in a client database; it always ends in a diff
  nobody can explain.
