**Goal:** build a search view for service orders with filters, group-by, and a
working default filter, and understand exactly why a typo in that default fails
silently. · **Time:** ~2 h · **Checkpoint:** `code/checkpoints/ch18`

## Why this matters

Every list you've built so far opens showing everything, sorted however the model's
`_order` says. Real users don't want everything: a technician wants their own jobs, a
manager wants to see progress by vehicle, and nobody wants to see cancelled orders on
the happy path. That's the search view's job, and it's a fourth view type alongside
list, form and (soon) kanban. It also comes with a footgun this chapter walks you
straight into: the mechanism that makes a filter apply automatically depends on
spelling one string correctly, and Odoo will never tell you if you didn't.

If "the search bar is a view" sounds odd, that is worth saying out loud, because it is
what makes this chapter feel stranger than it is. The search bar reads as furniture: a
strip that comes with the list, the same shape on every Odoo screen you have ever opened.
Being told it is a *fourth view type*, its own record with its own XML that you write
yourself, lands as a surprise.

Here is what actually happened. **You have had a search bar on every list since chapter
12, and you never wrote one.** Odoo made it for you: when a model has no search view,
core generates a minimal one containing a single field, your model's `_rec_name`. You can
read the whole of it in `_get_default_search_view` in
`base/models/ir_ui_view.py`, and it is four lines long. So you have not been living
without a search view, you have been living with the smallest possible one, which is
exactly why the bar has only ever matched on name. This chapter is you taking that
generated stub and writing a real one in its place.

So here is the shape to carry in. **What you are shipping is a small control panel**, and
it has exactly three kinds of control: the places the search bar is allowed to look, the
switches a user can flip, and the ways they can pile records into stacks. That is the
entire search view. Everything else in this chapter is one naming rule that connects your
control panel to the screen that opens it.

## Concepts

### The search view is data too

By now this shouldn't surprise you: a search view is just another `ir.ui.view` record,
`type="search"`, loaded from XML like every view before it. Its arch holds three kinds
of element, and they are the three controls from a moment ago, in order: where to look,
what to switch on, how to stack.

- **`<field>`**: a field the user can search on. Type text into the search bar and the
  dropdown offers one "search Vehicle for..." line per `<field>` listed here, so this is
  the list of things the search bar knows how to look in. For a many2one like
  `vehicle_id` the lookup runs `name_search`, the ORM method that matches records whose
  display name contains what you typed. It is the same method that fills the suggestion
  list when you type into a many2one on a form.
- A <Term k="filter (search view)">`<filter>`</Term>: a named, static domain the user can toggle on with a click. Each
  one needs a `domain` (or a `context` for group-by, see below) and a `name` that
  matters more than it looks like it should.
- **`<group>`** wrapping filters with `context="{'group_by': '...'}"`: the <Term k="group-by">Group By</Term>
  menu. Grouping never ships every record to the browser to be counted there. The web
  client calls `web_read_group`, the web module's entry point for loading grouped data
  in list and kanban views, and underneath it sits `_read_group`, the ORM call that
  turns your grouping into a single SQL `GROUP BY`: one bucket per distinct value, plus
  its count. A pivot's cells and a kanban's column counts come from the same machinery.
  The older public name, `read_group`, still works and is the one you'll call from the
  shell later in this chapter, though Odoo 19 marks it deprecated in favour of
  `_read_group`.

<Callout type="warn" title="Gotcha">
  Don't confuse a search view's `<filter>` element with the `ir.filters` model.
  `<filter>` is a static toggle baked into the view's XML by whoever wrote the module.
  `ir.filters` is the *favorites* system: a record a user saves themselves, from the
  search bar's "Save current search" button, stored per-user in the database. Same
  word, two different mechanisms.
</Callout>

### Ticking two filters: the rule that surprises everyone

Chapter 15 drilled that the conditions in a domain are **ANDed** by default. Search
views break that expectation on purpose, and this is the single most common Odoo search
surprise, so get it now rather than from a confused user. One word of vocabulary first:
every condition currently narrowing a list shows up in the search bar as a **facet**,
the rounded chip sitting there that you can remove with a click. Facets are what the
table below is really counting:

| What the user ticks | How it combines | Why |
|---|---|---|
| Two `<filter>`s with nothing between them | **OR** | Adjacent filters are alternatives: "show me draft *or* confirmed" |
| Two `<filter>`s with a `<separator/>` between them | **AND** | A separator starts a new group, and groups are ANDed |
| A value typed into the search bar | **AND** with everything else | It is a different facet |

So `Draft` plus `Confirmed` ticked together shows you both, not nothing. If they ANDed,
`stage = 'draft' AND stage = 'confirmed'` could never match a record, which is exactly
what a reader who trusts chapter 15 predicts.

That is what `<separator/>` is for: it starts a new group, so it is how you say "this
filter must narrow the others, not join them".

One warning about the word "group", because this chapter uses it for two unrelated
things, and both show up in the arch you are about to write:

- A **group of filters** is just a run of adjacent `<filter>` elements between two
  separators. Nothing in the XML marks it, you count separators to see where one ends.
  This is the thing that decides AND versus OR.
- The **`<group>` element** is something else entirely: it is the container that turns the
  filters inside it into the Group By menu, and it has nothing to do with AND and OR.

Now look ahead at the arch you write in step 1, because it has exactly one separator and
that is **one too few**. "My Services" and "Exclude Cancelled" end up in the same group,
so ticking both shows you *your* orders plus *everyone's* non-cancelled ones, which is
not what either label promises. The stage filters below the separator are correctly
ANDed against them. Exercise 4 has you fix it, and it is worth leaving wrong for one
read: this is precisely the bug you will meet in real modules, where the label says
"exclude" and the behaviour says "include as well".

Each group's facets appear as one chip in the search bar, which is the visual tell:
one chip means OR inside it, two chips mean AND between them.

### uid: a variable that only exists in this one context

The "My Services" filter you're about to write uses `uid` inside a domain string:

```xml
<filter string="My Services" name="my_services"
        domain="[('technician_ids', 'in', [uid])]"/>
```

<Term k="uid">`uid`</Term> isn't a Python variable, an import, or anything you'd find defined anywhere in
the codebase. It's a magic name the web client substitutes with **the current logged-in
user's id** when it evaluates the domain, client-side, right before sending the
search request. It only works inside domain and context strings written in XML (or
passed as literal context dicts); you'll never see `uid` used this way inside a Python
method, because Python methods have `self.env.uid` for the same thing, spelled
differently.

### The default-filter convention, and where it can quietly fail

Here is the division of labour that explains this whole section, footgun included. **The
search view only ever *offers*. The action decides which of those offers is switched on
when the page opens.** Those are two separate records. They can sit in different files,
be written months apart by different people, and the only thing joining them is a string
that has to match on both sides.

Read the rest of this section as a consequence of that split rather than as a quirk.

An action's `context` can pre-check a filter when the view first loads, using a naming
convention: <Term k="`search_default_<name>`">`search_default_<name>`</Term> set to a truthy value, where `<name>` is a
filter's `name` attribute:

```xml
<field name="context">{'search_default_not_cancelled': 1}</field>
```

<Mermaid
  label="The search_default naming convention: a matching filter name applies on load, a typo fails silently with no error anywhere"
  chart={`flowchart LR
    A["action.context has\nsearch_default_not_cancelled: 1"] --> B{"a filter named\n'not_cancelled' exists\nin the search view?"}
    B -- yes --> C["client pre-checks it,\nfilter applies on load"]
    B -- no, typo --> D["nothing happens.\nno error, no warning,\nlist just opens unfiltered"]`}
/>

Here's the part worth sitting with: **this convention is enforced by nobody.** There's
no schema linking an action's context keys to a search view's filter names. If you
write `search_default_not_cancelld` (typo) and the filter is actually named
`not_cancelled`, the module installs cleanly, the server starts, the list opens, and
it just... doesn't filter. No traceback, no log line, nothing. You'll build this bug on
purpose in a minute so you recognize the shape of it forever.

## Hands-on

<Steps>

<Step>
### Build the search view

In `views/service_order_views.xml`, add a new `ir.ui.view` record before the action.
You will notice there is no `<field name="type">search</field>` in it: leave `type`
out of a standalone view and Odoo reads the arch's root tag to decide, so a `<search>`
root makes this a search view. (Extension views like chapter 16's skip that guess
entirely: they take their parent's type through `inherit_id`.)

```xml
<record id="view_librefleet_service_order_search" model="ir.ui.view">
    <field name="name">librefleet.service.order.search</field>
    <field name="model">librefleet.service.order</field>
    <field name="arch" type="xml">
        <search>
            <field name="reference"/>
            <field name="vehicle_id"/>
            <field name="customer_id"/>
            <field name="technician_ids"/>
            <filter string="My Services" name="my_services"
                    domain="[('technician_ids', 'in', [uid])]"/>
            <filter string="Exclude Cancelled" name="not_cancelled"
                    domain="[('stage', '!=', 'cancelled')]"/>
            <separator/>
            <filter string="Draft" name="stage_draft" domain="[('stage', '=', 'draft')]"/>
            <filter string="Confirmed" name="stage_confirmed" domain="[('stage', '=', 'confirmed')]"/>
            <filter string="In Progress" name="stage_in_progress" domain="[('stage', '=', 'in_progress')]"/>
            <filter string="Done" name="stage_done" domain="[('stage', '=', 'done')]"/>
            <!-- Group By -->
            <group>
                <filter string="Vehicle" name="group_vehicle" context="{'group_by': 'vehicle_id'}"/>
                <filter string="Stage" name="group_stage" context="{'group_by': 'stage'}"/>
                <filter string="Service Type" name="group_service_type" context="{'group_by': 'service_type_id'}"/>
            </group>
        </search>
    </field>
</record>
```

Notice the `<group>` around the group-by filters has no attributes at all in Odoo 19,
just a comment above it for readability. (On Odoo 18 you may see `expand="0"` used to
collapse the group-by section by default; on 19 that attribute is rejected by the view
schema and the group-by list is always collapsed.) Four searchable fields, six
toggleable filters, three group-by options: this is already a working search view. You
don't need to reference it anywhere yet, the client finds a model's search view
automatically the same way it finds the lowest-priority list and form.
</Step>

<Step>
### Wire the default, with the typo left in on purpose

Now the action, further down the same file. It has never had a `context` field, so add
one between `view_mode` and the `help` block, and misspell the filter name on the way
in:

```xml
<record id="action_librefleet_service_order" model="ir.actions.act_window">
    <field name="name">Service Orders</field>
    <field name="res_model">librefleet.service.order</field>
    <field name="view_mode">list,form</field>
    <field name="context">{'search_default_not_cancelld': 1}</field>
```

Leave the `help` block and the closing `</record>` below it untouched.

That's `not_cancelld`, missing the second `e`. Bump the manifest to `19.0.1.11.0` and
upgrade:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial -u librefleet --stop-after-init
```

Zero errors. Zero warnings. The upgrade succeeds exactly as cleanly as it would with
the correct spelling, because nothing in the loading process ever reads a filter's
`name` attribute against an action's context keys. They're unrelated strings that
happen to follow a convention only the browser's JavaScript understands.

That is the two-records split from Concepts, biting. Your action said "switch on the
filter called `not_cancelld`". Nothing ever asked the search view whether it has one.
</Step>

<Step>
### Catch what the server can't

```console
$ python3 odoolings.py check ch18
✔ the search view has the expected filters
✔ the My Services filter domain is correct
✘ the action's default filter matches a real filter name
    action context key 'search_default_not_cancelld' has no matching filter in the search view. Filters actually present: group_service_type, group_stage, group_vehicle, my_services, not_cancelled, stage_confirmed, stage_done, stage_draft, stage_in_progress. The search_default_<name> suffix must be exact, or the default silently does nothing
    hint: Every search_default_<name> key in the action's context must match a filter's name= exactly, or nothing happens, silently, forever.
```

That check works the only way this bug *can* be caught outside a human eyeballing the
list: read the action's `context` dict, read the filter names out of the search view's
own arch, and compare the two strings yourself. Nothing in Odoo does this comparison for
you, ever, which is exactly why the check exists. Note that it lists the filters it did
find, which is usually enough to spot the typo without opening the XML, and that it reads
the live arch rather than a fixed list, so filters you add yourself (exercises 1 and 3)
count as real ones.

**The sentence to carry out of this chapter:** the search view offers, the action decides,
and nothing checks that the two agree. Whenever a default filter "does nothing", compare
those two strings before you doubt anything else.
</Step>

### Prove group-by actually aggregates

The next three steps all run in `odoo shell` against your `tutorial` database. Open it
and keep it open:

```console
$ docker compose exec odoo odoo shell -c /etc/odoo/odoo.conf -d tutorial --no-http
```

Grouping is not the browser slicing up a list it already downloaded: the server does the
counting and hands back one row per bucket. Call that aggregation yourself with
`read_group` and you get exactly the buckets the Group By menu draws:

```console
>>> action_id = env.ref("librefleet.action_librefleet_service_order").id
>>> env["ir.actions.act_window"].browse(action_id).context
"{'search_default_not_cancelled': 1}"
>>> groups = env["librefleet.service.order"].read_group([], ["id"], ["vehicle_id"])
>>> [(g["vehicle_id"], g["vehicle_id_count"]) for g in groups]
[((1, 'ZH 468 202'), 1), ((2, 'BE 30 447'), 1)]
```

One order per vehicle, which matches the two vehicles and two orders you've had since
chapter 12. The action's context now reads back exactly as written: the fixed string.
</Step>

<Step>
### Prove My Services actually scopes

`with_user` from chapter 15 makes this the cheapest security-relevant test you'll ever
write:

```console
>>> tina = env["res.users"].search([("login", "=", "tina")])
>>> as_tina = env["librefleet.service.order"].with_user(tina)
>>> as_tina.search([("technician_ids", "in", [tina.id])]).mapped("reference")
['SO/2026/0001']
```

Tina's own filter, evaluated as Tina, returns exactly the one order she's assigned to
(from chapter 12). In the browser, the exact same domain runs when she clicks "My
Services", with `uid` standing in for `tina.id` because the client fills it in from
her session.
</Step>

<Step>
### Prove that two ticked filters OR

The Concepts claim is easy to state and easier to disbelieve, so measure it. Your orders
are all in `draft` right now, so flip one to `confirmed` first, and note that we never
commit, so the flip evaporates when the shell exits (chapter 6's lesson, put to work):

```console
>>> O = env["librefleet.service.order"]
>>> O.search([("stage", "=", "draft")], limit=1).stage = "confirmed"
>>> O.search_count([("stage", "=", "draft")]), O.search_count([("stage", "=", "confirmed")])
(1, 1)
>>> O.search_count([("stage", "=", "draft"), ("stage", "=", "confirmed")])
0
>>> O.search_count(["|", ("stage", "=", "draft"), ("stage", "=", "confirmed")])
2
```

One record each, an ANDed domain that can never match anything, and an ORed domain that
returns both. Ticking **Draft** and **Confirmed** in the browser gives you 2, so the
search view is building the second domain. Quit without `env.cr.commit()` and both
orders are back to draft.
</Step>

## Gotchas

- **A missing `<separator/>` inverts a filter's meaning.** Adjacent filters OR, so a
  filter meant to *narrow* the list (an "Exclude Cancelled") that sits next to your
  stage filters instead *widens* it. Nothing errors, the label still reads correctly,
  and the filter appears to do nothing. If a filter behaves backwards, count the
  separators before you touch the domain.
- **`search_default_<name>` has no validation anywhere.** A typo installs clean,
  upgrades clean, and produces a list that silently ignores your intended default.
  Nothing short of reading both strings side by side (or a check like today's) catches
  it.
- **`uid` only means something inside domain/context strings the client evaluates.**
  It is not a Python name; don't go looking for where it's imported, and don't expect
  it to work inside a compute method or constraint.
- **A `<filter>` is not an `ir.filters` favorite.** One is static XML shipped with your
  module; the other is a per-user saved search. Don't reach for `ir.filters` when what
  you actually want is a `<filter>` element, and vice versa.
- **`<group>` for group-by filters takes no attributes on Odoo 19.** `expand="0"` and
  a `string` on the wrapping `<group>` are rejected by the view schema; a plain
  `<group>` with a comment above it is the correct 19.0 shape.
- **A many2many domain with `'='` and `'in'` behave the same for a single id.**
  We tested this directly: `[('technician_ids', '=', tina.id)]` and
  `[('technician_ids', 'in', [tina.id])]` return identical results in current Odoo.
  Use `'in'` anyway, it's the form that reads correctly when the value becomes a list
  of several ids, which `'='` was never designed to express.
