**Checkpoint:** `code/checkpoints/ch37`

## Why this matters

Every chapter so far has been a conversation between a logged-in user and the web
client: Odoo's own JavaScript talking to the ORM over RPC. That is not the only door
into your data. Somewhere, a customer who never opens the backend needs to see their own
history without becoming a Workshop user. That is what controllers are for: raw HTTP
routes you write yourself, with their own auth rules, answering requests directly.

URLs and HTTP appearing now can feel like a second framework bolted onto the side of
Odoo. That feeling is the main thing making this chapter seem harder than it is, so name
it and drop it. **A controller is just a Python method with a URL for a name.** Write a
method, add a decorator saying "answer requests at this address", return something. It
runs in the same process, with the same `env`, and can do anything you have done since
chapter 9.

Here is the reveal that should settle it: **you have been using controllers since chapter
1 without knowing.** That RPC conversation the web client has been having is itself a
controller. Every form save and every list load goes through `/web/dataset/call_kw`, in
core's `web/controllers/dataset.py`. It is an ordinary method with an ordinary decorator:

```python
@http.route(['/web/dataset/call_kw', '/web/dataset/call_kw/<path:path>'], type='jsonrpc', auth="user", ...)
def call_kw(self, model, method, args, kwargs, path=None):
```

Same `@http.route`, same `type=`, same `auth=` you are about to write yourself. There is no
second framework here, and there never was.

What is actually new is narrower than it looks. Until now, something else decided who was
allowed in and which records they could see: you inherited a logged-in session and
chapter 10's access rules. Write your own route and both become yours to state, once in
the decorator and once in the code inside it.

The customer portal, `/my/...`, is the well-worn shape Odoo gives this problem. This
chapter builds a `/my/service-orders` page a customer can log into, see only their own
orders on, and share by link without sharing their password.

## Concepts

### A route is a function with an address and a permission

`@http.route(path, type=..., auth=...)` on a method is the whole mechanism. Three
things about the decorator matter more than the rest:

- **`type`** decides the shape of the request and response. `type="http"` is a normal
  page: a `GET` or `POST`, your method returns HTML (or a redirect, or a file).
  `type="jsonrpc"` is for programmatic callers: the body is a JSON-RPC envelope, your
  method's return value is JSON-encoded automatically, no template involved.
- **`auth`** (short for authentication: *who are you?*) decides who can even reach the
  method, checked *before* your code runs. `"public"` means anyone, logged in or not.
  `"user"` means Odoo redirects to the login page first if there is no session. `"none"`
  skips authentication entirely, no `request.env.user`, used for things like webhooks.
- **`website=True`** wraps the response in the website builder's chrome (header, footer,
  the page you'd customize with the site editor). This chapter only takes a taste of
  that: the public page below skips it on purpose, and the portal pages use it because
  `/my/...` genuinely is part of the website layer.

<Callout type="warn" title="On Odoo 18 this differs">
  `type="json"` is what you would write on 18 and earlier. Odoo 19 renamed it to
  `type="jsonrpc"` and kept `"json"` as a deprecated alias: it still works, but every
  call logs `DeprecationWarning: Since 19.0, @route(type='json') is a deprecated alias
  to @route(type='jsonrpc')`. Reproduced for real in this chapter's first hands-on step.
</Callout>

### The portal pattern: one mixin, one controller class, one convention

Odoo's customer portal is not a special framework. It is three ordinary pieces, used the
same way everywhere from `/my/orders` (chapter 22's sales) to `/my/invoices` (chapter
27's accounting):

<Mermaid label="A portal page checks access one of two ways: a logged-in session with the right record rule, or a share-link access token, both funnelled through the same _document_check_access helper." chart={`flowchart TD
    Request["GET /my/service-orders/42"] --> Check["_document_check_access()"]
    Check -->|"logged in, record rule matches"| Ok["record returned, sudo'd"]
    Check -->|"no session, but access_token matches"| Ok
    Check -->|"neither"| Deny["AccessError / MissingError"]
`} />

1. **`portal.mixin`** on your model adds `access_token` and `access_url`. The token is a
   random UUID generated on demand (`_portal_ensure_token()`), and it is what a share
   link's `?access_token=...` carries. `access_url` defaults to the literal string `'#'`,
   so every model using the mixin must override `_compute_access_url` and point it
   somewhere real.
2. **`CustomerPortal`** (from the `portal` module) is the controller class every portal
   extension inherits from. Override `_prepare_home_portal_values` to add a tile and a
   counter to `/my`. Same extension pattern chapter 32 used on `res.partner`'s form view,
   just aimed at a controller method instead of an XML view.
3. **`_document_check_access(model, id, access_token)`** makes both access paths,
   logged-in and shared-link, run through the same code. It tries a normal
   `check_access('read')` first, so a record rule has to actually grant it. Only if that
   fails does it compare the token. This is why a portal route binds `auth="public"`, not
   `"user"`: an anonymous visitor with a valid token has to reach the method at all
   before the token check can run.

### ACL and record rule are still the two-layer system from chapter 10

Name this trap before you fall into it: **making a page public is not the same as making
a record readable.** They are separate questions, decided in separate places. `auth` only
settles whether a request may reach your method. Once inside, chapter 10's ordinary
access rules still apply, to whoever the request turned out to be.

That is why both public routes in the first hands-on step call `sudo()` (run this query
as the superuser, skipping access checks). An anonymous visitor is nobody, and nobody has
rights to read anything.

**`sudo()` is a decision, not a fix.** It stops the checks happening at all. On a
marketing page listing service types, fine. On a page showing one customer's history it
would be a data leak, which is why the portal half of this chapter leans on real rules
instead.

The two layers stack like this:

- **The ACL** (the `ir.model.access.csv` line) says portal users *can* read
  `librefleet.service.order` at all. It says nothing about *which* orders.
- **The record rule** scoped to `customer_id = user.partner_id.id` is what stops one
  customer reading another's history.

That is the identical split chapter 10 built for technicians versus managers, with a
third group added to the same model.

Controllers live in a `controllers/` package, which the module does not have yet:

```console

```

```python title="addons/librefleet/controllers/main.py"
from odoo import http
from odoo.http import request


class LibreFleetPublic(http.Controller):

    @http.route("/librefleet/services", type="http", auth="public", website=False)
    def services_page(self, **kwargs):
        service_types = request.env["librefleet.service.type"].sudo().search([])
        return request.render("librefleet.services_page", {"service_types": service_types})

    @http.route("/librefleet/vehicles/lookup", type="jsonrpc", auth="public")
    def vehicle_lookup(self, license_plate, **kwargs):
        vehicle = request.env["librefleet.vehicle"].sudo().search(
            [("license_plate", "=", license_plate)], limit=1)
        if not vehicle:
            return {"found": False}
        return {
            "found": True,
            "model_name": vehicle.model_name,
            "service_count": vehicle.service_count,
        }
```

Both routes use `sudo()`: `auth="public"` means there is no logged-in user with any
access rights at all, so without it every read would fail with an `AccessError`
before your code got anywhere.

`controllers/__init__.py` imports it, and the module's own `__init__.py` needs the
package:

```python title="addons/librefleet/controllers/__init__.py"
from . import main
```

Only `main` for now. The portal controller joins this file in step 5, once `portal.py`
exists: import it today and the next reload dies with `ImportError: cannot import name
'portal'`, chapter 32's "only import a file once it exists" rule again.


### ACL and record rule for the portal group

Two files, one per layer. First the ACL, appended to the CSV you already have. The
four trailing digits are `read,write,create,unlink`, so `1,0,0,0` is read-only: a

```text title="addons/librefleet/security/ir.model.access.csv"
access_librefleet_service_order_line_portal,librefleet.service.order.line portal,model_librefleet_service_order_line,base.group_portal,1,0,0,0
```

<Step>
### The portal controller, in Python

Four things go in this file. Read them as four separate jobs, not one wall:

- a counter for the `/my` home tile
- a list route
- a detail route
- a download route serving chapter 36's PDF

The detail and download routes are the interesting pair. They are the ones that have to
work for a visitor with no session at all.

```python title="addons/librefleet/controllers/portal.py"
from odoo.addons.portal.controllers.portal import CustomerPortal, pager as portal_pager
from odoo.http import request, route


class LibreFleetPortal(CustomerPortal):

    def _prepare_home_portal_values(self, counters):
        values = super()._prepare_home_portal_values(counters)
        if "service_order_count" in counters:
            partner = request.env.user.partner_id
            values["service_order_count"] = request.env["librefleet.service.order"].search_count(
                [("customer_id", "=", partner.id)])
        return values

    @route(["/my/service-orders", "/my/service-orders/page/<int:page>"],
           type="http", auth="user", website=True)
    def portal_my_service_orders(self, page=1, **kwargs):
        partner = request.env.user.partner_id
        ServiceOrder = request.env["librefleet.service.order"]
        domain = [("customer_id", "=", partner.id)]

        order_count = ServiceOrder.search_count(domain)
        pager = portal_pager(
            url="/my/service-orders",
            total=order_count,
            page=page,
            step=self._items_per_page,
        )
        orders = ServiceOrder.search(
            domain, limit=self._items_per_page, offset=pager["offset"],
            order="scheduled_start desc")

        values = self._prepare_portal_layout_values()
        values.update({
            "orders": orders,
            "page_name": "service_order",
            "pager": pager,
            "default_url": "/my/service-orders",
        })
        return request.render("librefleet.portal_my_service_orders", values)

    @route(["/my/service-orders/<int:order_id>"], type="http", auth="public", website=True)
    def portal_service_order_page(self, order_id, access_token=None, **kwargs):
        # auth="public", not "user": a share link (?access_token=...) has to
        # work for someone who isn't logged in at all. _document_check_access
        # is what actually decides, session-based read access first, the
        # token as a fallback only if that fails.
        try:
            order_sudo = self._document_check_access(
                "librefleet.service.order", order_id, access_token=access_token)
        except Exception:
            return request.redirect("/my")

        values = self._prepare_portal_layout_values()
        values.update({
            "order": order_sudo,
            "page_name": "service_order",
        })
        return request.render("librefleet.portal_service_order_page", values)

    @route(["/my/service-orders/<int:order_id>/report"], type="http", auth="public")
    def portal_service_order_report(self, order_id, access_token=None, **kwargs):
        order_sudo = self._document_check_access(
            "librefleet.service.order", order_id, access_token=access_token)
        report = request.env["ir.actions.report"].sudo()._get_report(
            "librefleet.report_service_order")
        pdf_content, _report_type = report._render_qweb_pdf(
            "librefleet.report_service_order", order_sudo.ids)
        # reference is "SO/2026/0001": a bare slash in Content-Disposition's
        # filename breaks the header (and some browsers read it as a path).
        filename = order_sudo.reference.replace("/", "_")
        return request.make_response(
            pdf_content,
            headers=[
                ("Content-Type", "application/pdf"),
                ("Content-Disposition", "attachment; filename=%s.pdf" % filename),
            ],
        )
```

That `filename = order_sudo.reference.replace("/", "_")` line exists because the first
version did not have it. Chapter 14's sequence gives orders references like
`SO/2026/0001`. A bare slash in a `Content-Disposition` filename looks fine in a curl
transcript and breaks quietly in a real browser, where some read it as a path separator.
Caught by downloading the file and inspecting the header, not by reading the code twice.

Now that `portal.py` exists, add it to the package:

```python title="addons/librefleet/controllers/__init__.py"

from . import portal
```

## Gotchas

- **`type="json"` still runs, deprecated, in Odoo 19.** No error, a `DeprecationWarning`
  in the server log only. Write new routes as `type="jsonrpc"`.
- **A multi-database dev environment needs a database hint on every unauthenticated
  request.** A browser gets this for free from its session cookie once you have
  logged in once; a bare `curl` (or any script) needs `X-Odoo-Database: <db>` or it
  gets a 404 that has nothing to do with your route. A reader's own single-database
  container never sees this.
- **`portal_client_category_enable` defaults to `False`.** Inheriting
  `portal.portal_my_home` and adding content inside `#portal_client_category` renders
  nothing until you also set that flag `True` via an xpath positioned `before` the
  `o_portal_docs` div, the same two-step every core module (`sale`, `project`,
  `account`) does for its own tile.
- **A slash in a filename breaks `Content-Disposition`.** `librefleet.service.order`'s
  `reference` field (chapter 14) contains `/`, exactly the character that field is
  not safe to put raw into an HTTP header meant to name a file. Sanitize it.
- **`auth="user"` and `access_token` do not mix.** A route meant to work for an
  anonymous visitor with a share link must be `auth="public"`; `auth="user"` redirects
  to login before your code, token or no token, ever runs. `_document_check_access`
  is what does the real authorization either way.
