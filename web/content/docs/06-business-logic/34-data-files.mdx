**Goal:** ship a service type as proper master data instead of a UI click, build a
small self-contained demo dataset with `ref()` across files, find out exactly
what `noupdate` does and does not protect, and translate both halves of the module into
French. · **Time:** ~2.5 h · **Checkpoint:** `code/checkpoints/ch34`

## Why this matters

In chapter 11 you created three service types by clicking "New". That was fine then: you
were learning views, not data files. But it does not scale. A fresh install should not
depend on someone remembering to click New three times in the right order.

Writing those records again in a file feels like doing the same work twice. It is not.
**A record you click exists in one database, yours. A record in a data file exists in
every database that ever installs the module.** The file is the definition; the Postgres
row is a copy Odoo makes from it, once per install, forever.

That reversal is the whole chapter. From here on you maintain the file, and the database
follows. You will also learn when XML beats CSV, what a module's `demo` key really does
(and when it deliberately does nothing), and the exact rule deciding whether an upgrade
overwrites a record or leaves it alone. Chapter 14's `ir_sequence.xml` and chapter 33's
`mail_template.xml` both promised "chapter 34 goes deeper on `noupdate`". This is that
chapter.

## Concepts

Five ideas, one per question:

1. XML or CSV, which do I write?
2. Does this record ship to every install, or only to demos?
3. On the next upgrade, does my file overwrite the database or leave it alone?
4. How do records in different files point at each other?
5. What happens to all of it in a second language?

Number 3, `noupdate`, is the one people get wrong, so it gets the most room.

### XML and CSV are the same loader, two shapes

XML and CSV both end up in the same place. Each resolves an xml id, builds a `vals` dict
from its fields, and calls `create` or `write`. The format you pick is about shape, not
capability.

Your own module already has one of each. `security/ir.model.access.csv`:

```console
$ head -3 addons/librefleet/security/ir.model.access.csv
```

```text
id,name,model_id:id,group_id:id,perm_read,perm_write,perm_create,perm_unlink
access_librefleet_vehicle_user,librefleet.vehicle user,model_librefleet_vehicle,group_librefleet_user,1,1,0,0
access_librefleet_vehicle_manager,librefleet.vehicle manager,model_librefleet_vehicle,group_librefleet_manager,1,1,1,1
```

Sixteen rows, all with the same six fields. That is what CSV is for: a uniform table,
one row per record, no variation in shape.

`data/mail_template.xml` is the opposite case, a single record with a nested HTML field
and nothing else like it in the file. Reach for XML when the shape is not a table, or
when there are only one or two records and a header row would be overkill.

<Callout type="info" title="Official docs">
  The [data files reference (19.0)](https://www.odoo.com/documentation/19.0/developer/reference/backend/data.html)
  covers the full `<record>`/`<field>` grammar this chapter builds on: `eval`,
  `search`, function calls, and more than the handful of attributes used here.
</Callout>

### A CSV file's name is not a label, it's the model

**The filename before `.csv` is the model's technical name**, not a description you
chose. Skip this and it will burn you.

Odoo's loader takes the part of the filename before the first `-` and looks up a model
with that exact name. `ir.model.access.csv` works because `ir.model.access` is a real
model. Need a second file for the same model, or a descriptive suffix? Add a dash. Core's
Kuwait localization ships `account.account-kw.csv`: model `account.account`, suffix `kw`.

Here is this chapter's own first attempt, named like a description instead of a model:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial_demo_test2 -i librefleet --with-demo --stop-after-init
```

```text
Module librefleet: loading demo
loading librefleet/data/res_partner_demo.csv
Module librefleet demo data failed to install, installed without demo data
KeyError: 'res_partner_demo'
```

`res_partner_demo.csv` has no dash, so the whole basename becomes the model lookup:
a model literally named `res_partner_demo`, which does not exist. Renaming it
`res.partner-demo.csv` (model `res.partner`, suffix `demo`) fixed it outright, no
other change needed.

### Master data vs demo data: same mechanism, opposite intent

Two manifest keys load data files, and the difference is not the file format:

- **`"data"`**: everything the module needs to be useful. Runs on every install and
  every upgrade.
- **`"demo"`**: fictional records for training, demoing, and testing. Runs only
  when demo is explicitly requested.

The `service_type_master.xml` you are about to write is master data: a real,
required service type. The customer, vehicle, and order you'll add after it are
demo data: illustrative, disposable, never something a production install needs.

### `noupdate`: what it protects, and the one thing it never claimed to

Here is the question `noupdate` exists to answer. Your file says the fee is 59. A manager
has since changed it to 75 in the UI. You upgrade the module. **Who wins, the file or the
database?**

- **Without `noupdate`** (the default for a `"data"` XML file), the **file wins**. Every
  upgrade rewrites the record to match the file exactly, and the manager's 75 is gone.
- **With `noupdate`**, the **database wins**. The record is left exactly as it is, even
  though the file in front of you says something different.

The choice is about ownership. Config *you* own (a sequence prefix, a technical setting)
should let the file win, so upgrades can correct it. Config *the customer* owns (prices,
email wording, anything a manager is invited to edit) needs `noupdate`, or every upgrade
silently undoes their work.

Now the catch, which `noupdate` never promised to cover: "the database wins" only applies
to records that *already exist*.

Chapter 14 wrapped the sequence in `<data noupdate="1">` and promised more detail here.
Odoo 19's own loader (`odoo/modules/loading.py`, `odoo/tools/convert.py`) settles it
precisely, instead of by folklore:

```python
convert_file(env, package.name, filename, idref, mode, noupdate=kind == 'demo')
```

That one line decides a lot:

- Every file under `"demo"` loads with `noupdate=True` automatically, whatever its format.
- A `"data"`-listed **XML** file defaults to `noupdate=False`, but a `<data noupdate="1">`
  block inside it can raise that for just its own records. That is what `ir_sequence.xml`
  and `mail_template.xml` do.
- A **CSV** file has no such block to write. So a `"data"`-listed CSV can never become
  noupdate, and a `"demo"`-listed CSV can never opt out of it.

The manifest list you put a file in decides its default. Only XML can override that
default per file.

What noupdate actually does on an upgrade, from `_tag_record` in the same file:

```python
if self.noupdate and self.mode != 'init':
    if record := env['ir.model.data']._load_xmlid(xid):
        # if the resource already exists, don't update it but store
        # its database id (can be useful)
        self.idref[xid] = record.id
        return None
    # else create it normally
```

Two branches, and only the first is protection:

- **xml id already exists?** Its field values are left untouched, full stop, even if the
  XML in front of you now says something different.
- **xml id does not exist yet?** The record is created normally, noupdate or not.

So `noupdate` protects existing records from being silently rewritten. It never claimed to
block new records from a later upgrade. That is exactly what lets you add a second
master-data record in a follow-up release without touching the first.

  chart={`flowchart TD

### `ref()` and xml ids: one namespace, any format

First, what an xml id is for, because the name says nothing useful.

A record's real database id is a number Postgres hands out, and that number is
**different in every install**. Your Tire Rotation might be id 4; a customer's might be id
91. So a data file can never point at another record by number. An **xml id is a permanent
nickname** you choose, stored next to the record in `ir.model.data`, identical in every
database forever. That is the only reason files can reference each other at all.

Every record from any data file gets one, and any file can then address it, whatever
format created it. The spelling differs:

- **XML**: `ref="xmlid"` on a `<field>`, or `ref('xmlid')` inside a Python `eval`.
- **CSV**: a `field_name:id` column holding the xmlid string.

Same module, use the bare id (`vehicle_demo_ag_12_345`). Another module, use the dotted
form (`base.group_user`, already in your `security/librefleet_security.xml` from chapter
10). The demo data below chains all of it: a CSV row references another CSV row, and an
XML record references both a CSV row and a master-data XML record. Four files, two
formats, one shared namespace.

### Translations are data files too, in two very different places

A `.po` file is a data file, which is why it belongs here. But translations split into two
halves stored nothing alike. Knowing which half you are looking at saves a lot of
confusion.

| | What it covers | Marked with | Stored in |
|---|---|---|---|
| **Code strings** | literals in Python and XML: error messages, button labels | `_("...")` | the module's `i18n/*.po` on disk, cached in memory |
| **Field values** | data a user typed or you shipped: a service type's name | `translate=True` on the field | the database, as a `jsonb` column |

Read the right-hand column again. This is the part that surprises people: **code
translations never enter the database at all.** They are read from your module's `.po`
files and held in memory. Field translations are the opposite. They live in Postgres, one
JSON key per language, in the very same column as the original.

<Callout type="warn" title="ir.translation is gone">
  If you have read older Odoo tutorials, you know a model called `ir.translation` that
  held every translated term in one big table. It does not exist in Odoo 19:
  `"ir.translation" in env` is `False`. Field values moved into `jsonb` columns and code
  strings moved into the in-memory catalog above. Any answer that tells you to query or
  write `ir.translation` was written for Odoo 15 or earlier.
</Callout>

`translate=True` is the interesting one here, because turning it on **changes the column
type**. Chapter 21 warned you that a translatable field is JSON in Postgres, using a core
product as the example. Below you do it to your own model and watch the migration happen.

### The i18n CLI, which moved in Odoo 19

Translations get their own subcommand, alongside `db` and `shell` from chapter 6:

```console
$ docker compose exec odoo odoo i18n --help
usage: odoo [--addons-path=PATH,...] i18n [-h] {import,export,loadlang} ...
```

Three verbs: `loadlang` installs a language, `export` writes a `.po`/`.pot` of your
module's terms, `import` reads one back in. Older tutorials use server flags instead
(`--load-language`, `--i18n-export`, `--i18n-import`); on 19 the subcommand is the way in.

### Ship a service type as master data, not a UI click

Create `data/service_type_master.xml`:

```xml title="addons/librefleet/data/service_type_master.xml"
<?xml version="1.0" encoding="utf-8"?>
<odoo>
    <!-- Master data: config the app needs to be useful out of the box, not
         examples to delete before going live. noupdate="1" so a manager's
         edits (say, a price change) survive the next module upgrade. -->
    <data noupdate="1">
        <record id="service_type_tire_rotation" model="librefleet.service.type">
            <field name="name">Tire Rotation</field>
            <field name="flat_fee">59.0</field>
            <field name="default_duration_h">0.5</field>
        </record>
    </data>
</odoo>
```

Register it in the manifest, after the existing data files and before the views:

```python title="addons/librefleet/__manifest__.py"
    "data": [
        "security/librefleet_security.xml",

        "data/ir_sequence.xml",
        "data/mail_template.xml",
        "data/service_type_master.xml",
        "views/vehicle_views.xml",
```

Nothing. Not an error, not a warning, just silently absent. The upgrade log never even

```console
$ docker compose exec db psql -U odoo -d tutorial -c "select demo from ir_module_module where name='librefleet';"
```

```text

------

```

That one column is Odoo's per-module memory of whether demo was ever loaded. Chapter 8

had no `demo` key at all. So `demo` was set to `false`, and stayed there.

`odoo/modules/loading.py`'s upgrade branch shows why that stored value is the only thing
that matters now:

```python
else:  # 'upgrade' or 'reinit'
    load_data(env, idref, mode, kind='data', package=package)
    if package.demo:
        package.demo = load_demo(env, package, idref, mode)
```

An upgrade checks `package.demo`, the value **already sitting in the database**, not
whether your manifest now has demo files. Install time is the only moment that flag can
flip from false to true. Adding demo files months later does not flip it retroactively.

There is a second, version-specific reason install time itself needs an explicit ask.
Check the actual flag rather than trusting an old habit:


```text
    --without-demo=BOOL

    --skip-auto-install
```

Odoo 19 installs **without** demo unless you ask for `--with-demo` explicitly. If
you remember older tutorials where demo just showed up, that default is why this
one doesn't match your memory.

### Mark your code strings for translation

`translate=True` covers data. Literals in your Python are the other half, and they need
wrapping in `_()`. The wizard from chapter 20 has two user-facing messages. Open
`addons/librefleet/wizards/service_order_approve.py`, which needs two edits.

First the import at the top of the file. It currently reads `from odoo import fields,
models`, so add `_` to it:

```python title="addons/librefleet/wizards/service_order_approve.py"
from odoo import _, fields, models
```

Then the two `raise UserError(...)` calls, both inside `action_confirm`. Wrap each
message in `_()`, leaving the surrounding `if` statements exactly as they are:

```python title="addons/librefleet/wizards/service_order_approve.py"
        if order.stage != "in_progress":
            raise UserError(
                _("Only an order that is in progress can be marked done."))
        if order.margin < 0 and not self.override_negative_margin:
            raise UserError(
                _("This order loses money (margin %(margin).2f). A manager must "
                  "tick the override to complete it anyway.", margin=order.margin))
```

Two things about that second one. The interpolation moved *inside* `_()`, and it became a
**named** placeholder: `%(margin).2f`, with `margin=` passed as a keyword.

Why it matters: formatting outside the call (`_("...") % value`) hands translators a
string with a bare `%.2f` in it and no clue what it holds. A named placeholder survives
translation, and the translator can even reorder it. The output is identical, `-210.90`
either way, so chapter 20's transcript still reads exactly as it did.

<Callout type="info" title="Two spellings of the same helper">
  `from odoo import _` is what you will meet almost everywhere: 990 files under
  `addons/*/models/` use it in Odoo 19, against 238 for the newer `self.env._("...")`.
  Both work and mean the same thing. This book uses the import form because that is what
  core mostly still looks like.
</Callout>

</Step>

<Step>
### Export what you just marked

Now export your own module's terms as a template. The `.pot` is the untranslated master
list a translator works from.

First make the directory it goes in. Your module has no `i18n/` folder yet, and the
command below writes into it with a shell redirect, which will not create a missing
directory for you:

```console
$ mkdir -p addons/librefleet/i18n
```

Skip that and the export fails with `no such file or directory`, pointing at the path
rather than at the real problem. `i18n` is the conventional name and Odoo looks for
translation files there by default, so it is not a name you get to choose.

Now export:

```console
$ docker compose exec -T odoo odoo i18n export -c /etc/odoo/odoo.conf -d tutorial librefleet -l pot -o - > addons/librefleet/i18n/librefleet.pot
$ wc -l addons/librefleet/i18n/librefleet.pot
```

```text
869 addons/librefleet/i18n/librefleet.pot
```

146 terms, and the interesting part is *where they came from*. Three kinds of entry, each
with a comment naming its source:

```console
$ grep -B2 -A1 "Only an order that is in progress" addons/librefleet/i18n/librefleet.pot
```

```text
#. odoo-python
#: code:addons/librefleet/wizards/service_order_approve.py:0
msgid "Only an order that is in progress can be marked done."
msgstr ""
```

That one is there **because you wrapped it in `_()` in step 7**, and it points back at the
exact file. The second kind needs no marking at all, because Odoo knows your field labels
already:

```text
#. module: librefleet
#: model:ir.model.fields,field_description:librefleet.field_librefleet_service_type__default_duration_h
msgid "Default Duration (h)"
msgstr ""
```

And the third kind is the payoff for the two halves of this chapter meeting:

```text
#. module: librefleet
#: model:librefleet.service.type,name:librefleet.service_type_tire_rotation
msgid "Tire Rotation"
msgstr ""
```

That is the *value* of a record, exportable only because the field became `translate=True`
in step 6 **and** the record has a stable xml id from the master data you shipped in step
1. Data with no xml id has nothing for a `.po` to point at.

### Write the French translations

Write `i18n/fr.po` with three translations, keeping each `msgid` byte-identical to the
template (that string *is* the lookup key) and the named placeholder intact:

```text title="addons/librefleet/i18n/fr.po"
# Translation of Odoo Server.
# This file contains the translation of the following modules:
# 	* librefleet
#
msgid ""
msgstr ""
"Project-Id-Version: Odoo Server 19.0\n"
"Report-Msgid-Bugs-To: \n"
"MIME-Version: 1.0\n"
"Content-Type: text/plain; charset=UTF-8\n"
"Content-Transfer-Encoding: \n"
"Plural-Forms: nplurals=2; plural=n > 1;\n"

#. module: librefleet
#: model:librefleet.service.type,name:librefleet.service_type_tire_rotation
msgid "Tire Rotation"
msgstr "Rotation des pneus"

#. odoo-python
#: code:addons/librefleet/wizards/service_order_approve.py:0
msgid "Only an order that is in progress can be marked done."
msgstr "Seul un ordre en cours peut être marqué comme terminé."

#. odoo-python
#: code:addons/librefleet/wizards/service_order_approve.py:0
msgid ""
"This order loses money (margin %(margin).2f). A manager must tick the "
"override to complete it anyway."
msgstr ""
"Cet ordre est déficitaire (marge %(margin).2f). Un responsable doit cocher "
"la dérogation pour le terminer malgré tout."
```

The gettext header (that first `msgid ""` block) is boilerplate every `.po` file carries.
Write it once and never think about it again.

The third message is the one with the named placeholder, `%(margin).2f`, sitting untouched
in both `msgid` and `msgstr`. The translator moves it wherever French phrasing wants it,
but never renames or drops it, because Python fills it in by name at raise time, not by
position.

</Step>

## Gotchas

- **A CSV filename is a model lookup, not a label.** `res_partner_demo.csv` fails
  with `KeyError: 'res_partner_demo'`, a real error from this chapter's own first
  attempt. The model name goes before the first `-`; anything after it is yours.
- **CSV cannot opt out of noupdate.** There is no CSV equivalent of
  `<data noupdate="...">`. A `"data"`-listed CSV is always fully rewritable; a
  `"demo"`-listed CSV is always protected. If a CSV row needs the other behavior,
  it needs to become an XML record instead.
- **noupdate protects existing records, not the file.** Add a new record with a
  fresh xml id to an already-shipped noupdate block, and it is created on the very
  next upgrade, same as any other record. Only records that already exist by xml id
  are left alone.
- **A plain `-u` will not add demo data to a database that never had it.**
  `ir_module_module.demo` is set once, at that module's first install, and an
  upgrade only reloads demo if that flag is already true. Adding demo files later
  needs a fresh database with `--with-demo`, not an upgrade of an existing one.
- **Odoo 19 defaults to `--without-demo`.** If you expected demo data to just show
  up the way an older memory says it should, that default, not a bug in your
  files, is why it didn't.
- **`translate=True` changes the column type, so raw SQL has to change with it.**
  `where name = 'Tire Rotation'` stops working the moment the field becomes
  translatable, with `invalid input syntax for type json` rather than anything
  mentioning translations. Use `name->>'en_US'`. ORM domains are unaffected.
- **`-l` on the i18n commands is greedy.** It takes a list, so
  `i18n export -l pot librefleet` reads *both* `pot` and `librefleet` as language codes
  and then complains `the following arguments are required: MODULE`. Put the module name
  before the flag: `i18n export ... librefleet -l pot`.
- **Exporting without `-o` writes into the module folder, which fails in this setup.**
  The container runs as uid 100 and your bind-mounted `addons/` belongs to your host user,
  so the in-place write dies with `PermissionError`. Export to stdout with `-o -` and let
  your own shell create the file, which is the recipe used above.
- **Pass the iso_code to the i18n commands, not the locale code.** `-l fr_FR` works but
  logs `Ignoring not found languages: fr_FR` first, which reads like a failure and is not
  one: the lookup matches on either `code` or `iso_code`, then reports what is missing by
  comparing against `iso_code` only, and French is `code=fr_FR`, `iso_code=fr`. Passing
  `-l fr` does the same work without the scare.
- **Code translations are not in the database.** There is no table to inspect and nothing
  for a database backup to carry: they are read from your module's `i18n/*.po` files. Ship
  the `.po`, or the translation does not exist on the next machine.
