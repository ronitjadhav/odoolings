**Goal:** write `TransactionCase` and `HttpCase` tests covering the constraint,
computed field, wizard guard and idempotent cron from earlier chapters, run them with
`--test-tags`, and see the demo-data pitfall fail for real before fixing it. ·
**Time:** ~1.5 h · **Checkpoint:** `code/checkpoints/ch38`

## Why this matters

Every chapter since chapter 8 has ended in the same place: `python3 odoolings.py
check chNN`, green, move on. That has been genuinely verifying your work, but it
verifies *your running instance*, by hand, once. It says nothing about whether
chapter 14's overlap constraint still holds after someone refactors
`_check_no_overlap` next month, and it cannot run in a CI pipeline that spins up a
brand new database for every pull request. That is what this chapter's tests are
for: the same behaviors, proven automatically, on any database, forever, not just on
yours today.

One thing will look wrong before it looks obvious, so take it head on. If you have
tested code anywhere else, you expect a test runner: point a command at some files, it
runs them, it prints dots. **Odoo has no such command.** There is no `odoo test`. What
you do instead is install or upgrade the module and *ask the install to run the tests on
its way past*, which is why every command in this chapter looks like a deployment with
`--test-tags` bolted on.

That seems heavyweight until you notice what a test here actually needs. Almost
everything worth testing in Odoo is the ORM: a constraint, a computed field, a record
rule, an `onchange`. None of that is importable Python you can exercise on its own,
because none of it exists until a database has the tables and a module has been loaded
into it. So the database is not test scaffolding, it is the thing under test. Odoo builds
one, installs into it, and runs your assertions inside it.

The good news is the sandbox that makes it safe: every test runs in a transaction that is
thrown away afterwards, so you can create whatever you like and leave no trace. Think of
each test as a rehearsal on a stage that is reset before the next one walks on.

This is also where the tutorial's own house rule (chapter 4: readers get
`--without-demo`, no demo data ships to production installs) stops being background
noise and becomes a trap you can walk straight into. A test that reaches for a demo
record works perfectly on your machine, where you happened to install with demo
data on, and fails on the first real CI run that does not. This chapter makes you
watch that failure happen before showing you how to avoid it.

## Concepts

### TransactionCase: a whole test, one transaction, never committed

The rehearsal-on-a-reset-stage idea, now with the real name on it.

`odoo.tests.TransactionCase` wraps every test method in a database transaction that
gets rolled back when the method ends. Nothing you create in a test method
persists, which is what makes tests safe to run against a real database and fast to
run in bulk: no cleanup code, no risk of one test's leftover data breaking the next
one.

```python
from odoo.tests import TransactionCase, tagged

@tagged("post_install", "-at_install")
class TestServiceOrder(TransactionCase):
    def test_something(self):
        order = self.env["librefleet.service.order"].create({...})
        self.assertEqual(order.margin, 42.0)
```

`@tagged` is what makes a test class findable by the test runner and controls when
it runs. `at_install` (the default) runs right after this module installs, before
any *other* module that might later depend on it. `post_install` runs after
everything in the current batch has finished loading, the more realistic moment for
a test that reads company settings or cross-module data. `@tagged("post_install",
"-at_install")` is the standard combination for a test that needs the database in a
finished state, the `-` removes the default tag rather than adding a second one.

### `--test-tags`: choosing which tests actually run

Odoo's own test suite, every core and OCA module combined, is enormous. Running all
of it on every `-u librefleet` would make iteration unbearable, so `--test-tags`
filters by a compact spec:

```
[-][tag][/module][:class][.method]
```

`/librefleet` runs everything tagged in this module. `/librefleet:TestServiceOrder`
narrows to one class, `.test_no_overlapping_bookings` narrows to one method. A
leading `-` excludes instead of includes. This chapter's Hands-on uses all three
forms for real, against the actual test output, not a description of what they
would do.

### HttpCase: the same idea, over a real HTTP connection

`HttpCase` (itself a `TransactionCase` subclass) starts an actual HTTP client
against the server under test, so `self.url_open(path)` genuinely round-trips
through your `@http.route` decorators, chapter 37's routing and auth logic
included, not a mocked call. It is the non-browser half of Odoo's test tooling; the
browser-driven half, **tours**, script real clicks through real JavaScript and are
what chapter 39's OWL work will use, briefly surveyed in Further reading rather than
built here.

### Fixtures that build their own world

```python title="addons/librefleet/tests/test_service_order.py"
from odoo.exceptions import UserError, ValidationError
from odoo.fields import Datetime
from odoo.tests import TransactionCase, tagged


@tagged("post_install", "-at_install")
class TestServiceOrder(TransactionCase):
    """Every fixture is built here, on purpose: this module installs with
    --without-demo (chapter 4's rule), so a test that reaches for a demo
    record instead is a test that only passes on the author's machine."""

    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        cls.vehicle = cls.env["librefleet.vehicle"].create({
            "license_plate": "TEST-001",
        })
        cls.service_type = cls.env["librefleet.service.type"].create({
            "name": "Test Service",
            "flat_fee": 100.0,
        })
        cls.part = cls.env["librefleet.part"].create({
            "name": "Test Part",
            "standard_cost": 10.0,
            "list_price": 20.0,
        })

    def _create_order(self, start, end, **extra):
        vals = {
            "vehicle_id": self.vehicle.id,
            "service_type_id": self.service_type.id,
            "scheduled_start": start,
            "scheduled_end": end,
        }
        vals.update(extra)
        return self.env["librefleet.service.order"].create(vals)
```

`setUpClass` runs once for the whole class, in its own transaction shared by every
test method, faster than repeating the same creates per test. `_create_order` is a
plain helper, not a test itself; nothing about it is special to Odoo.
</Step>

<Step>
### Chapter 14's constraint and chapter 13's computed field

```python title="addons/librefleet/tests/test_service_order.py"
    def test_no_overlapping_bookings(self):
        """Chapter 14's constraint: the same vehicle cannot be double-booked."""
        self._create_order(Datetime.to_datetime("2026-09-01 09:00:00"),
                            Datetime.to_datetime("2026-09-01 11:00:00"))
        with self.assertRaises(ValidationError):
            self._create_order(Datetime.to_datetime("2026-09-01 10:00:00"),
                                Datetime.to_datetime("2026-09-01 12:00:00"))

    def test_margin_computed(self):
        """Chapter 13: parts_total + labor_total, minus what the parts cost the workshop."""
        order = self._create_order(
            Datetime.to_datetime("2026-09-02 09:00:00"),
            Datetime.to_datetime("2026-09-02 10:00:00"),
            line_ids=[(0, 0, {"part_id": self.part.id, "qty": 2, "price_unit": 20.0})])
        # 2 * 20.0 parts revenue + 100.0 labor - 2 * 10.0 parts cost = 120.0
        self.assertEqual(order.margin, 120.0)
```

`assertRaises` as a context manager is the standard way to assert a constraint
fires: the `with` block is expected to raise, and the test fails if it does not.
</Step>

<Step>
### Chapter 20's wizard guard, tuned to actually lose money

```python title="addons/librefleet/tests/test_service_order.py"
    def test_approve_wizard_blocks_negative_margin(self):
        """Chapter 20: a losing order needs the manager override, not a plain confirm."""
        # A part priced far under what it costs the workshop, so the loss on
        # the part outweighs the flat labor fee: 1.0 revenue + 100.0 labor -
        # 200.0 cost = -99.0. A more realistic loss (say, one cheap part)
        # would not necessarily overcome a flat fee this high, and the point
        # of this test is the wizard's guard, not tuning a margin to the wire.
        expensive_part = self.env["librefleet.part"].create({
            "name": "Expensive Part", "standard_cost": 200.0, "list_price": 1.0,
        })
        order = self._create_order(
            Datetime.to_datetime("2026-09-03 09:00:00"),
            Datetime.to_datetime("2026-09-03 10:00:00"),
            line_ids=[(0, 0, {"part_id": expensive_part.id, "qty": 1, "price_unit": 1.0})])
        order.write({"stage": "confirmed"})
        order.write({"stage": "in_progress"})
        self.assertLess(order.margin, 0, "fixture should lose money for this test to mean anything")
        wizard = self.env["librefleet.service.order.approve.wizard"].create({"order_id": order.id})
        with self.assertRaises(UserError):
            wizard.action_confirm()
```

The first version of this test used `self.part` (standard_cost 10.0) at a low
price, expecting a loss. It passed the `assertLess` check by accident, barely, and a
slightly different fixture would have flipped it silent-green for the wrong reason:
the flat labor fee (100.0) covers a small parts loss easily. The
`self.assertLess(order.margin, 0, ...)` line above is not decoration, it is what
would have caught that: a fixture that fails to set up the scenario it claims to
test should fail loudly, not pass by luck.
</Step>

<Step>
### Wire the tests up, and run them

Wire both files into the package (`tests/__init__.py` is what makes them
discoverable, the same import-chain rule chapter 9 taught for models):

```python title="addons/librefleet/tests/__init__.py"
from . import test_service_order
from . import test_controllers
```

Test files never go in the manifest's `data` list, only Python files that get
imported. Bump the version, then run the whole module's tests on a scratch
database, `--without-demo` on purpose.

Read the command that follows carefully, because it is the intro's point made real:
there is no test subcommand anywhere in it. It installs `librefleet` (`-i`) into a
brand new database (`-d test_ch38`) and `--test-tags` is the flag that says "and while
you are in there, run these". The tests are a passenger on an install:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d test_ch38 --without-demo=True \
    -i librefleet --test-tags /librefleet --http-port=8070 --stop-after-init
...
INFO test_ch38 odoo.tests.result: 0 failed, 0 error(s) of 5 tests when loading database 'test_ch38'
```

<Callout type="warn" title="On Odoo 18 this differs">
  `--without-demo=all` was the idiom on 18 and earlier. Odoo 19 wants a plain
  boolean: passing `all` logs `WARNING option --without-demo: since 19.0, invalid
  boolean value: 'all', assume True` and falls back to `True` anyway, so old scripts
  still work, just noisily. Use `--without-demo=True` going forward. The
  `--http-port=8070` above is only needed because this tutorial's own container is
  already running on 8069, your own single-container setup will not need it.
</Callout>
</Step>

<Step>
### Watch the demo-data pitfall fail, for real

Before settling on the self-contained fixtures above, the natural first instinct is
reaching for a real demo record instead of creating one:

```python
def test_vehicle_count_via_demo_ref(self):
    vehicle = self.env.ref("librefleet.vehicle_demo_ag_12_345")
    self.assertTrue(vehicle.license_plate)
```

That xml id is real, `data/librefleet.vehicle-demo.csv` defines it, and this test
passes on a database installed *with* demo data. Run it on the same
`--without-demo` scratch database everything else in this chapter uses:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d test_ch38 -u librefleet \
    --test-tags /librefleet:TestNaiveDemoPitfall --http-port=8070 --stop-after-init
...
ValueError: External ID not found in the system: librefleet.vehicle_demo_ag_12_345
0 failed, 1 error(s) of 1 tests when loading database 'test_ch38'
```

An `error`, not a `failure`, Odoo's test runner's way of distinguishing "the
assertion was wrong" from "the test could not even run". This tutorial's own
convention (chapter 4, `--without-demo` by default) is exactly the production
convention: a real CI pipeline testing a module meant to ship should never assume
demo data exists. Delete this test, the fixture-building version from the earlier
steps is the fix, not a patch on top of it.
</Step>

## Verify

This chapter's verification is the test runner itself, not `odoolings`: the whole
point is a check that runs on a database it built from scratch, not one that reads
state off yours. There is no `python3 odoolings.py check ch38`.

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial -u librefleet \
    --test-tags /librefleet --stop-after-init
...
INFO tutorial odoo.tests.result: 0 failed, 0 error(s) of 5 tests when loading database 'tutorial'
```

Running against your own `tutorial` database works too, since every test rolls
back: nothing about your chapters 1-37 work changes.

## Gotchas

- **`--without-demo=all` is deprecated.** Odoo 19 wants a boolean; the old value
  still works with a warning, but write `--without-demo=True`.
- **`error` and `failure` are different things in the test summary.** A `failure` is
  a wrong assertion, an `error` is the test not completing at all (an exception
  outside an `assertRaises` block). `self.env.ref()` on a demo xmlid that does not
  exist is always the second kind.
- **Test files are never registered in the manifest.** Only `tests/__init__.py`'s
  imports make them discoverable; adding a file to `data` would try (and fail) to
  load it as an XML or CSV data file instead.
- **A weak assertion can pass by accident.** `test_approve_wizard_blocks_negative_margin`'s
  first fixture happened to pass without actually losing money, because the flat
  labor fee dominated. `assertLess(order.margin, 0, ...)` before the real assertion
  is what would have caught it.
- **`at_install` runs before every module in the batch has finished loading.** A
  test that reads company settings, cross-module records, or anything set up by a
  dependency's own data files should be `post_install`, or it can run against a
  database that is not actually finished yet.
