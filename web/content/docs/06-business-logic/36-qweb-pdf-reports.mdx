**Goal:** give `librefleet.service.order` a printable PDF report with the company's
header and footer, built on the same two-template pattern as the invoice you posted
in chapter 27. · **Time:** ~1.5 h · **Checkpoint:** `code/checkpoints/ch36`

## Why this matters

Every business app eventually needs to hand someone a document: an invoice, a
delivery slip, a service report a customer signs before driving off. You have
printed exactly one of these already, chapter 27's and 28's invoice PDF, and never
looked at how it is built.

Here is the part that catches people, and it is worth saying before anything else.
"Generate a PDF" sounds like a separate discipline: a drawing library, coordinates,
fonts, page geometry, the kind of code where you position a box 40 points in from the
left margin. Odoo does none of that. **An Odoo report is a web page.** You write HTML,
with the same `t-field`, `t-if` and `t-foreach` you have used since chapter 9's views.
Odoo renders it exactly as it renders anything else. Then it hands the finished HTML to
`wkhtmltopdf`, a browser engine whose only job is to print a page rather than display
it. The PDF appears right at the end, as a consequence.

So none of this is a new skill. It is the templating you already know, plus two
conventions that make it print correctly: a wrapper template Odoo calls once per
selected record, and a document template that supplies the header and footer every
company wants on every report without repeating the markup.

## Concepts

Before any of the field names, get the two layers straight, because merging them into
one thing is the most common source of confusion here. A printable report is **a record
plus a template**, and the two know almost nothing about each other:

| | What it is | What it does |
|---|---|---|
| `ir.actions.report` | a row in the database | makes the **Print** entry exist, and names the template to render |
| the QWeb template | XML in your module | produces the actual ink: headings, tables, totals |

The record is the button. The template is the page. Nothing checks that the record's
name for a template matches a template that actually exists, which is why a typo there
installs perfectly and only breaks when somebody clicks Print. Keep the two layers apart
in your head and that behaviour stops being mysterious.

### Two templates, not one

Open any of Odoo's own printable reports and you will find the same shape twice: a
short **wrapper** template that loops over the records you selected and calls a
**document** template for each one. Core's invoice report is exactly this:

```xml
<template id="report_invoice">
    <t t-call="web.html_container">
        <t t-foreach="docs" t-as="o">
            ...
            <t t-call="account.report_invoice_document" t-lang="lang"/>
        </t>
    </t>
</template>
```

`docs` is the recordset the report was called on, whatever you selected before
clicking Print. `web.html_container` is what turns a plain HTML string into the
document wkhtmltopdf will accept; you always call it once, at the top, never per
record. The interesting content lives in the document template, called once per
record inside the loop.

### `web.external_layout`: header, footer, one call

The document template's job is to wrap its own content in `web.external_layout`,
which supplies the company logo, address, and footer from `res.company` without your
template knowing anything about them:

```xml
<template id="report_invoice_document">
    <t t-call="web.external_layout">
        <div class="page">
            <!-- your content -->
        </div>
    </t>
</template>
```

`external_layout` looks for `o.company_id` on whatever record it is wrapping, and
falls back to the current company if the model has no such field, which is exactly
`librefleet.service.order`'s situation: no `company_id` anywhere on it, and the
report still renders the right header because of that fallback.

The `<div class="page">` matters for more than styling. Wrap each record's content in
one and the wrapper template's loop produces one `<div class="page">` per record,
which is what makes printing three selected orders come out as a three-page PDF
instead of three orders squeezed onto whatever pages fit. You are not managing page
breaks by hand; the class does it.

### Binding a report to the Print menu works exactly like chapter 35's server action

`ir.actions.report` is a model, the same family as `ir.actions.server`. It binds to a
model's Print dropdown the same way chapter 35's server action bound to the Vehicles
list's Action menu, `binding_model_id`, but with `binding_type = "report"` instead of
`"action"`. No button XML, no menu record: set the two fields and the report shows up.

## Hands-on

<Steps>

<Step>
### Write the report action and the wrapper template

```xml title="addons/librefleet/report/service_order_report.xml"
<?xml version="1.0" encoding="utf-8"?>
<odoo>
    <data>

        <record id="action_report_service_order" model="ir.actions.report">
            <field name="name">Service Report</field>
            <field name="model">librefleet.service.order</field>
            <field name="report_type">qweb-pdf</field>
            <field name="report_name">librefleet.report_service_order</field>
            <field name="report_file">librefleet.report_service_order</field>
            <field name="print_report_name">'Service Report - %s' % (object.reference)</field>
            <field name="binding_model_id" ref="model_librefleet_service_order"/>
            <field name="binding_type">report</field>
        </record>

        <template id="report_service_order">
            <t t-call="web.html_container">
                <t t-foreach="docs" t-as="o">
                    <t t-call="librefleet.report_service_order_document" t-lang="o.customer_id.lang"/>
                </t>
            </t>
        </template>

    </data>
</odoo>
```

`report_name` is `module.template_id`, the same qualification every xml id needs
outside its own module, chapter 9's rule again. Get it wrong (say, just
`report_service_order` with no module prefix) and the action saves fine but printing
fails with a template-not-found error the moment someone clicks it: nothing at
install time catches it, because the action record and the template it names are
validated independently.

Depend on `web` explicitly in the manifest, even though it is always installed. Your
templates `t-call` into `web.html_container` and `web.external_layout`, and an
explicit dependency is what guarantees those templates are loaded before yours, not
an accident of "web happens to already be there."

```python title="addons/librefleet/__manifest__.py"
"depends": ["base", "product", "base_automation", "web"],
```
</Step>

<Step>
### Write the document template

```xml title="addons/librefleet/report/service_order_report.xml"
        <template id="report_service_order_document">
            <t t-call="web.external_layout">
                <div class="page">
                    <h2>
                        Service Report
                        <span t-field="o.reference"/>
                    </h2>

                    <div class="row mt-4">
                        <div class="col-6">
                            <strong>Vehicle</strong>
                            <p>
                                <span t-field="o.vehicle_id.license_plate"/><br/>
                                <span t-field="o.vehicle_id.model_name"/>
                            </p>
                        </div>
                        <div class="col-6">
                            <strong>Customer</strong>
                            <div t-field="o.customer_id"
                                 t-options='{"widget": "contact", "fields": ["address", "name"], "no_marker": True}'/>
                        </div>
                    </div>

                    <div class="row mt-3">
                        <div class="col-6">

                        <thead>
                            <tr>
                                <th>Part</th>
                                <th class="text-end">Qty</th>
                                <th class="text-end">Unit price</th>
```

That is the whole page. Now go and look at it, because it is not right yet.
</Step>

<Step>
### Render it, and meet a widget that lies

Register the file in the manifest's `data` list and upgrade, then render it once
from the shell to see it for real:

```console
$ docker compose exec -T odoo odoo shell -c /etc/odoo/odoo.conf -d tutorial --no-http
>>> order = env["librefleet.service.order"].search([("reference", "=", "SO/2026/0001")])
>>> report = env["ir.actions.report"]._get_report("librefleet.report_service_order")
>>> pdf_content, report_type = report._render_qweb_pdf("librefleet.report_service_order", order.ids)
>>> open("/tmp/service_report.pdf", "wb").write(pdf_content)
```

```console
$ pdftotext /tmp/service_report.pdf -
Service Report SO/2026/0001
Vehicle
ZH 468 202
Fiat Ducato
Customer
Anna Keller
Service type: Oil change
Technicians: res.users(5,)
Part
Oil filter
...
```

The layout is right, the header and footer are there. But "Technicians:
res.users(5,)" is not a name, it is a recordset's `repr()`. `many2many_tags` is a
**web client widget**, one of the little pills you see in a form view; it has no
meaning to the QWeb report field converter, which silently falls back to printing
whatever `str()` gives it instead of raising an error.

This is the "a report is a web page, not a form view" idea collecting its first debt.
Widgets are the web client's vocabulary, and the web client is not in the room when a
report renders. Anything that only a browser-side widget knows how to draw, you have to
spell out yourself. Fix it with a plain `t-out` over the mapped names:

```xml title="addons/librefleet/report/service_order_report.xml"
                        <div class="col-6">
                            <strong>Technicians:</strong>
                            <span t-out="', '.join(o.technician_ids.mapped('name'))"/>
                        </div>
```

While you're in there, give the money columns two decimal places, the same
`widget: "float"` you would reach for on a form:

```xml title="addons/librefleet/report/service_order_report.xml"
                                <td class="text-end">
                                    <span t-field="line.price_unit" t-options='{"widget": "float", "precision": 2}'/>
                                </td>
```

Do the same for `line.subtotal` and, in the totals row you'll add next, for
`o.parts_total` and `o.labor_total`.
</Step>

`parts_total` and `labor_total` are what the customer paid for. `margin`, chapter
13's computed field, is what the workshop keeps after paying for the parts, and it
has no business on a document you hand to the person who booked the service. Nothing
in Odoo stops you from adding `t-field="o.margin"` here; the only thing that catches
it is knowing not to, which is exactly why this chapter's odoolings checks include one
that fails if that field ever shows up in the template's arch.

<Callout type="warn" title="Gotcha">
  Testing from `odoo shell --no-http`, like the transcripts above, logs a harmless
  `wkhtmltopdf: Exit with code 1 due to network error: ContentNotFoundError` warning.
  `--no-http` means there is no running web server for wkhtmltopdf to fetch images
  from (a company logo, say), so any `<img>`-backed content silently fails to load
  while the rest of the PDF renders fine. Printing from the real running server, the
  one serving `localhost:8069`, has no such gap: there is always an HTTP server to
  fetch from.
</Callout>

## Gotchas

- **`many2many_tags` is a web client widget, not a report field converter.** Used on
  a `t-field` inside a QWeb report, it does not error, it silently prints the
  recordset's `repr()` instead of the names. Join the names yourself with `t-out` and
  `.mapped('name')`.
- **`report_name` needs the module prefix.** `"report_service_order"` instead of
  `"librefleet.report_service_order"` saves without complaint and fails only when
  someone actually clicks Print, with a template-not-found error nothing at install
  time warned you about.
- **`external_layout`'s company fallback is automatic, but only if you never override
  it.** If your model does grow a `company_id` field later, the header switches to
  that company instantly. Worth remembering before you add one without meaning to
  change what a report prints.
- **Testing without a running HTTP server breaks embedded images, not templates.**
  The `ContentNotFoundError` warning from `odoo shell --no-http` looks alarming but
  only affects `<img>`-backed content; text, tables and totals render correctly
  regardless.
- **A field existing on the model does not mean it belongs on every document built
  from that model.** `margin` is a perfectly good field for the form view chapter 13
  built and a terrible thing to hand a customer. The report template is a second
  place field-level access decisions get made, separate from the ACLs chapter 10 set up.
