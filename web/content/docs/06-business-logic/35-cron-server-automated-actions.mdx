**Goal:** build a real feature (nudge the workshop about vehicles overdue for
service) using a scheduled action, a server action and an automated action, and see
exactly how the three relate. · **Time:** ~2 h · **Checkpoint:** `code/checkpoints/ch35`

## Why this matters

Every LibreFleet feature so far has run because a human clicked something. That is
fine for a workshop where a technician opens the app every morning, but a real
integrator's backlog is full of tickets that start "nobody remembered to..." A vehicle
that has not been serviced in six months does not send itself a reminder. An order
stuck in draft for a week does not escalate itself. A digest email does not compose
itself at 7 a.m.

Odoo answers this with three mechanisms. They look separate in the UI but share one
foundation:

- A **scheduled action** (also called a **cron**, after the classic Unix timer) runs code
  on a schedule.
- A **server action** is that code, stored as a database record instead of a Python file,
  runnable from a menu, a button, or a cron.
- An **automated action** wires a server action to a *database event* instead of a clock:
  a field changing, a record being created, a date arriving.

You already met the mechanism tying two of these together, back in chapter 31:
`_inherits`. `ir.cron` uses the same delegation trick against `ir.actions.server` that
`librefleet.loaner` used against `librefleet.vehicle`. Once you see that, "a cron is a
server action with a schedule bolted on" stops being a slogan and becomes something you
can point at in the database.

## Concepts

Almost everyone new to Odoo mixes these three up. The UI files them in three different
menus, and none of the names says what makes it different. Sort them by the only question
that matters, **what makes the code run**, and they stop overlapping:

| | What makes it run | You reach for it when |
|---|---|---|
| **server action** | a person, a button, or another action asking it to | the work needs a home that is not a Python file |
| **scheduled action** (cron) | a clock | nothing and nobody will be there to ask |
| **automated action** | a database event: a record created, a field written, a date arriving | the trigger is something happening to data |

The first row is the one that dissolves the confusion. **The server action is the code;
the other two are only ways of starting it.** A cron is a server action with a schedule
attached. An automated action is a server action with a trigger attached.

You are not choosing between three tools. You are writing one thing, then deciding what
wakes it up. That is why this chapter builds the same feature three times and ends up
pointing at a single database row.

### A server action is code Odoo can point at from three places

`ir.actions.server` is a model, not a script file. A record with `state = "code"` holds a
Python string in its `code` field. That string runs through `safe_eval` against a small,
fixed set of names: `env`, `model` (the model class, e.g. `librefleet.vehicle`), `record`
/ `records` (whatever this run is bound to), and a few date/time helpers. To return
something, assign to a variable named `action` inside the code. That is how a server
action can open a window.

`records` is the detail that trips people up. It is only filled in when the action runs
*bound to a selection*, meaning something with specific ids in mind. Run the same action
from a cron, which has no selection and no rows ticked, and `records` comes back empty. A
server action meant to work both ways has to handle that itself.

### A cron is a server action wearing a schedule

`ir.cron`'s model definition has one line that explains the whole relationship:

```python
_inherits = {'ir.actions.server': 'ir_actions_server_id'}
```

That is delegation inheritance, chapter 31's `librefleet.loaner` pattern, applied by core
Odoo itself. A cron record does not *have* a server action the way an order *has* lines.
It **is** one, plus `interval_number`, `interval_type`, `nextcall` and the other
scheduling fields.

Read or write `cron.code`, `cron.model_id`, `cron.state`, even `cron.name`, and you are
touching the exact same database row the linked `ir.actions.server` record points at. One
row, two models looking at it.

Binding an action to a menu uses two fields on the *action*, not the cron:
`binding_model_id` (which model's views it shows up on) and `binding_view_types` (list,
form, or both). Set those and the action appears in that model's Action menu, runnable on
a selection, with no separate menu record to build.

### An automated action is a server action with a trigger instead of a clock

`base.automation` (module `base_automation`, a separate dependency from `base`) watches
one model for an event and runs a linked server action when it fires. The trigger
vocabulary is wide: `on_create`, `on_create_or_write`, `on_unlink`, `on_time` (a date
field arriving), `on_stage_set` (a `stage_id` many2one reaching a specific value, built
for kanban-pipeline models), and a few mail-specific ones.

Two domain fields narrow it further: `filter_pre_domain` (must have matched *before* the
write) and `filter_domain` (must match *after*). Using both together is how you catch a
*transition*, rather than firing on every write to an already-matching record.

## Hands-on

You will teach `librefleet.vehicle` to remind the workshop about overdue maintenance
three ways: a daily cron, an on-demand button, and an automated action that retires
the reminder once a service actually happens.

<Steps>

<Step>
### Depend on Automated Actions

Automated Actions live in their own module. Add it to `librefleet`'s dependencies:

```python title="addons/librefleet/__manifest__.py"
"version": "19.0.1.21.0",
    ...
    "depends": ["base", "product", "base_automation"],
```

Installing it pulls in `digest`, `resource` and `sms`, which are `base_automation`'s own
dependencies. That is normal, not a sign you depended on the wrong thing. Automation
Rules ship in the same functional area as digest emails and SMS reminders.
</Step>

<Step>
### Give the vehicle both mail mixins

A reminder is an activity, and clearing one when service happens needs to log that
somewhere. Both need mixins from chapter 33:

```python title="addons/librefleet/models/vehicle.py"
from dateutil.relativedelta import relativedelta

from odoo import api, fields, models
from odoo.exceptions import ValidationError

DAYS_BETWEEN_SERVICES = 180


class Vehicle(models.Model):
    _name = "librefleet.vehicle"
    _inherit = ["mail.thread", "mail.activity.mixin"]
    _description = "Workshop Vehicle"
    _rec_name = "license_plate"
```

`mail.activity.mixin` alone looks like it should be enough: vehicles get reminder
activities, not a discussion thread. It is not enough. `action_feedback()`, the method
that marks an activity done, logs its completion note through
`message_post_with_source()`, which lives on `mail.thread`.

Ship with only `mail.activity.mixin` and marking a reminder done throws
`AttributeError: 'librefleet.vehicle' object has no attribute 'message_post_with_source'`
the first time anyone tries. Take both mixins from the start.
</Step>

<Step>
### Write the two methods

One method schedules reminders, one clears them, and both live on the vehicle so the
cron, the button and the automated action can all call the same code:

```python title="addons/librefleet/models/vehicle.py"
    def action_send_maintenance_reminders(self):
        # The scheduled action and the "Send reminders now" server action both
        # call this, so the two triggers can never drift into two different
        # definitions of "overdue".
        reminded = self.env["librefleet.vehicle"]
        activity_type = self.env.ref("mail.mail_activity_data_todo")
        # activity_schedule() leaves user_id empty unless told otherwise (the
        # "Assigned to" default you see in the UI is a client-side fill-in, not
        # something the ORM does), so an unassigned reminder is a real bug and
        # not just a cosmetic one: nobody's activity list would ever show it.
        manager = self.env.ref("librefleet.group_librefleet_manager").user_ids[:1]
        assignee_id = manager.id if manager else self.env.user.id
        cutoff = fields.Datetime.now() - relativedelta(days=DAYS_BETWEEN_SERVICES)
        for vehicle in self:
            done_orders = vehicle.service_order_ids.filtered(
                lambda o: o.stage == "done")
            last_service = max(done_orders.mapped("scheduled_end"), default=False)
            if last_service and last_service >= cutoff:
                continue
            has_open_reminder = vehicle.activity_ids.filtered(
                lambda a: a.activity_type_id == activity_type)
            if has_open_reminder:
                continue
            vehicle.activity_schedule(
                activity_type_id=activity_type.id,
                summary="Schedule maintenance",
                note="No completed service order in the last %d days."
                     % DAYS_BETWEEN_SERVICES,
                user_id=assignee_id)
            reminded += vehicle
        return reminded

    def _clear_maintenance_reminder(self):
        # The automated action's payload: retire the reminder once a service
        # actually happened, instead of leaving it to rot on the activity list.
        activity_type = self.env.ref("mail.mail_activity_data_todo")
        for vehicle in self:
            open_reminders = vehicle.activity_ids.filtered(
                lambda a: a.activity_type_id == activity_type
                and a.summary == "Schedule maintenance")
            open_reminders.action_feedback(feedback="Service completed.")
```

The overdue check walks `service_order_ids` in Python rather than using a clever domain.
LibreFleet's dataset is small enough that this is the right call: a domain over a related
field's aggregate would be harder to read for no real performance gain.

The duplicate check (`has_open_reminder`) matters more than it looks. Without it, a daily
cron creates a fresh "Schedule maintenance" activity every single day for the same
vehicle, forever.
</Step>

<Step>
### Register the server action and the cron, and hit the bug they share

```xml title="addons/librefleet/data/maintenance_reminder_cron.xml"
<?xml version="1.0" encoding="utf-8"?>
<odoo>
    <data noupdate="1">

        <record id="action_send_maintenance_reminders" model="ir.actions.server">
            <field name="name">LibreFleet: maintenance reminders</field>
            <field name="model_id" ref="model_librefleet_vehicle"/>
            <field name="binding_model_id" ref="model_librefleet_vehicle"/>
            <field name="binding_view_types">list</field>
            <field name="state">code</field>
            <field name="code">action = records.action_send_maintenance_reminders()</field>
        </record>

        <record id="cron_send_maintenance_reminders" model="ir.cron">
            <field name="ir_actions_server_id" ref="action_send_maintenance_reminders"/>
            <field name="interval_number">1</field>
            <field name="interval_type">days</field>
            <field name="active" eval="True"/>
        </record>

    </data>
</odoo>
```

`noupdate="1"` for the same reason chapter 34 used it on `ir_sequence.xml`: a manager may
retune the schedule or disable the cron, and an upgrade must not silently reset that.

Notice the cron record sets no `name`. That is deliberate. `ir.cron` delegates `name` to
the same row as the action, so setting it here would also rename the "LibreFleet:
maintenance reminders" entry in the Vehicles list's Action menu. One row, one name.

Register the file, upgrade, and use Settings > Technical > Scheduled Actions >
"LibreFleet: maintenance reminders" > **Run Manually** (the UI button for
`method_direct_trigger()`) to test it without waiting a day:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial -u librefleet --stop-after-init
...
ERROR tutorial odoo.registry: Failed to load registry
...
ValueError: AttributeError("'NoneType' object has no attribute 'action_send_maintenance_reminders'") while evaluating
'action = records.action_send_maintenance_reminders()'
```

This is the eval-context detail from Concepts, made concrete. Run Manually, like the real
scheduler, passes no selection. So `records` is `None`, and `None.anything` fails.

The code needs to fall back to every vehicle when nothing specific was picked:

```xml title="addons/librefleet/data/maintenance_reminder_cron.xml"
            <field name="code">action = (records or model.search([])).action_send_maintenance_reminders()</field>
```

Upgrade again and Run Manually a second time:

```text
INFO tutorial odoo.addons.base.models.ir_cron: Job 'LibreFleet: maintenance reminders' (16) fully done (#loop 1; done 0; remaining 0; duration 0.16s)
```

No traceback this time. Every vehicle overdue for service now has a "Schedule
maintenance" activity, assigned to a workshop manager.

The same server action is also the one a manager clicks by hand, right from the Vehicles
list: select any rows, open the **Actions** cog, and it sits at the bottom, below the
built-ins Odoo ships for every model.

</Step>

<Step>
### Register the automated action

```xml title="addons/librefleet/data/maintenance_reminder_automation.xml"
<?xml version="1.0" encoding="utf-8"?>
<odoo>
    <data noupdate="1">

        <record id="automation_clear_maintenance_reminder" model="base.automation">
            <field name="name">Clear the maintenance reminder when a service order is done</field>
            <field name="model_id" ref="model_librefleet_service_order"/>
            <field name="trigger">on_create_or_write</field>
            <field name="filter_pre_domain">[('stage', '!=', 'done')]</field>
            <field name="filter_domain">[('stage', '=', 'done')]</field>
        </record>

        <record id="action_clear_maintenance_reminder" model="ir.actions.server">
            <field name="name">Clear the vehicle's maintenance reminder</field>
            <field name="model_id" ref="model_librefleet_service_order"/>
            <field name="base_automation_id" ref="automation_clear_maintenance_reminder"/>
            <field name="state">code</field>
            <field name="code">records.mapped('vehicle_id')._clear_maintenance_reminder()</field>
        </record>

    </data>
</odoo>
```

`trigger` is `on_create_or_write`, not the `on_stage_set` you will see in the trigger
dropdown. `on_stage_set` only applies to a `stage_id` many2one on a kanban-pipeline
model, and `librefleet.service.order.stage` is a plain `Selection`, the kind chapter 17
built.

The `filter_pre_domain` / `filter_domain` pair makes this fire exactly once, on the
transition into `done`, instead of on every save of an order that is already done. Before
the write it must **not** match `done`; after the write it must.

Register the file in the manifest's `data` list and upgrade. Then take one order through
chapter 20's flow (statusbar to `in_progress`, then Mark Done in the approve wizard) and
watch its vehicle:

```console
$ docker compose exec -T odoo odoo shell -c /etc/odoo/odoo.conf -d tutorial --no-http
>>> order = env["librefleet.service.order"].search([("reference", "=", "SO/2026/0001")])
>>> vehicle = order.vehicle_id
>>> vehicle.activity_ids.mapped("summary")
['Schedule maintenance']
>>> order.write({"stage": "confirmed"})
>>> order.write({"stage": "in_progress"})
>>> wiz = env["librefleet.service.order.approve.wizard"].create({"order_id": order.id})
>>> wiz.action_confirm()
>>> vehicle.invalidate_recordset()
>>> vehicle.activity_ids.mapped("summary")
[]
```

The reminder is gone, and the vehicle's chatter carries the record of why: a "To-Do
done" note with the feedback "Service completed." attached, because
`action_feedback()` posts one automatically. Nothing in the wizard or the statusbar
button knows the reminder exists; the automated action is what connects a business
decision (this order is finished) to a completely different feature (retire a
maintenance nudge) without either one importing the other.

**The sentence to carry out of this chapter:** you did not build three features, you wrote
two Python methods and then attached three different ways of starting them. A clock started
one, a manager's click started the same one, and a field changing on a different model
started the other. Whenever a ticket says "and it should also happen automatically", this
is the question it is really asking: the code already exists, so what should wake it up?

## Gotchas

- **`records` is empty when nothing triggered a selection.** A cron running on its
  schedule, or Run Manually, passes no selection at all, so a server action meant to
  work from both a menu and a cron needs `records or model.search([])`, not a bare
  `records.whatever()`.
- **`action_feedback()` needs `mail.thread`, not just `mail.activity.mixin`.** It
  posts its completion note through `message_post_with_source()`, which only exists
  on the chatter mixin. Marking an activity done on a model with only
  `mail.activity.mixin` throws `AttributeError`.
- **`ir.cron` and its `ir.actions.server` share one row.** Setting `name` (or
  `model_id`, or `code`) on the cron record writes through to the exact same row the
  action points at, `_inherits` delegation, not a copy. Set it in one place, not both.
- **There is no `on_stage_set` for a plain `Selection` field.** That trigger is
  wired to `stage_id` many2ones on kanban-pipeline models. A hand-rolled `Selection`
  stage (chapter 17's kind) needs `on_create_or_write` with a `filter_pre_domain` /
  `filter_domain` pair to catch a transition.
- **`activity_schedule()` does not default `user_id`.** The "Assigned to" field you
  always see filled in when creating an activity by hand in the UI is a client-side
  convenience, not an ORM default. Skip `user_id` in code and the activity gets
  created with nobody responsible for it, invisible on every user's activity list.
- **Forgetting `binding_model_id` fails silently.** The action still saves, the cron
  still runs it fine, it simply never appears in any Action menu, only under
  Settings > Technical > Server Actions. No error tells you; you just never see the
  button you expected.
