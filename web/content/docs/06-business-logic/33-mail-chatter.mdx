**Goal:** wire `mail.thread` and `mail.activity.mixin` into the service order, track its
important fields, and send a real templated email. · **Time:** ~2 h ·
**Checkpoint:** `code/checkpoints/ch33`

## Why this matters

Open almost any record in Odoo (a partner, an invoice, a lead) and there is a column of
messages and log entries down the right side: who changed what, who was notified, what
still needs doing. That is the **chatter**. It is not a plugin bolted onto a few special
models. It is two mixins any model can inherit.

By the end of this chapter your service orders have the same audit trail, follower list
and to-do scheduler as a core Odoo invoice. This is also where `_inherit` shows its fourth
face. Chapter 31 covered a single string, a new `_name`, and `_inherits` with an `s`, but
never the form you type most often in real modules: a **list**.

Why this feels like overkill at first, said out loud: on screen the chatter looks like a
comment box, and a comment box should be one text field. Two mixins, a separate message
model, a follower table and an activity scheduler is a lot of machinery for somewhere to
type notes.

Here is the picture that fixes it. **Odoo keeps one shared drawer for every message in the
system.** Your model does not store its conversation. Every message in the database lives
in one table, each carrying a label saying which record it belongs to.

So inheriting the mixin does not give your record a notes field. It makes your record
*addressable*, so messages, followers and to-dos can point at it. That is why the
machinery exists, and why the next section can promise none of it touches your table.

## Concepts

The panel you are about to add is really three separate things sharing one column of the
form. Keep them apart from the start:

| The piece | What it answers | Lives in |
|---|---|---|
| the **thread** | what happened to this record | `mail.message` |
| the **followers** | who gets told about it | `mail.followers` |
| the **activities** | what still needs doing, and by whom | `mail.activity` |

Two mixins supply them. `mail.thread` gives you the first two, `mail.activity.mixin` the
third. Everything below is those three ideas, plus one rule about *when* a tracked change
actually becomes a message. That last one is the part that costs people an evening.

### `_inherit` as a list: mixing in, not extending

```python
_inherit = ["mail.thread", "mail.activity.mixin"]
```

This is still classic extension (chapter 31), just aimed at more than one target at once,
with `_name` still present. Read it as: "this model *is* `librefleet.service.order`, and it
also picks up everything `mail.thread` and `mail.activity.mixin` contribute."

Both of those are an `AbstractModel`: a model with no table of its own, existing purely to
be mixed into others this way. It is exactly the alternative chapter 31 pointed you at when
prototype inheritance felt like the wrong tool.

<Mermaid
  chart={`flowchart LR
    A["librefleet.service.order"] -- "_inherit = [...]" --> B["mail.thread<br/>(AbstractModel)"]
    A -- "_inherit = [...]" --> C["mail.activity.mixin<br/>(AbstractModel)"]
    B --> D["message_ids, message_follower_ids<br/>message_post(), message_subscribe()"]
    C --> E["activity_ids, activity_state<br/>activity_schedule()"]`}
/>

Neither mixin adds a single column to `librefleet_service_order`. You can prove that
yourself once the module is upgraded:

```console
$ docker compose exec db psql -U odoo -d tutorial -c "\d librefleet_service_order"
```

Same fourteen columns as chapter 32 left it, nothing new. The thread lives in
`mail_message`, keyed back to your record by a generic `(model, res_id)` pair, the same
polymorphic pattern that lets one `mail.message` table serve every model in Odoo:

```console
$ docker compose exec db psql -U odoo -d tutorial -c "\d mail_message" | grep -E "model |res_id"
```

```text
 model               | character varying |
 res_id              | integer           |
```

There is the shared drawer, literally. `model` holds the name of your model, `res_id` holds
the id of the one record, so a single table carries the conversation for every model in
Odoo at once. Nothing about `mail_message` knows or cares that service orders exist.

Followers (`mail.followers`) and activities (`mail.activity`) work the same way. The mixin
gives your model the *fields and methods* to read and write that shared storage. It never
touches your table.

### `tracking=True`: the field decides, the framework writes the message

Add `tracking=True` to a field and every value change posts itself to the chatter, before
and after, with no code beyond the one keyword:

```python
stage = fields.Selection([...], default="draft", required=True, tracking=True)
```

Track the fields that answer "what happened to this record and when", not everything.
`notes` changing constantly would bury the two changes that actually matter under noise
nobody reads.

### The chatter widget: one tag, three panels

```xml
<chatter/>
```

That is the entire Odoo 19 syntax. It renders the message thread, the follower list, and
the activity scheduler, wired to whichever mixins the model inherited. Put it as the last
child of `<form>`, after `</sheet>`, the same place every core form puts it.

<Callout type="info" title="On Odoo 18 this differs">
  18 spells this out as three separate elements inside a `<div class="oe_chatter">`:
  `<field name="message_follower_ids"/>`, `<field name="activity_ids"/>`, and
  `<field name="message_ids"/>`. The single `<chatter/>` tag is new in 19. If you ever
  read an older module's form view, that expanded form is what you are looking at.
</Callout>

### The rule that will cost you an evening if you don't know it: tracking needs a commit

Here is the fact this chapter is really about, found by testing, not by reading a
changelog. Write a tracked field in the shell and check `message_ids` right away:

```console
>>> o = env["librefleet.service.order"].search([], limit=1)
>>> o.write({"stage": "confirmed"})
>>> len(o.message_ids)
0
```

Nothing. Not a bug, and not something `env.flush_all()` fixes either. Flushing writes your
pending changes to the database, but tracking messages are built by a **precommit** hook,
which only runs when the transaction actually commits:

```console
>>> env.cr.commit()
>>> o.invalidate_recordset()
>>> len(o.message_ids)
1
>>> m = o.message_ids[0]
>>> m.subtype_id.name
'Note'
>>> tv = m.tracking_value_ids[0]
>>> tv.field_id.name, tv.old_value_char, tv.new_value_char
('stage', 'Draft', 'Confirmed')
```

That message did not exist a moment ago. The commit is what materialised it, complete with
the exact before and after values.

This is exactly why this chapter's odoolings check tests over XML-RPC rather than a bare
recordset write. Every RPC call is its own transaction, so by the time the call returns
the commit already happened and the message is really there. In the shell you control the
transaction yourself, so you have to ask for it.

## Hands-on

### Inherit the mixins

In `models/service_order.py`:

```python title="addons/librefleet/models/service_order.py"
class ServiceOrder(models.Model):
    _name = "librefleet.service.order"
    _inherit = ["mail.thread", "mail.activity.mixin"]
    _description = "Service Order"
    _rec_name = "reference"
    _order = "scheduled_start desc, id desc"
```

### Post, subscribe, schedule

```console
$ docker compose exec odoo odoo shell -c /etc/odoo/odoo.conf -d tutorial --no-http
```

```python
>>> o = env["librefleet.service.order"].search([], limit=1)
>>> o.message_post(body="Customer called: OK to keep the vehicle overnight.")
>>> env.cr.commit()
>>> o.message_ids[0].body
'<p>Customer called: OK to keep the vehicle overnight.</p>'
>>> o.message_subscribe(partner_ids=o.customer_id.ids)
>>> env.cr.commit()
>>> o.message_follower_ids.mapped("partner_id.name")
['Administrator', 'Beat Muster']
>>> o.activity_schedule("mail.mail_activity_data_call",
...     summary="Call about pickup time", user_id=env.uid)
>>> env.cr.commit()
>>> o.activity_state, o.activity_ids[0].activity_type_id.name
('today', 'Call')
```

`message_post` is the manual, no-tracking way to add a note. `message_subscribe` adds a
follower without posting anything; every follower gets notified the next time a message
is logged. `activity_schedule` needs an activity type's XML id (`mail_activity_data_call`
is core's built-in "Call" type) and gives you `activity_state` back for free, one of
`overdue`, `today`, or `planned`, computed from the earliest deadline across all of a
record's activities.

Refresh the order in the browser and the chatter panel shows all three: the tracked
stage change from earlier, your note, and the scheduled call.

![The service order's chatter panel: a Planned Activity "Call about pickup time", a posted note "Customer called: OK to keep the vehicle overnight", and a tracked Draft to Confirmed stage change, all on one record](/screens/ch33-chatter-three-pieces.jpg)

That is the three pieces from the top of the chapter, now real on your own model: a thread
carrying two messages, a follower list naming who hears about them, and one activity
waiting to be done. Your table still has the same fourteen columns it had before you
started. Everything you just created is sitting in the shared drawer with your record's
name on the label.

### A template that writes itself, correctly, per customer

Create `data/mail_template.xml`:

```xml title="addons/librefleet/data/mail_template.xml"
<record id="mail_template_service_done" model="mail.template">
    <field name="name">Service Order: ready for collection</field>
    <field name="model_id" ref="librefleet.model_librefleet_service_order"/>
    <field name="subject">Your vehicle is ready ({{ object.reference }})</field>
    <field name="email_from">{{ user.email_formatted }}</field>
    <field name="partner_to">{{ object.customer_id.id }}</field>
    <field name="body_html" type="html">
        <div>
            <p>Hello <t t-out="object.customer_id.name or ''">Customer</t>,</p>
            <p>
                The work on <t t-out="object.vehicle_id.license_plate or ''">plate</t>
                is finished and the vehicle is ready for collection.
            </p>
        </div>
    </field>
</record>
```

`{{ }}` is [QWeb inline expressions](https://www.odoo.com/documentation/19.0/developer/reference/backend/mixins.html#reference-mixins-mail-chatter):
`object` is always the record the template renders against, so `{{ object.reference }}`
in the subject and `{{ object.customer_id.id }}` in `partner_to` mean this one template
produces a different subject and a different recipient for every single order, with no
Python at all. Wrap the file in `<data noupdate="1">`, the same tag ch14 used for the
sequence: a template is master data a manager is expected to edit in the UI, and an
upgrade must never overwrite their wording. Register it in the manifest, above the view
files:

```python
"data": [
    "security/librefleet_security.xml",
    "security/ir.model.access.csv",
    "data/ir_sequence.xml",
    "data/mail_template.xml",
    ...
```

Upgrade, then render it against a real order without sending anything:

```console
>>> tmpl = env.ref("librefleet.mail_template_service_done")
>>> tmpl._render_field("subject", o.ids)[o.id]
'Your vehicle is ready (SO/2026/0002)'
>>> tmpl._render_field("body_html", o.ids)[o.id]
'...The work on ZH 468 202 is finished...'
```

Two different orders render two different subjects. That is the entire point of a
template: write the wording once, let every send fill in its own facts.

</Step>

you saw in the shell.

## Gotchas

- **A tracked write posts nothing until the transaction commits.** In the shell that means
  you, explicitly, with `env.cr.commit()`. Over RPC, a form save, or any normal request,
  it already happened by the time you can look. This is the single most likely thing to
  make you think tracking is broken when it is not.
- **`tracking=True` on every field is worse than on none.** A chatter that logs
  `notes` changing every time someone fixes a typo trains everyone to stop reading it,
  right before the stage change that actually mattered scrolls past unnoticed.
- **`message_post` and a tracked write look similar and are not.** `message_post` is a
  manual note with no before/after values and nothing enforcing you wrote something true.
  Tracking is automatic, sourced from the ORM's own diff, and cannot be forgotten to call.
- **The message body wants HTML, not plain text.** `message_post(body="...")` works with
  a plain string because Odoo wraps it in `<p>`, but anything containing `<`, `>` or `&`
  from user input should be escaped first, or a stray angle bracket in a customer's note
  corrupts the rendered thread.
- **`activity_schedule` needs a real activity type's XML id.** Guessing a name that looks
  right (`"call"`, `"mail.activity_call"`) fails with `ValueError: External ID not found`.
  Confirm one from the `res.groups`-style search you already know:
  `env.ref("mail.mail_activity_data_call")`.
