**Goal:** build all three inheritance mechanisms into LibreFleet and be able to
predict, before running anything, what each one does to the database. ·
**Time:** ~2.5 h · **Checkpoint:** `code/checkpoints/ch31`

## Why this matters

This is the chapter that makes you dangerous in someone else's codebase. Nearly
every ticket an integrator picks up ends with the same instruction: *change how
this existing thing behaves, without touching its source*. Odoo gives you three
different mechanisms for that, they look almost identical in Python, and they do
completely different things to your schema. Choosing the wrong one is not a
style mistake: it produces a second table full of records nobody wanted, or a
field that silently never appears where you expected it.

Before the mechanisms, the thing nobody says out loud. You already know what
inheritance means: you write a subclass, you get a new class, and the original is
left alone. Odoo's most common form of inheritance does the **opposite**. It
reaches back into a model somebody else wrote and edits it in place, for every
module that uses it and every record that already exists. That is not subclassing
in any sense Python taught you, and it is the reason these three keep feeling
slippery: you are trying to map all three onto subclassing, and only one of them
fits.

Part 6 spends the next seven chapters extending things, and all of it rests on
getting this right.

## Concepts

### One keyword, three behaviours

Picture the registry as **a cabinet of blueprints**, one blueprint per model name.
Each of the three mechanisms is a different thing you can do at that cabinet:

- **Classic extension** walks up to a blueprint that is already filed and pencils an
  extra line onto it. Nothing new gets filed.
- **Prototype** photocopies a blueprint, files the copy under a new name, and edits
  only the copy. The original never hears about it again.
- **Delegation** files a new blueprint that says "for the chassis, see blueprint X",
  keeping a pointer to it rather than a copy of it.

Two questions tell them apart, and they are the only two that matter: **does a new
blueprint get filed at all**, and if one does, **did it copy the original or point
at it?**

Everything hinges on two class attributes, `_inherit` and `_name` (and a third,
`_inherits`, with an `s` that is very easy to misread):

<Mermaid
  chart={`flowchart TD
    A["_inherit set"] --> B{"is _name also set?"}
    B -- "no" --> C["CLASSIC EXTENSION<br/>same model, same table<br/>you are editing the original"]
    B -- "yes, a new one" --> D["PROTOTYPE<br/>new model, new table<br/>fields copied, then unrelated"]
    E["_inherits = {parent: field}"] --> F["DELEGATION<br/>two tables, linked<br/>parent's fields reachable through the link"]`}
/>

All three side by side, which is the table worth coming back to:

| | Classic extension | Prototype | Delegation |
|---|---|---|---|
| Written as | `_inherit`, no `_name` | `_inherit` **and** `_name` | `_inherits` and `_name` |
| A new model name appears? | No | Yes | Yes |
| A new table appears? | No | Yes | Yes |
| The parent's fields are | the ones you are editing | copied once, then independent | reachable live, through a link |
| Records that already exist | all gain the field at once | unaffected | unaffected |
| Data shared with the parent? | same model, so the question is moot | No | Yes, one single copy |
| Reach for it when | changing something that already exists | almost never, see the callout below | "an X **is a** Y, plus extra" |

### Classic extension: you are editing the original

```python
class Vehicle(models.Model):
    _inherit = "librefleet.vehicle"      # no _name

    is_loanable = fields.Boolean()
```

No `_name`, so this class **is** `librefleet.vehicle`. The field lands on the
existing model and the existing table, as if it had been written in the original
file. Every existing record gets the new column, every existing view can show it,
and any other module that touches vehicles sees it too. This is the mechanism you
will use for about ninety percent of real work, and it is what chapter 32 uses to
add fields to core models like `res.partner`.

### Prototype: a copy that then goes its own way

```python
class Consumable(models.Model):
    _name = "librefleet.consumable"      # a NEW name
    _inherit = "librefleet.part"         # start from part's fields

    unit = fields.Char(default="litre")
```

Adding a `_name` changes the meaning entirely. You now get a **brand new model**
with a **brand new table**, pre-populated with copies of the parent's field
definitions. The two models share no data and no records: a consumable is not a
part, and a part is not a consumable.

<Callout type="info" title="In the field">
  Of the three, prototype is by far the rarest in real integrator work, and if
  you find yourself reaching for it, pause. Wanting "the same fields again"
  usually means you actually want one model with a category field on it, or an
  `AbstractModel` mixin holding the shared fields. Recognise prototype mostly so
  that you notice when you have written one **by accident**, which is how it almost
  always shows up: someone copies a class as a starting point, keeps its `_inherit`,
  and changes the `_name`.
</Callout>

### Delegation: composition, wearing inheritance's clothes

```python
class Loaner(models.Model):
    _name = "librefleet.loaner"
    _inherits = {"librefleet.vehicle": "vehicle_id"}   # note the s

    vehicle_id = fields.Many2one(
        "librefleet.vehicle", required=True, ondelete="cascade", index=True)
    daily_rate = fields.Float()
```

`_inherits` is not really inheritance at all, it is composition with automatic
forwarding. A loaner **has a** vehicle (via a required many2one) and Odoo makes
that vehicle's fields readable and writable straight off the loaner, as though
they belonged to it. Two tables, two rows, one logical thing. Core uses this for
`res.users`, which delegates to `res.partner`: that is why a user has a `name`
and an `email` without `res_users` having those columns.

Use delegation when the sentence "an X **is a** Y, plus extra" is genuinely true
and you want to reuse Y's data, not just its shape.

## Hands-on

<Steps>

<Step>
### Write all three classes

One file, three classes, one of each mechanism, so you can compare them without
switching context. Create `models/loaner.py`:

```python
from odoo import fields, models


class Vehicle(models.Model):
    """Classic extension: no _name, so this IS librefleet.vehicle."""

    _inherit = "librefleet.vehicle"

    is_loanable = fields.Boolean(
        help="Can this vehicle be lent out while a customer's own car is in "
             "the workshop?")


class Consumable(models.Model):
    """Prototype: _inherit plus a new _name copies the fields into a new model."""

    _name = "librefleet.consumable"
    _inherit = "librefleet.part"
    _description = "Workshop Consumable"

    unit = fields.Char(default="litre", help="Litres, metres, whatever it is sold in.")


class Loaner(models.Model):
    """Delegation: a loaner IS a vehicle, plus rental attributes."""

    _name = "librefleet.loaner"
    _inherits = {"librefleet.vehicle": "vehicle_id"}
    _description = "Loaner Car"

    vehicle_id = fields.Many2one(
        "librefleet.vehicle", required=True, ondelete="cascade", index=True)
    daily_rate = fields.Float(help="What the customer is charged per day.")
    available = fields.Boolean(default=True)
```

Note what the classes do *not* include: the classic extension needs no ACL, no view
and no menu, because `librefleet.vehicle` already has all three. Only the two brand
new models need wiring, which is the next step.

</Step>

<Step>
### Wire up the two new models

The two new models need ACLs, exactly as chapter 10 taught. Add four lines to
`security/ir.model.access.csv`: read plus write for users and full CRUD for managers on
loaners, read-only for users and full CRUD for managers on consumables.

```csv
access_librefleet_consumable_user,librefleet.consumable user,model_librefleet_consumable,group_librefleet_user,1,0,0,0
access_librefleet_consumable_manager,librefleet.consumable manager,model_librefleet_consumable,group_librefleet_manager,1,1,1,1
access_librefleet_loaner_user,librefleet.loaner user,model_librefleet_loaner,group_librefleet_user,1,1,0,0
access_librefleet_loaner_manager,librefleet.loaner manager,model_librefleet_loaner,group_librefleet_manager,1,1,1,1
```

Then a simple list/form view plus a menu item for loaners, in a new
`views/loaner_views.xml`, and **register both new files**, which means two different
places and forgetting either one bites:

- `loaner.py` goes in `models/__init__.py` (last, for the reason step 3 is about to make
  painfully clear).
- `views/loaner_views.xml` goes in the manifest's `data` list, above
  `views/librefleet_menus.xml`. Miss this and the menu item you just wrote points at an
  action that was never loaded, so the upgrade dies with
  `External ID not found in the system: librefleet.action_librefleet_loaner`.

Bump the version to `19.0.1.16.0` while you are in the manifest.

</Step>

<Step>
### Break-it lab: import order is not decorative

Add the import alphabetically, the way the file is already sorted:

```python
from . import loaner
from . import part
from . import service_order
from . import service_type
from . import vehicle
```

Upgrade, and it refuses to start:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial -u librefleet --stop-after-init
...
TypeError: Model 'librefleet.vehicle' does not exist in registry.
```

`loaner.py` extends `librefleet.vehicle` and prototypes `librefleet.part`, so
both have to be registered by the time it is imported. **Within a single module,
`__init__.py` import order matters** whenever one file inherits from a model
defined in another. Move the import to the end and it loads:

```python
from . import part
from . import service_order
from . import service_type
from . import vehicle

# loaner.py extends librefleet.vehicle and prototypes librefleet.part, so both
# must already be registered: within a module, import order matters.
from . import loaner
```

This bites people most often when they alphabetise imports out of tidiness, or
when a linter does it for them.

</Step>

<Step>
### Ask Postgres what actually happened

This is the part worth doing slowly. Three mechanisms, three completely
different schema outcomes, all visible in one query each. First, the classic
extension:

```console
$ docker compose exec db psql -U odoo -d tutorial -c "select column_name from information_schema.columns where table_name='librefleet_vehicle' and column_name='is_loanable';"
 column_name
-------------
 is_loanable
(1 row)
```

A new column on the **existing** vehicle table. No new table, no new model.

Now the prototype:

```console
$ docker compose exec db psql -U odoo -d tutorial -c "select column_name from information_schema.columns where table_name='librefleet_consumable' order by ordinal_position;"
  column_name
---------------
 id
 create_uid
 write_uid
 name
 code
 unit
 create_date
 write_date
 standard_cost
 list_price
(10 rows)
```

A whole new table carrying **copies** of `name`, `code`, `standard_cost` and
`list_price` from `librefleet.part`, plus its own `unit`. And the delegation:

```console
$ docker compose exec db psql -U odoo -d tutorial -c "select column_name from information_schema.columns where table_name='librefleet_loaner' order by ordinal_position;"
 column_name
-------------
 id
 vehicle_id
 create_uid
 write_uid
 available
 create_date
 write_date
 daily_rate
(8 rows)
```

Look at what is **missing**: no `license_plate`, no `model_name`, no `year`. The
loaner table holds only its own fields plus the link. The vehicle data stays in
the vehicle table, which is the entire point.

Three trips to the blueprint cabinet, three different things in the schema: a
pencil line on a blueprint already filed, a photocopy filed under a new name, and
a new blueprint holding a pointer instead of a copy. **The sentence to carry out of
this chapter:** `_inherit` alone edits what already exists, `_inherit` with `_name`
copies it, and `_inherits` points at it.

</Step>

<Step>
### Delegation from the inside

In the shell, watch one `create` write two rows:

```console
>>> V, L = env["librefleet.vehicle"], env["librefleet.loaner"]
>>> V.search_count([])
3
>>> loaner = L.create({"license_plate": "LOAN-001", "model_name": "Fiat Panda", "daily_rate": 29.0})
>>> V.search_count([])
4
```

Creating a loaner created a vehicle. You passed `license_plate` and `model_name`
to a model that has neither column, and Odoo routed them to the parent row.
Reading and writing work the same way:

```console
>>> loaner.license_plate, loaner.model_name
('LOAN-001', 'Fiat Panda')
>>> loaner.vehicle_id.license_plate
'LOAN-001'
>>> loaner.license_plate = "LOAN-999"
>>> loaner.vehicle_id.license_plate
'LOAN-999'
```

Writing through the child changed the parent, because there is only one copy of
that data. And because the backing row is a genuine vehicle, it shows up
everywhere vehicles do:

```console
>>> V.search([("license_plate", "=", "LOAN-999")]).ids == loaner.vehicle_id.ids
True
```

</Step>

<Step>
### How delegation is actually implemented

`_inherits` is not magic bolted into the ORM's read path. Ask the field itself
what it is:

```console
>>> f = env["librefleet.loaner"]._fields["license_plate"]
>>> f.inherited, f.related, f.store
(True, 'vehicle_id.license_plate', False)
```

It is a **non-stored related field**, exactly the kind you wrote by hand back in
chapter 13, generated automatically for every field on the parent. That single
line explains all the behaviour above: why there is no column, why reads and
writes pass through, and why `related` points along `vehicle_id`.

</Step>

<Step>
### Prototype records are strangers

```console
>>> P, C = env["librefleet.part"], env["librefleet.consumable"]
>>> c = C.create({"name": "Engine oil 5W-30", "code": "OIL-530", "standard_cost": 6.5})
>>> c.name, c.code, c.unit
('Engine oil 5W-30', 'OIL-530', 'litre')
>>> P.search([("code", "=", "OIL-530")]).ids
[]
```

The consumable has part's fields and its own `unit` default, but searching parts
for it finds nothing. Two tables, no relationship. The copy happened once, at
class definition time, and the models have been strangers ever since.

</Step>

<Step>
### The cascade only runs one way

Delete the backing vehicle and the loaner goes with it, which is what
`ondelete="cascade"` on `vehicle_id` buys you:

```console
>>> loaner = L.create({"license_plate": "CASCADE-1", "daily_rate": 10.0})
>>> lid = loaner.id
>>> loaner.vehicle_id.unlink()
>>> L.browse(lid).exists().ids
[]
```

But go the other way and the vehicle survives on its own:

```console
>>> l = L.create({"license_plate": "ASYM-TEST", "daily_rate": 1.0})
>>> vid = l.vehicle_id.id
>>> l.unlink()
>>> bool(V.browse(vid).exists())
True
```

Deleting a loaner leaves an ordinary vehicle behind. That is defensible (the car
still exists, it just is not a loaner any more) but it is rarely what people
expect, and it quietly accumulates rows. Roll back when you are done
experimenting.

</Step>

</Steps>

## Gotchas

- **`_inherit` versus `_inherits` is one letter and a completely different
  feature.** Reading code quickly, they look the same. If a model has a
  mysterious required many2one and fields you cannot find declared anywhere,
  look for the `s`.
- **Adding `_name` to an existing extension silently forks it.** The class keeps
  working, the module still installs, and your field quietly stops appearing on
  the model you meant to change, because you just created a copy instead. Quiz
  question 1 walks through exactly this scenario; in real life it usually happens
  while copy-pasting a class as a starting point.
- **Import order inside a module matters.** A file that inherits from a model
  defined in a sibling file must be imported after it, or the registry raises
  `Model '...' does not exist in registry`. Alphabetising imports is the usual
  cause.
- **Delegation cascades parent to child only.** Deleting the parent removes the
  child (via `ondelete="cascade"`); deleting the child leaves the parent behind
  as an orphan. Decide deliberately whether that is what you want, and clean up
  in an override if it is not.
- **Prototype inheritance copies definitions, not data, and not future
  changes to records.** The two models are independent from the moment the
  registry is built. Nothing you do to a part will ever touch a consumable.
