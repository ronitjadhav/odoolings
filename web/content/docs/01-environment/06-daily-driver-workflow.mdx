**Goal:** master the handful of commands and habits that make up 90% of an Odoo
developer's day, including stopping inside core with a debugger. · **Time:** ~2.5 h ·
**Checkpoint:** none, but `odoolings check ch06` must pass.

## Why this matters

Odoo development has a rhythm: change code, upgrade the module, read the log, poke the
database, repeat. Developers who know the CLI do a lap of that loop in seconds;
developers who don't restart everything and click through the UI hoping for the best.
This chapter installs the fast loop, and every hands-on from chapter 8 onward assumes
you have it.

## Concepts

### One binary, many commands

Everything is a subcommand of the `odoo` executable (called `odoo-bin` when you run
from source; the Docker image installs it as `odoo`). In our environment it lives
inside the container, so the daily pattern is:

```console
$ docker compose exec odoo odoo <command> -c /etc/odoo/odoo.conf ...
```

That's a mouthful. If you want to shorten it, two aliases cover almost everything:

```console
$ alias oc='docker compose exec odoo odoo -c /etc/odoo/odoo.conf'
$ alias ocdb='docker compose exec odoo odoo db -c /etc/odoo/odoo.conf'
```

An **alias** is just a nickname your shell expands before it runs anything: type `oc`
and the shell swaps in the long command, then appends whatever else you typed. So
`oc --version` runs the whole thing with `--version` on the end:

```console
$ oc --version
Odoo Server 19.0-20260630
```

Two aliases, not one, and the reason is a genuine sharp edge in Odoo's CLI:
**`-c` belongs to whichever command you are running.** The server accepts it up front,
so `oc -d tutorial -u librefleet` works. The `db` command defines its own `-c`, so the
config flag has to come *after* the word `db`. Get it wrong and you get a confusing
error blaming the server for arguments it never asked for:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf db init scratch
odoo [--addons-path=PATH,...] server: error: unrecognized parameters: db init scratch
```

Odoo read `db init scratch` as stray server arguments, because with `-c` in front it
never recognised `db` as a command at all. The `ocdb` alias puts the flag in the right
place once, so if you set it up, you never think about it again.

### Making an alias permanent (entirely optional)

Typing `alias oc=...` at a prompt only lasts as long as that terminal window. Open a new
one and it is gone:

```console
$ alias oc
bash: alias: oc: not found
```

To keep it, put the same two lines in the file your shell reads when it starts. Which
file depends on your shell, not on your operating system, so check which shell you are
in first:

```console
$ echo $SHELL
/usr/bin/zsh
```

That machine runs zsh, so its owner wants the `zsh` row below. Yours will very likely
print a path ending in `bash` instead. Read the last word of the path, not the whole
thing:

| Your shell | File to add them to | Who has this by default |
|---|---|---|
| `bash` | `~/.bashrc` | most Linux (Ubuntu, Debian, Fedora), WSL2, Git Bash |
| `zsh` | `~/.zshrc` | macOS since Catalina, and plenty of Linux users by choice |
| `fish` | `~/.config/fish/config.fish` | only if you installed it deliberately |

On Windows you are already in one of those, because chapter 5 has you running commands
from WSL2 or Git Bash rather than PowerShell. Both are `bash`, so use the first row.

PowerShell is a different story. `Set-Alias` there cannot carry arguments, so an `oc`
that includes `-c /etc/odoo/odoo.conf` has to be written as a function instead. That is a
detour the tutorial does not need you to take.

Append and reload, in one go (bash shown; swap the filename for your shell):

```console
$ cat >> ~/.bashrc <<'EOF'
alias oc='docker compose exec odoo odoo -c /etc/odoo/odoo.conf'
alias ocdb='docker compose exec odoo odoo db -c /etc/odoo/odoo.conf'
EOF
$ source ~/.bashrc
```

`source` re-reads the file in the shell you already have open, so you do not have to
close it. Every terminal you open from now on gets them for free. (fish is the exception
to the syntax above: it spells aliases differently and has its own way of persisting
them, so check `help alias` there rather than copying the bash form.)

<Callout type="info" title="You can skip all of this">
  Aliases are a convenience for *your* terminal, nothing more. **This tutorial always
  spells out the full command**, in every chapter to the end, so nothing later depends on
  you setting these up. Use them, use the long form, or invent your own names: every
  command in the book stays copy-paste safe either way.

  The one thing worth taking from this section is *why there are two of them*. That `-c`
  placement rule bites whether or not you alias anything.
</Callout>

Run `docker compose exec odoo odoo help` once to see everything (`scaffold`,
`populate`, `neutralize`, `cloc`...). Today we need three: the **server** (the default
command), **`db`**, and **`shell`**.

### Server flags that matter

You'll rarely start the server by hand (Compose does it), but these flags are the
vocabulary of every Odoo conversation, and you *will* type them constantly from
chapter 8 on, mostly in module install/upgrade runs:

| Flag | Meaning |
|---|---|
| `-d tutorial` | act on this database |
| `-i librefleet` | **install** this module (comma-separated list allowed) |
| `-u librefleet` | **upgrade** this module: reload its XML/data into the database |
| `--stop-after-init` | do the install/upgrade, then exit instead of serving |
| `--addons-path=...` | where to find modules (ours is in `odoo.conf`) |
| `--dev=all` | developer features, see below |
| `--test-enable`, `--test-tags` | run tests, the subject of chapter 38 |

The pair to burn in now: **`-i` installs, `-u` upgrades.**

Python code changes are picked up by a restart (or auto-reload). But XML and data files
live *in the database* (chapter 3), and only an upgrade reloads them. "I changed the view
and nothing happened" is the most common beginner complaint, and `-u` is almost always
the answer.

### What `--dev=all` gives you

Our `odoo.conf` sets `dev_mode = all`. Watch the spelling: the config-file key is
`dev_mode`, the CLI flag is `--dev`, and writing the flag's name in the file silently
disables the whole thing rather than complaining. On Odoo 19, `all` expands to four
features:

<CardGrid cols={2}>
  <Card tone="sage" title="reload">
    The server restarts itself when Python source changes.
  </Card>
  <Card tone="sand" title="xml">
    View architectures are read directly from your XML files instead of the database,
    papering over many (not all) `-u` cases during development.
  </Card>
  <Card tone="violet" title="qweb">
    Logs the compiled XML when a QWeb template breaks.
  </Card>
  <Card tone="plain" title="access">
    Logs the full traceback of access errors, which will save you in chapter 10.
  </Card>
</CardGrid>

(A fifth, `werkzeug`, can be enabled by name: an interactive HTML debugger on request
errors.)

<Callout type="warn" title="Gotcha">
  `dev` mode is why our workflow feels magic, and it is strictly a development
  setting. It must never reach production; the werkzeug debugger alone is a remote
  code execution hole.
</Callout>

Now put both halves together, because the question you will actually ask twenty times a
day is not "what does `-u` mean" but "I just changed a file, do I need to do anything?"

| What you changed | What makes it take effect | What dev mode does about it |
|---|---|---|
| Python code (a model, a method) | a server restart | `reload` restarts for you, so usually nothing |
| A view's XML architecture | `-u librefleet` | `xml` reads it from your file, covering many cases but not all |
| Any other XML or data file | `-u librefleet` | nothing: `xml` covers view architectures only |

"View architecture" in the second row is wider than it sounds: QWeb templates are stored
as views too, so the reports of chapter 36 and the portal pages of chapter 37 fall in that
row as well, not the third. (`xml` also switches off a few internal caches, which is why
it can feel faster in general, but that has nothing to do with picking up your file
changes.)

The third row is the one that bites, because it looks like the second. Dev mode makes
view edits feel instant, which quietly teaches you that XML is live. Then a data file
changes and the lesson turns out to have been wrong.

So when something you edited is not showing up and you cannot immediately say which row
you are in, just run the upgrade. Being in the first row and upgrading anyway costs a few
seconds. Being in the third row and not upgrading costs you the afternoon.

### Reading the log

The log is your primary debugging instrument, so learn its grammar. A real line from
this environment:

```text
2026-08-09 12:43:29,362 1 INFO tutorial werkzeug: 172.23.0.1 - - [09/Aug/2026 12:43:29] "POST /xmlrpc/2/object#res.partner.search HTTP/1.1" 200 - 20 0.016 0.266
```

Left to right: timestamp, process id, **level**, **database name** (`?` when no
database is bound yet, `None` for calls like `xmlrpc/2/common` that authenticate before
picking one), **logger name**, message.

The bracketed `[09/Aug/2026 12:43:29]` inside the message is werkzeug's own request
timestamp, not Odoo's. It duplicates the leading one, so ignore it.

Habits that pay off:

- Follow it live while you click around: `docker compose logs -f odoo`.
- Python tracebacks read **bottom-up**: the last line is the actual error, the lines
  above tell you how it got there. The frames that mention `/mnt/extra-addons` are
  *your* code.
- `WARNING` lines are not decoration. Odoo warns about real problems (missing access
  rules, deprecated APIs) that will bite later. Read them.
- **One recurring exception:** `missing --http-interface/http_interface, using
  0.0.0.0 by default...` prints on every `odoo` command this tutorial's Docker setup
  runs, starting now and continuing through the rest of the tutorial. It is
  `odoo.conf` being verbose about a network-binding default, unrelated to whatever
  chapter you're actually working through. Every other WARNING is worth reading;
  this specific one is safe to skip.

### When the log isn't enough: pdb

The log tells you what happened. Sometimes you need to stop time and look around
instead, and Python ships the tool for that: <Term k="pdb">`pdb`</Term>, the interactive
debugger. Two ways in, and the second is the one that feels like a superpower.

**In your own code**, call the `breakpoint()` builtin. Execution stops on that line and
hands you a prompt with every local variable in scope:

```python
def owner_count(env):
    partners = env["res.partner"].search([])
    breakpoint()
    return len(partners)
```

**In code you don't want to edit**, which mostly means core, use `pdb.runcall`. It calls
the function for you and stops on its first line, so you can read core's own source
without touching a file you'd only have to revert:

```python
>>> import pdb
>>> pdb.runcall(env["res.partner"].search, [("name", "like", "Ada")])
```

Either way you land at a `(Pdb)` prompt, and these eight commands cover almost everything:

| Command | What it does |
|---|---|
| `l` | list source around the current line |
| `p expr` / `pp expr` | print (or pretty-print) any Python expression |
| `w` | where am I: the call stack, current frame marked `>` |
| `n` | next line, stepping *over* calls |
| `s` | step *into* the call on this line |
| `c` | continue until the next breakpoint or the end |
| `b file:line` | set another breakpoint |
| `q` | quit the debugger |

The prompt is a full Python REPL, so `p` takes any expression: `p self._name`,
`p domain`, `pp self.env.context`. That is the real reason pdb beats adding print
statements, because you decide what to look at *after* you have stopped.

<Callout type="warn" title="pdb needs a terminal, and one flag takes it away">
  pdb reads its commands from standard input, so it only works where you have a real
  terminal. `docker compose exec` allocates one **by default**, which is why the shell
  commands in this book drop you into a working prompt with no extra flags.

  The flag that breaks it is `-T` (`--no-tty`), which this book uses when *piping* a
  script in. Add `-T` and pdb has nothing to read from: it gives up immediately with
  `bdb.BdbQuit` and takes your script down with it.

  The same reasoning explains why you cannot put `breakpoint()` in a model method and
  catch it from a browser click. The server process inside the container has no terminal
  attached, so the request dies instead of pausing. Call the method from `odoo shell`
  instead, which is what the hands-on does.
</Callout>

`debugpy`, which lets an editor attach to a running server over a socket and is the
answer when you truly must debug a live request, is not in the `odoo:19` image. Installing
it is a legitimate step on a real project; this book stays with `pdb` because it is always
already there.

### The database lifecycle, without the browser

Chapter 5 used the database-manager screen. The CLI equivalent is the `odoo db`
command, and it's better: scriptable, and **filestore-aware** (dump, duplicate and
drop also carry the attachments, which a naive `pg_dump` does not). Real session:

```console
$ ocdb init --with-demo scratch     # create + initialize, demo data included
$ ocdb duplicate scratch scratch2   # instant copy, filestore included
$ ocdb drop scratch2
$ ocdb dump tutorial /tmp/tutorial.zip   # backup: SQL dump + filestore in one zip
```

`init` replaces the create screen (note the explicit `--with-demo`; the CLI default
is no demo). `duplicate` is the underrated one: copy your database before a risky
experiment, throw the copy away after.

For looking *inside* a database, `psql` is the tool (chapter 9 leans on it hard):

```console
$ docker compose exec db psql -U odoo -d tutorial
tutorial=# \dt res_*          -- list tables matching a pattern
tutorial=# \d res_partner     -- describe a table: columns, types, indexes
tutorial=# select id, name, email from res_partner limit 5;
```

### The Odoo shell

<Term k="odoo shell">`odoo shell`</Term> opens a Python REPL with a fully loaded environment: the <Term k="env (environment)">`env`</Term> object
gives you every model, exactly like the code you'll write from chapter 9. It is the
single best tool for experimenting with the ORM.

```console
$ docker compose exec odoo odoo shell -c /etc/odoo/odoo.conf -d tutorial --no-http
>>> env["res.users"].search([]).mapped("login")
['admin']
>>> env.cr.dbname
'tutorial'
```

Two things to know before the hands-on:

- **`--no-http`** stops the shell from trying to serve on port 8069, which your real
  server already occupies.
- **The shell does not auto-commit.** It runs in one transaction, like a request
  (chapter 3), but nothing ever triggers the commit. Write without
  `env.cr.commit()` and your changes silently vanish when you quit. This is the
  gotcha the Verify step below is built around.

## Gotchas

- **Shell writes need `env.cr.commit()`.** Worth repeating, because next time it
  happens it will be a "fix" you ran on a real database that silently didn't stick.
- **`-u` is not optional after XML changes.** `dev=xml` covers view *rendering* from
  files, but records like menus, actions and security rules still only update on
  upgrade. When in doubt, `-u`.
- **Don't run a second server on a busy port.** Anything that loads the registry
  (`shell`, `-i`/`-u` runs) is fine alongside the running server, but only with
  `--no-http` or `--stop-after-init` keeping it off port 8069.
- **`db drop` takes one database at a time.** `ocdb drop scratch scratch2` is an
  error; run it twice instead.
- **The log level is configurable, not fixed.** `--log-level=debug_sql` (or
  `log_level` in the config) shows every SQL statement, which chapter 50 uses to hunt
  performance problems.
- **A committed `breakpoint()` is an outage.** In the container the server has no
  terminal, so pdb cannot prompt anyone: the call raises `bdb.BdbQuit` and takes the
  request with it. It will pass review looking like one harmless line. If you need a
  safety net, `PYTHONBREAKPOINT=0` in the environment turns every `breakpoint()` into a
  no-op without editing code, which is worth knowing for the day you inherit somebody
  else's.
- **`exec -T` and pdb are mutually exclusive.** `-T` disables the pseudo-terminal, which
  is exactly what you want when piping a script in and exactly what pdb cannot survive.
  If a breakpoint seems to be ignored in a scripted run, check for `-T` before you
  suspect the breakpoint.
