## Why this matters

You already know git. What's new is how the Odoo world uses it: one convention
(a branch per Odoo version) shapes every repository you'll touch, and integrator
projects are mostly *assemblies* of other people's modules, which makes dependency
pinning a first-class concern. Get this mental model now, and OCA repos, client
projects, and your own tutorial work all look organized instead of arbitrary.

## Concepts

### Branch-per-version, everywhere

An Odoo module is written *for* one Odoo version (chapter 1). Git encodes that as a
branch named after the version, and the convention is universal:

- `odoo/odoo` has branches `17.0`, `18.0`, `19.0`, plus `master` where the next
  release is developed.
- Every OCA repo has the same branches. The same module exists on several of them,
  and moving it forward is an explicit **migration** commit (`[MIG]`).
- Client projects follow suit: when the client upgrades from 18 to 19, the project
  repo grows a `19.0` branch and the porting work happens there.

Two rules fall out of this: **never target `master`** with a fix (that's next year's
Odoo), and **a branch name is a compatibility statement**, so code on `19.0` must run
on Odoo 19, full stop.

Here's the model measured for real. The `OCA/server-tools` repo, same repo, two
branches:

```console
$ git clone --depth 1 -b 19.0 https://github.com/OCA/server-tools.git st-19
$ git clone --depth 1 -b 16.0 https://github.com/OCA/server-tools.git st-16
$ ls st-19 | wc -l
34
$ ls st-16 | wc -l
73
```

Same repository: 73 modules on the mature 16.0 branch, 34 on the young 19.0 branch.
(A few of those entries are `README.md`, `setup` and similar non-module files on both
branches, so read the counts as roughly-how-many. The gap is the point either way.)

That gap is the migration queue: modules nobody has needed, or volunteered for, on 19
yet. When a client project needs one of them, an integrator developer does the `[MIG]`.
That developer will regularly be you.

### How commit messages look

Odoo and OCA share a commit convention you'll adopt from chapter 43 on, but should start
reading now. Real messages from `server-tools` 19.0:

```text
5dcfe30 [FIX] database_cleanup: restrict cleanup tools to settings users
63d1654 [MIG] base_search_fuzzy: Migration to 19.0
f0a3744 [IMP] module_auto_update: confirm message before updating
```

The shape is <Term k="commit tags">`[TAG] module_name: what and why`</Term>. Common tags: `[FIX]` bugfix, `[IMP]`
improvement, `[ADD]` new module/feature, `[MIG]` migration to a version, `[REF]`
refactor. A `git log --oneline` on any OCA module reads like a changelog, which is
the point.

### What a client project repo looks like

An integrator's project repo rarely contains much code. It's an assembly manifest:

```text
client-project/            # branch: 19.0
├── addons/                # the project's own custom modules (a handful)
├── external-src/          # OCA & third-party repos, pinned (see below)
├── odoo/                  # Odoo itself: a pinned checkout, or nothing if the
│                          #   Docker image provides it (our setup)
├── docker-compose.yml / Dockerfile
└── requirements.txt / repos.yml / .gitmodules   # the pinning mechanism
```

The custom `addons/` part stays small on healthy projects because the first question
is always "does an OCA module already do this?" (chapter 2). The bulk of the
assembly is *other people's modules at exact versions*.

### Pinning: never deploy a moving target

`19.0` branches move daily. If your production image checks out "whatever
`OCA/server-tools` 19.0 is today", every deploy is a surprise. So professional
projects <Term k="pinning">pin</Term>, using one of three mechanisms:

<CardGrid cols={3}>
  <Card tone="sage" icon={<Icon name="branch" />} title="git submodules">
    A SHA per external repo, recorded in `.gitmodules`. Native git, clunky UX.
  </Card>
  <Card tone="sand" icon={<Icon name="layers" />} title="git-aggregator">
    A `repos.yml` listing repos and SHAs/PRs to merge. OCA tooling, powerful: can
    **stack unmerged PRs**.
  </Card>
  <Card tone="violet" icon={<Icon name="module" />} title="pip">
    OCA publishes every module as `odoo-addon-<name>`; pin it in `requirements.txt`.
    Plain Python packaging.
  </Card>
</CardGrid>

<Callout type="info" title="In the field">
  [git-aggregator](https://github.com/acsone/git-aggregator) is widespread among OCA
  contributors and integrators (including Camptocamp). One YAML file describes every
  external repo, the commit to pin, and even pending PRs to merge into your build.

  That last part is how you ship a fix the day you write it, instead of waiting out the
  OCA review cycle. Ask your team which mechanism your projects use; the concept
  transfers.
</Callout>

Whatever the tool, the invariant is the same: **a production build is reproducible
from a commit of the project repo alone.** If `git checkout` + build can produce two
different deployments on two days, the project is broken.

### Where your tutorial work fits

Look at that `client-project/` layout again, then look at the repository you created in
chapter 4. They are the same shape: a compose file, a config file, and an `addons/`
holding the project's own modules. Yours is just smaller, and from chapter 8 LibreFleet
grows inside it.

Which means the git side of your workspace is already right, and worth understanding
rather than taking on trust:

- **It is your repository, not a copy of someone else's.** Using a template rather than
  forking means there is no upstream tying you to the starter. When you show this to a
  colleague (or an interviewer) it is a clean Odoo module repo with your history on it,
  which is also exactly how a custom module arrives on a client engagement.
- From chapter 8 on, **commit after every chapter** using the OCA message style
  (`[ADD] librefleet: vehicle model`). By chapter 43 the convention will be muscle
  memory, and your git history becomes your own set of checkpoints.

You never clone this tutorial's repository at all. When you want to compare your work
against a chapter's reference snapshot, chapter 8 shows you how to pull down just that one
snapshot, and nothing else.

<Callout type="info" title="Forking comes later, and for a real reason">
  Forking is the mechanism for contributing to *someone else's* repository, which is
  exactly what you'll do to OCA in chapter 45: fork, branch off the version branch, PR.
  It is the wrong tool for holding your own project, which is why the starter is a
  template instead.
</Callout>

## Hands-on

<Steps>

<Step>
### Confirm the workspace is really yours

```console
$ git remote -v
origin  https://github.com/<you>/librefleet.git (fetch)
origin  https://github.com/<you>/librefleet.git (push)
```

One `origin`, pointing at **your** account. That is what "Use this template" bought you:
no `upstream`, nothing to keep in sync, no chance of accidentally opening a pull request
against the tutorial.

If instead you see `ronitjadhav/odoolings-starter` there, you cloned the starter
rather than templating it. Create an empty repository on your own GitHub and re-point:

```console
$ git remote set-url origin https://github.com/<you>/librefleet.git
$ git push -u origin main
```

Now look at what the starter already committed for you, because each line is a decision
you would otherwise have had to make:

```console
$ git log --oneline
$ cat .gitignore
__pycache__/
*.pyc

# Reference snapshots fetched from the tutorial: our code, not yours.
.checkpoints/

# odoolings snapshot/diff scratch state (chapter 21 on), never worth committing.
.odoolings-snapshot.json
```

`.checkpoints/` is where chapter 8 drops reference snapshots. They are this tutorial's
code, so they stay out of your history. `.odoolings-snapshot.json` is scratch state the
checker writes starting in chapter 21, also not yours to commit. And `addons/` contains
a single zero-byte `.gitkeep`, because git cannot track an empty directory but Docker
needs the directory to exist before the first `docker compose up` (chapter 5's gotcha
explains what happens otherwise).
</Step>

<Step>
### Measure the migration queue yourself

Run the two shallow clones from the Concepts section and count modules per branch.
Then pick one module that exists on `16.0` but not on `19.0`, and check its
`__manifest__.py` on the old branch: would *you* need it on a project?
</Step>

<Step>
### Read a module's history like a changelog

```console
$ cd st-19
$ git log --oneline -15 -- database_cleanup
```

Identify each tag you see and notice how much you understand about the module without
opening a single source file. That's what disciplined commit messages buy.
</Step>

<Step>
### Practice the message style on yourself

Commit something harmless in your own repo (add a `.gitignore` entry, drop a
`notes.md`) with a properly shaped message, e.g.
`[IMP] docs: add scratch notes directory to gitignore`. Shape, module, what, why.
</Step>

</Steps>

## Verify

`git remote -v` shows a single `origin` pointing at **your** GitHub, and `git push`
works. You can say out loud why `OCA/server-tools` has fewer modules on `19.0` than
on `16.0`, and what `[MIG]` means. No odoolings checks this chapter; git lives
outside the Odoo server.

## Gotchas

- **`master` is a trap.** On `odoo/odoo` and OCA repos it's the unreleased next
  version. Code examples found on `master` may not work on 19, and PRs against it
  will be closed with a polite "wrong branch".
- **Branch names are floats, sort of.** `19.0` not `19`, `16.0` not `v16`. Tooling
  (and humans) rely on the exact `XY.0` form.
- **Submodule/aggregator checkouts are detached HEADs.** That's normal: pins point at
  SHAs, not branches. Don't "fix" it by checking out the branch inside a pinned repo.
- **One module, one concern, one history.** Resist the "misc" module that accretes
  everything; OCA repos are readable because each module's log tells one story.
  Chapter 8 starts LibreFleet with that discipline.
