---
title: Glossary
description: Every piece of Odoo jargon, defined the day a chapter first uses it.
---

**AbstractModel**: a model with no table of its own (`models.AbstractModel`),
meant to be mixed into other models via the list form of `_inherit`, never
instantiated directly. `mail.thread` and `mail.activity.mixin` (chapter 33) are
both `AbstractModel`.

**account.move / account.move.line**: one accounting document and its debit/credit
lines. **The same model holds invoices, bills, credit notes and plain journal entries**,
told apart by `move_type`; there is no `account.invoice` model. Every move balances, and
Odoo refuses to post one that does not (chapter 27).

**access rights (ACL)**: `ir.model.access` records, conventionally loaded from
`security/ir.model.access.csv`, granting a group read/write/create/unlink on one
model. Additive across groups (rights union, never subtract) and model-wide; see
*record rule* for per-record filtering.

**activity (`mail.activity`)**: a scheduled to-do attached to one record: a type, a
deadline, an assignee (`user_id`), a note. Lives in the chatter but is its own model,
separate from `mail.message`. `activity_schedule()` creates one; `action_feedback()`
marks it done and logs the feedback as a chatter note. A model needs
`mail.activity.mixin` to have activities at all, and `mail.thread` too if
`action_feedback()` will ever run on it, since the feedback note is posted through
`message_post_with_source()` (chapter 35).

**active_test**: a context flag. Default searches silently add `active = True`;
`with_context(active_test=False)` switches that off so archived records show up too.

**addon**: see *module*. The two words are used interchangeably; `--addons-path` is
the directory list Odoo scans for them.

**addons path**: the ordered list of directories Odoo searches for modules, set with
`addons_path` in `odoo.conf` or `--addons-path` on the command line. Odoo scans each
entry **exactly one level deep**: an immediate child holding a `__manifest__.py` is a
module, and it does not recurse. Since an OCA repository keeps its modules at the
repository root, **each repository is its own entry** (chapter 49), which is why real
deployments have a long comma-separated list. The server logs the resolved list as
`addons paths: [...]` at startup, including the image's own built-in directories.

**auto_install**: a manifest flag meaning "install me automatically as soon as every
module I depend on is installed". Nobody asks for these; they arrive, which is how
*bridge modules* ship. Two consequences worth knowing: installing one module can install
others that were waiting for it, possibly from repositories you cloned for something
else, and Apps hides them behind its default **Apps** facet, since bridges are not flagged
as applications (chapter 50).

**arch (view architecture)**: the XML document stored in an `ir.ui.view` record's
`arch` field describing how to render a model (`<list>`, `<form>`, ...). Validated
against the model at load time: a field typo in an arch fails the upgrade.

**archiving**: setting `active = False` on a record. Archived records keep their data
and relations but are hidden from `search()` unless the `active_test=False` context
asks for them. Odoo's "soft delete" (chapter 9).

**assets bundle**: a named list of JS/CSS/XML files, declared under the manifest's
top-level `"assets"` key (a **sibling** of `"data"`, never inside it), concatenated and
served as one file. The bundle name decides where code loads: `web.assets_backend` for
the web client, `web.assets_frontend` for public pages. You declare into
`web.assets_backend` but the browser downloads `web.assets_web`, which includes it.
Bundles rebuild when the web client requests an uncached hash, **not** on module
upgrade (chapter 39).

**automated action (`base.automation`)**: a rule that runs a server action when a
trigger fires: on create, on write, on a field reaching a value, on a date field
arriving. Lives in its own module (`base_automation`, not `base`). Under the hood it
*is* the server action, with a `base_automation_id` linking back, the same
share-a-row relationship a cron has with the action it schedules (chapter 35).

**automatic fields**: the columns the ORM maintains on every model without being
asked: `id`, `create_uid`, `create_date`, `write_uid`, `write_date`, plus the
computed (never stored) `display_name`.

**AVCO (average cost)**: a costing method that keeps one average per product: (value before + value received) ÷ quantity at every receipt, and deliveries leave at that average. Switching a product to AVCO recomputes the average over its whole history (Inventory chapter 12).

**backend adapter**: in OCA's connector, the component that speaks one external
system's protocol. Per the connector docs it "has a common interface to speak with the
backend" and "translates the basic orders (search, read, write)" into that system's API.
One adapter per backend, all answering the same method names (appendix on components).

**backorder**: the transfer Odoo creates for the part of a demand that was not shipped
or received when a transfer is validated short. Its `backorder_id` points at the
original; the original's demand is rewritten to what actually moved. Whether Odoo asks,
always creates one or never does is the operation type's **Create Backorder** setting.

**barcode nomenclature (`barcode.nomenclature`)**: the list of rules that says what a
scanned code means. Each rule has a Type (product, weighed product, location, package,
lot...), an encoding and a pattern; Odoo reads the rules in order and the first pattern
matching the start of the code wins. The **Default Nomenclature** knows `21` weights, `414`
locations, `PACK` packages, `10` lots and everything else as products; the **Default GS1
Nomenclature** reads GS1 application identifiers.

**batch transfer (`stock.picking.batch`)**: several transfers of one operation type
grouped into one job and validated together, from the Batch, Wave & Cluster Transfers
setting (`stock_picking_batch`). Made by hand (Actions → Add to batch) or automatically
by the operation type's **Automatic Batches**, which needs at least one grouping
(contact, destination country, source or destination location).

**bridge module**: a small module whose only job is to connect two other modules that
do not know about each other, depending on both and holding just the glue. Usually
`auto_install`, so it appears by itself once both sides are installed;
`sale_order_secondary_unit` bridges `product_secondary_unit` and `sale`. The same shape,
written deliberately for one project and *not* auto-installed, is how you change an OCA
module's behaviour without editing it (chapter 51).

**button box**: the `<div name="button_box">` at the top of a form sheet holding
smart buttons. Extensions target it by name to add their own buttons.

**bill of materials (`mrp.bom`)**: the recipe for a product: a `product_qty` it
yields, `bom_line_ids` for its components, and optional `operation_ids` against work
centers. Operations are optional; several real BoMs have none (chapter 26).

**calendar view**: a view type placing records on a date grid via `date_start` /
`date_stop`, with `color` bucketing events by another field's value.

**chart of accounts (`account.account`)**: the list of buckets value can sit in. Each
account carries an `account_type` (`asset_receivable`, `expense`, ...) which is what
reports group by, so code should branch on the type rather than on account codes. In
Odoo 19 `code` itself is computed, unstored and **company-dependent** (chapter 27).

**chatter**: the message/activity feed at the bottom (or side) of most form views:
emails, notes, followers, scheduled activities. Models opt in via `mail.thread` and
`mail.activity.mixin`, and render it with the single `<chatter/>` view tag
(chapter 33). Adds no columns to the model's own table; the thread lives in
`mail.message`, keyed generically by model and record id.

**CLA**: Contributor License Agreement. The OCA requires every contributor to sign one
(a one-time, per-person process via a bot check on your first PR) before a merge,
granting the OCA the rights it needs to keep a module's license enforceable and its
authorship clear (chapter 45).

**classic extension**: `_inherit` with no `_name`. The class *is* the existing
model: fields land on the same model and the same table. The mechanism behind
almost all real extension work.

**client action (`ir.actions.client`)**: an action that hands a whole screen to an OWL
component instead of to the view engine. The record's `tag` is an unvalidated string
looked up in the `actions` registry, where the JavaScript registered a component under
the same name; a mismatch throws `KeyNotFoundError` in the browser console and nothing
anywhere else. The component receives the action record as a prop, so it must spread
`standardActionServiceProps` (chapter 41).

**closing entry (stock)**: the journal entry that brings the stock valuation account to the stock's value under periodic valuation, against the stock variation account. Made from the Inventory Valuation report (`/odoo/stock-valuation-closing`, Generate Entry) or daily or monthly by a scheduled action (Inventory chapter 12).

**collection (OCA component)**: the model components register against, and the
entry-point into the component system through its `work_on()` context manager. In the
connector a collection is the backend. Unlike a component it *is* an ordinary model, so it
has a table and needs access rights (appendix on components).

**cron (scheduled action, `ir.cron`)**: a server action plus a schedule. `ir.cron`
`_inherits` `ir.actions.server` through `ir_actions_server_id`, sharing that record's
row rather than copying it, so a cron and the action it runs are, structurally, the
same object viewed two ways. "Run Manually" in Settings > Technical > Scheduled
Actions calls `method_direct_trigger()`, useful for testing without waiting for the
schedule (chapter 35).

**COGS (cost of goods sold)**: the expense recognised when goods leave the company. In
Odoo 19 it is produced by *validating the delivery*, not by invoicing: the stock asset is
credited and the account named on the Customers location is debited (chapter 30).

**costing method (`property_cost_method`)**: how a unit is priced, set on the product
category. `standard` uses a cost you type, `fifo` consumes the oldest receipt first, and
`average` (AVCO) keeps a running average recomputed on each receipt. Independent of
whether the books hear about it, which is *inventory valuation* (chapter 30).

**component (OCA)**: a class registered by `_usage`, `_collection` and `_apply_on` and
resolved at runtime, from the OCA `component` module (written by Camptocamp). Not a model:
no table, no ACL, nothing in `ir.model`. It exists to do the one thing `_inherit` cannot,
namely let several implementations of the same behaviour coexist and be selected per
backend (appendix on components).

**command list (x2many commands)**: the tuple language for writing relational
fields: `(0, 0, {vals})` create, `(4, id)` link, `(3, id)` unlink, `(2, id)`
delete, `(6, 0, [ids])` replace all. Spelled `Command.create/link/set/...` since
Odoo 15; the tuples remain everywhere in existing code.

**commit tags**: the `[TAG] module: description` convention Odoo and the OCA use for
commit messages: `[FIX]` bugfix, `[IMP]` improvement, `[ADD]` new feature/module,
`[MIG]` migration to a version, `[REF]` refactor.

**compute_sudo**: whether a computed field recomputes as superuser (bypassing record
rules and `groups=`) or as whoever triggered it. Defaults to whatever `store` is on
that field, `True` for stored fields, `False` for non-stored ones, so mixing stored
and non-stored fields under one compute method silently mixes privilege levels too
(chapter 20).

**computed field**: a field filled by a method instead of the user, with
`@api.depends` declaring exactly which fields the value derives from (the ORM's
recompute triggers). Non-stored by default (no column, computed on read);
`store=True` adds a real column recomputed when dependencies change.

**controller**: a Python class decorated `@http.route` per method, the raw HTTP
door into Odoo, separate from the ORM-over-RPC traffic the web client normally uses.
`type` picks the request/response shape (`"http"` for pages, `"jsonrpc"` for
programmatic JSON calls, `type="json"` is a deprecated alias since 19.0), `auth`
picks who can reach it at all (`"public"`, `"user"`, `"none"`), checked before the
method runs (chapter 37).

**consignment (owner on quants)**: stock on your shelf that belongs to someone else,
usually a vendor paid only for what you use. The **Consignment** setting
(`stock.group_tracking_owner`) adds **Assign Owner** to receipts; the owner then stays on
the quants (`owner_id`) through every move. Owned stock counts in On Hand and is reserved
for deliveries like your own, but has no value in your stock valuation.

**constraint (Python)**: a validation method decorated `@api.constrains(*fields)`
that raises `ValidationError` when a rule is broken. Runs in the ORM on every write
path (form, import, RPC, shell, code) but never on raw SQL, and only re-runs when a
field it lists changes. Use it for rules that need judgment or other records
(chapter 14).

**constraint (SQL)**: a database-level rule (`UNIQUE`, `CHECK`, foreign key) enforced
by Postgres itself, so nothing bypasses it, not even raw SQL. Declared on Odoo 19 with
`models.Constraint` (see that entry). Limited to what SQL can express (chapter 14).

**container (package)**: a package holding other packages, its `parent_package_id`
seen from the inside. Two cartons on a pallet have the pallet as container, and names show
the nesting as `PAL0000001 > CTN0000001`. A container moves whole when all its packages do,
unless its type is reusable.

**context**: the read-only dict of settings every ORM call carries (`lang`, `tz`,
`uid`, behavior flags like `active_test`). Never mutated in place; `with_context()`
derives a new recordset with an extended copy.

**CSV data file**: a data file whose name IS the target model's technical name
(`ir.model.access.csv`), optionally with a `-suffix` before `.csv`
(`account.account-kw.csv` in core). Relational columns end in `:id` and hold an
xml id. Always uniform, one row per record, and (chapter 34) always noupdate when
listed under `demo`, never able to opt out of it when listed under `data`, since
CSV has no equivalent of XML's `<data noupdate="...">` wrapper.

**debit / credit**: the two sides of every accounting entry. A debit increases an asset
or expense and decreases a liability, equity or income; a credit does the reverse. The
totals of the two sides are equal by definition, which is what "double-entry" means
(chapter 27).

**decoration-***: list (and badge) attributes carrying an expression over the view's
loaded fields; matching rows render in the semantic color (muted, info, success,
warning, danger) or style (bf, it).

**default value**: a field's starting value on a new record, set with `default=`.
Static (`default="draft"`) or a callable (`default=lambda self: ...`) evaluated once
per record for dynamic values like today's date or the next sequence number. Fires on
every creation path (chapter 14).

**delegation (`_inherits`)**: note the `s`. Composition with automatic
forwarding: the child holds a required many2one to the parent, and the parent's
fields become non-stored related fields on the child. Two tables, one logical
record. Core uses it for `res.users` to `res.partner`.

**delivery method (`delivery.carrier`)**: a way to ship that has a price, added by **Delivery Methods** (`stock_delivery`). Fixed Price or Based on Rules in Community, a carrier connector in Enterprise. Its delivery product becomes the shipping line of the sales order, and the method travels to the transfers as their Carrier (Inventory chapter 11).

**demo data**: fictional records (customers, products, orders) listed under a
module's `demo` manifest key, for training and testing, never required config.
Loads only when a module is *installed* with demo explicitly requested
(`--with-demo`, Odoo 19's default is *without*); a later `-u` upgrade only reloads
it if that module's very first install already had it, since Postgres remembers
per module in `ir_module_module.demo`. See *master data* for the config a module
does need. Chapter 34 goes deeper, including why an upgrade alone will not add it
to a database that never had it.

**depends**: the manifest list of modules yours builds on. It sets load order and is
what makes extending their models legal: extend a model whose module is not in
`depends` and the registry refuses to load at all. Transitive, so one entry can install
several modules.

**developer mode**: a per-session backend mode (`?debug=1` or Settings → General
Settings) that reveals technical field tooltips and the Settings → Technical menu.
`debug=assets` additionally serves unminified JS/CSS.

**development_status**: a manifest key OCA modules use to declare maturity: `Alpha`,
`Beta` (the silent default when the key is omitted), `Production/Stable`, or `Mature`.
Shows as a colored badge on the module's generated README (chapter 43); judge a
module's fitness for production by this badge before its star count.

**display_name**: the one-line string Odoo uses to present a record (breadcrumbs,
dropdowns). Computed on demand from the field `_rec_name` points at, which defaults
to a field literally named `name`; with neither, you get the `"model,id"` fallback.

**domain**: the list-of-tuples filter language used by `search()`, record rules and
filters: `[("license_plate", "=", "ZH 468 202")]`. Conditions AND together by
default; `"|"` and `"&"` prefix operators change that. Domains can walk relations
with dots (`order_id.technician_ids`).

**dropshipping**: selling a product that the vendor ships straight to your customer. The **Dropship** route turns a confirmed sale into a purchase order whose Deliver To is the Dropship operation type, and one transfer moves the goods from Vendors to Customers without touching your stock (Inventory chapter 11).

**editable list**: a list view with `editable="top|bottom"`, letting users add and
edit rows inline instead of opening a form. The natural fit for flat config tables
(LibreFleet's service types).

**edition**: Community (open source, LGPL-3) or Enterprise (paid superset with extra
apps, hosted options and the upgrade service). This tutorial uses Community.

**env (environment)**: the object every piece of Odoo server code works through:
`env["res.partner"]` reaches a model, `env.cr` the database cursor, `env.user` the
current user. First met in `odoo shell` (chapter 6), studied properly in chapter 15.

**ERP**: Enterprise Resource Planning. One system, one database for a company's
operations (sales, stock, accounting...), so every department sees the same facts.

**expiration dates (`product_expiry`)**: the Expiration Dates setting. A product gets four
day counts (Expiration, days after receipt; Best Before, Removal and Alert, days before
expiration) and each lot received gets four dates from them. Past its removal date a lot
leaves Free to Use and is skipped by reservation, though it still counts as On Hand; past
its alert date it shows in the Expiration Alerts filter and the scheduler logs an *Alert
Date Reached* activity; validating a transfer with an expired lot asks for confirmation.

**extension view**: an `ir.ui.view` with `inherit_id` set (mode `extension`): a list
of patches (xpath or field locators plus a position) applied to its parent's arch at
request time. The parent record itself is never modified.

**extension hook**: a method core defines with an empty (or minimal) body purely so
other modules can override it and add behaviour. `sale.order._action_confirm` is the
clearest example: it holds only a docstring, and each installed bridge module
(`sale_stock`, `sale_purchase`, ...) overrides it to create its own document on
confirmation (chapter 22).

**FEFO (First Expiry First Out)**: the removal strategy that reserves the lot with the
earliest removal date first, then the earliest arrival. Set on a location (Removal
Strategy) or a product category; it comes with Expiration Dates.

**FIFO (costing)**: a costing method where each receipt keeps its own value and deliveries consume the oldest receipts first. What is left of each receipt is its `remaining_qty` and `remaining_value`. Not the same thing as the FIFO removal strategy, which decides which unit leaves the shelf (Inventory chapter 12).

**filestore**: the on-disk directory where Odoo stores attachments and uploaded files
(one subdirectory per database). Binary content lives here, not in PostgreSQL; in the
tutorial's Docker setup it sits in the `odoo-data` volume.

**filter (search view)**: a named, static domain toggle in a search view's arch.
Distinct from `ir.filters`, which stores a user's own saved searches.

**fiscal position (`account.fiscal.position`)**: the record answering "this customer is
not taxed like the others", resolved from the customer's country (or set by hand) as a
document is created. In Odoo 19 it no longer holds source/destination tax pairs: it lists
taxes, and each replacement tax names what it replaces in `original_tax_ids` (chapter 29).

**form view**: the one-record view type (`<form>` arch): a `<sheet>` canvas with
`<group>`s laying out fields. Opened from a list row when the action's `view_mode`
includes `form`.

**`_get_custom_move_fields()`**: the `stock.rule` hook listing which keys of a procurement's `values` a pull rule copies onto the move it creates. The way to carry your own field, such as a service order, onto stock moves (Inventory chapter 13).

**get_view**: the model method the web client calls to obtain the combined arch of a
view type; useful in the shell to see exactly what inheritance produced.

**golden rule (never modify core)**: you extend Odoo's own modules from yours, never by
editing their source. Editing core loses the change at the next upgrade, breaks other
modules extending the same model, and leaves an Odoo nobody else can reproduce.

**graph view**: a chart rendering of the same row/column/measure aggregation a
pivot view describes, as a bar, line or pie.

**group**: a `res.groups` record permissions are granted to (users are never granted
rights directly). Groups can imply other groups (`implied_ids`): members of the
implying group automatically hold everything the implied group has.

**group-by**: a `<filter>` inside a search view's `<group>` block whose `context`
sets `group_by`, delegating aggregation to a `read_group` call server-side.

**GS1**: the standards body behind EAN and GTIN product numbers and the barcodes that
chain **application identifiers**: `(01)` a product's GTIN, `(10)` a lot, `(17)` an expiry
date, `(30)` a quantity, `(00)` a shipping container's SSCC. Odoo reads them through the
Default GS1 Nomenclature and can print them on lot labels.

**HS code**: the Harmonized System number customs use to classify goods, kept on the product with its **Origin of Goods** (`hs_code`, `country_of_origin`). Carrier connectors print both on customs forms (Inventory chapter 11).

**inventory adjustment (counting)**: writing a **Counted** quantity on a quant in
Physical Inventory and applying it: Odoo moves the difference between the shelf and the
virtual **Inventory adjustment** location, which in Odoo 19 also receives scraps. A count
whose stock moved before it was applied is *outdated* and raises a conflict: Keep Counted
Quantity or Keep Difference.

**Inventory Frequency (`cyclic_inventory_frequency`)**: a location's cyclic count, in
days: its quants are scheduled for a count that many days after the **Last Inventory**,
or on the company's annual inventory day if that comes first.

**invoice policy (`invoice_policy`)**: the per-*product* setting deciding when a sales
order line becomes invoiceable: `order` (as soon as the order is confirmed) or
`delivery` (only once goods ship). It lives on the product, not the order, so one order
can mix both (chapter 22).

**invoice_status**: the billing state of a `sale.order` (`no`, `to invoice`,
`invoiced`, `upselling`), tracked independently of `state` because commercial and
billing progress move at different speeds.

**integrator / partner**: a company implementing Odoo for clients: configuration,
custom modules, migrations, support. Most Odoo developers work at one.

**inventory valuation (`property_valuation`)**: when stock movements reach the ledger,
set on the product category. `periodic` ("Periodic (at closing)") values every move but
posts no journal entry; `real_time` ("Perpetual (at invoicing)") posts one per valued
move. Odoo 18 stored `manual_periodic` and called them Manual/Automated. Switching is
never retroactive (chapter 30).

**is_storable ("Track Inventory")**: the boolean deciding whether Odoo counts a
product in stock. Contributed by the Inventory app, not by `product`, and in Odoo 19 it
replaces the old `type = 'product'` storable type (chapter 21).

**landed cost (`stock.landed.cost`)**: freight, customs or insurance added to the value of received goods, split over the products Equal, By Quantity, By Current Cost, By Weight or By Volume. FIFO and AVCO products only; it posts a journal entry only for perpetual ones (Inventory chapter 12).

**lead / opportunity**: the two values of `crm.lead.type`, not two models. Converting a
lead flips the field on the record that already existed, which is why the pipeline has
no `crm.opportunity` model and no second table (chapter 22).

**lead time (replenishment)**: how long a refill takes, added up from the route a
reordering rule would use: the vendor's lead time and the company's Days to Purchase when
it buys, the bill of materials' lead times when it manufactures, and any rule delay on
the way. Odoo adds 365 days when a buy rule finds no usable vendor, or a manufacture rule
no bill of materials. The Replenishment Information window shows the sum step by step.

**journal (`account.journal`)**: the book an accounting entry is written in (Sales,
Purchases, Bank, Miscellaneous), and the owner of its numbering sequence. The sequence is
asked for a number at **posting** time, not creation, which is why accounting numbering
has no gaps (chapter 27).

**kit (phantom bill of materials)**: a `mrp.bom` of type **Kit** (`phantom`). No
manufacturing order is ever made for it: when a transfer line for the kit product is
confirmed, Odoo replaces it with one line per component, each pointing at its BoM line
(`bom_line_id`), and the transfer flags `has_kits`. The kit product has no quant; its
on-hand quantity is computed from its components.

**kanban view**: the card-per-record, column-per-group view type (e.g. the CRM
pipeline grouped by stage). One of the standard view types you'll build in chapter 19.

**list view**: the rows-and-columns view type (`<list>` arch; `<tree>` before
Odoo 17, removed in 19). Each `<field>` in the arch is a column.

**location (`stock.location`)**: a place stock can be. Locations form a tree (`LFD` holds
`LFD/Stock`, which holds `LFD/Stock/Shelf A`), and the full path is the location's
*complete name*. The *Location Type* (`usage`) decides how Odoo treats it: Internal is a
real place where your quants live; Virtual groups other locations; Vendor, Customer,
Inventory Loss, Production and Transit are the "other side" of receipts, deliveries,
counts, manufacturing and inter-site moves. The Inventory deep dive opens with them.

**lock date**: a `res.company` date field (`fiscalyear_lock_date`, `tax_lock_date`,
`sale_lock_date`, `purchase_lock_date`, `hard_lock_date`) that blocks editing any
move dated on or before it. Each guards a different slice (sales, purchases,
everything); setting the broadest ones first checks that the period's bank
statement lines are actually reconciled, and refuses to lock a messy period
(chapter 27).

**lot / serial number (`stock.lot`)**: the record that names a batch (a lot, any
quantity) or a single unit (a serial number) of a tracked product. Quants are split per
lot, so the shelf says which lot is where. The lot form shows its on-hand quantity, its
expiry dates, and smart buttons to its sales, transfers, locations and Traceability
report. Numbers come from the product's own sequence (*Custom Lot/Serial*), from the
receipt's Generate or Import buttons, or are typed.

**lot valuation (Valuation by Lot/Serial)**: a product option that gives each lot or serial its own cost: receipts need a lot, deliveries leave at the lot's cost, and the product's value is the sum of its lots (Inventory chapter 12).

**manufacture steps (`manufacture_steps`)**: the warehouse's Manufacture choice: one
step (consume from Stock, deliver to Stock), two steps (a Pick Components transfer brings
parts to Pre-Production first) or three steps (and a Store Finished Product transfer
carries the product from Post-Production to Stock). Like the shipment steps, each extra
step is a location, an operation type and a rule in a generated route.

**manufacturing order (`mrp.production`)**: the document that executes a bill of
materials. Unlike every other transactional document in this part, it gets its sequence
number at *creation*, not confirmation. Confirming reserves the component and
finished-good moves; marking it done executes them (chapter 26).

**manifest**: `__manifest__.py`, the dict at a module's root declaring its name,
version, `depends`, data files, and license. Its presence is what makes a directory a
module.

**many2many**: the both-ways relation (`technician_ids` on orders, orders on
technicians) stored as an automatic table of id pairs in Postgres. Plural `_ids`
naming, like one2many.

**many2one**: *the* relation: an integer column holding another record's id, with a
real foreign key and an `ondelete` policy. Singular `_id` naming. One2many and
many2many are built on top of it.

**monkey patching**: replacing a method on a class at runtime rather than through
inheritance, keeping the original so the replacement can still call it
(`new.origin = getattr(cls, name); setattr(cls, name, new)`). OCA's `auditlog` audits
any model this way, which is why nothing in the audited model's own source mentions it.
The hardest kind of Odoo behaviour to trace, and the reason to check the installed
module list when code cannot explain what a model is doing (chapter 50). The web client
has its own version, `patch()` from `@web/core/utils/patch` (chapters 40, 50).

**mixin**: an `AbstractModel` inherited via the list form of `_inherit` to pull in a
bundle of ready-made fields and methods (chatter, activities) without any of them
belonging to a real parent record. Composition through classic extension, not a new
inheritance mechanism.

**master data**: config records a module needs to be useful on day one, shipped as
regular data files (not `demo`), typically wrapped in `noupdate="1"` so a manager's
later edits (a renamed stage, an adjusted price) survive the next upgrade instead
of being silently overwritten. Chapter 34's `service_type_master.xml` is an
example. Contrast with *demo data*, which is optional and disposable.

**master password**: the `admin_passwd` option in `odoo.conf`. It guards
database-manager operations (create, duplicate, drop), and is unrelated to any user's
login password.

**measure**: a field a pivot or graph view sums or averages. Requires the field to
have a real database column (`store=True`); a non-stored computed field raises a
ValueError the moment it's actually aggregated, even though the view installs fine.

**menu item**: an `ir.ui.menu` record (usually written with the `<menuitem>`
shortcut tag) forming the app's navigation tree. `action=` makes it open something,
`groups=` trims who sees it (navigation only, not security), and a root item with a
`web_icon` becomes an app tile.

**model**: a Python class extending `models.Model` whose `_name` (like
`librefleet.vehicle`) identifies it everywhere: `env[...]` lookups, and the Postgres
table name with dots turned into underscores. Its fields become the table's columns.

**models.Constraint**: the Odoo 19 way to declare an *SQL constraint* on a model:
`_name_uniq = models.Constraint("unique(name)", "message")`. The attribute name
becomes the Postgres constraint name; it replaces the pre-19 `_sql_constraints` list
(chapter 14).

**module**: a directory with `__manifest__.py` and `__init__.py` that adds models,
views, data, or code to an Odoo database. An *app* is just a module with
`'application': True`.

**move line (`stock.move.line`)**: the layer under a stock move that says *which exact
stock*: the source location, the lot or serial, the package, and a `quantity`. Reserving
creates them, Validate turns them into quant changes, and **Moves History** lists the
done ones. The **Details** button on a transfer line opens them.

**Multiple (`replenishment_uom_id`)**: the pack size a reordering rule orders in: one of
the product's packagings or the vendor's unit. To Order is rounded **up** to whole packs,
so it can end above the rule's Max; the Replenishment screen flags that with a warning
icon next to the forecast.

**Multiple Warehouses (group)**: `stock.group_stock_multi_warehouses`, switched on by
Odoo itself when a company gets its second active warehouse and off again when it is back
to one; there is no setting for it. It shows the warehouse form's Resupply From field, the
Warehouses panel in reports and the Warehouse field on sales orders.

**namespacing (field prefixes)**: naming fields you add to a model you do not own after
your module (`librefleet_is_part`), so they cannot collide with core's or with another
module extending the same model. Nothing enforces it, which is why the collision only
surfaces much later.

**notebook**: the tab container inside a form sheet; each `<page>` groups one concern.
Give pages a stable `name` so xpaths can anchor on them.

**noupdate**: a data file's protection against being silently rewritten on the next
module upgrade. `<data noupdate="1">` opts an XML block in explicitly; every file
listed under a module's `demo` key gets it automatically, whether XML or CSV
(chapter 34, verified against Odoo's own loader: `noupdate=kind == 'demo'`). On
upgrade, a noupdate record that already exists (matched by its xml id) is left
alone, but a *new* noupdate record with no existing xml id is still created
normally, which is why adding a second master-data record later still works.

**OCA**: Odoo Community Association. A Swiss nonprofit hosting hundreds of
community-maintained module repositories at [github.com/OCA](https://github.com/OCA).

**ocabot**: the bot account that runs OCA repository chores from PR comments:
`/ocabot merge`, migration-issue tracking, and the CLA check on a contributor's
first PR (chapter 45).

**Odoo SA**: the Belgian company that develops Odoo, ships the yearly release, and
sells Enterprise subscriptions and hosting (Odoo Online, odoo.sh).

**odoo shell**: `odoo shell -d <db>`, a Python REPL with a fully loaded `env`. The
best place to experiment with the ORM. It never commits by itself; writes need an
explicit `env.cr.commit()`.

**on-hand vs forecast (`qty_available` vs `virtual_available`)**: `qty_available` is
what physically sits in a location right now; `virtual_available` nets in what is already
reserved to leave (`outgoing_qty`) and expected to arrive (`incoming_qty`). The number
safe to promise a customer is the forecast, not the shelf count (chapter 25).

**onchange**: a method (`@api.onchange("field")`) run while a user edits a form,
before saving, typically to prefill other fields. Never fires from code, imports or
RPC, so it is a typing assistant, not a business rule.

**ondelete**: the many2one policy for when the referenced record is deleted:
`set null` (default, forget the link), `restrict` (block the deletion), `cascade`
(delete me too). Becomes a real `ON DELETE` clause in Postgres.

**one2many**: the mirror of a many2one, declared with the comodel and the inverse
field name. Stored nowhere: it is a live query over the comodel's many2one, which
is why it cannot exist without one.

**operation type (`stock.picking.type`)**: a kind of transfer with its own numbering and
its own default source and destination: Receipts (Vendors to Stock, `IN`), Delivery
Orders (Stock to Customers, `OUT`), Internal Transfers (`INT`), and later Pick, Pack,
Manufacturing, Dropship. The Inventory Overview is one card per operation type.

**ORM**: Odoo's object-relational mapper, the layer that turns Python model classes
into PostgreSQL tables and back.

**orphaned column**: a database column whose field no longer exists (renamed, deleted,
or made non-stored). Odoo adds columns but never drops them, so these accumulate
silently; clearing them is explicit migration work.

**OWL**: Odoo Web Library, the in-house JavaScript component framework used by the web
client since Odoo 14, shipped as version 2.8.2 in Odoo 19. A component is a class with
a `static template` naming a QWeb template, a `setup()` method (hooks go here, not in a
constructor), and reactive state from `useState` (chapter 39).


**pre_init_hook / post_init_hook**: manifest keys naming functions, defined in the
module's `__init__.py`, that run around installation. The pre-init one runs **before**
the module's models load, so it works in raw SQL and is the sanctioned way to add a
column to a table that already has rows; the post-init one runs after, with the ORM
available. `crm_lead_code` uses both to give every pre-existing lead a sequence number,
which no data file could do. Read them before installing anything on a database that
matters: a per-row loop in a post-init hook is a maintenance window on real data
(chapter 50).

**pinning**: fixing every external dependency (OCA repos, Odoo itself) to an exact
commit or package version so a production build is reproducible from the project repo
alone. Done with git submodules, git-aggregator, or pip requirements.

**package (`stock.package`)**: one physical box with a name, a type, a location and
contents: the quants that carry it. Put in Pack creates one; a move line names where goods
come from (Source Package) and where they go (Destination Package). It needs the
**Packages** setting.

**package type (`stock.package.type`)**: a kind of box: dimensions, empty and maximum
weight, a barcode, a name prefix (Sequence Prefix) and its **Package Use**, disposable (the
box travels) or reusable (emptied at the next step). Configuration → Package Types.

**packaging**: a unit a product is sold or bought in, such as Pack of 6. In Odoo 19 a
packaging is a unit of measure; it can name a package type and carry a barcode per product
(Packaging Barcodes). On a stock move it rides beside the real quantity as Packaging and
Packaging Quantity.

**payment provider (`payment.provider`)**: the record backing one checkout payment
method (Stripe, PayPal, Wire Transfer, ...), disabled by default for every method
Odoo ships. A `payment.transaction` links a specific attempt back to whatever
document it's paying for (a `sale.order`, an invoice); a manual provider like Wire
Transfer leaves that transaction `pending` until a human confirms the money
actually arrived, rather than confirming itself (chapter 42).

**payment_state**: the *computed* billing summary on an `account.move` (`not_paid`,
`partial`, `in_payment`, `paid`, `reversed`, `blocked`). Derived from `amount_residual`
and the lines' `reconciled` flags, so writing it directly fixes nothing (chapter 28).

**payment term (`account.payment.term`)**: sets an invoice's due date, and can split it
into dated instalments. It changes *when* money is expected, never which accounts are
used: overdue is a date question, unpaid is a reconciliation question (chapter 28).

**pdb**: Python's built-in interactive debugger. Entered either by calling
`breakpoint()` in your own code or with `pdb.runcall(fn, *args)` to stop inside code you
do not want to edit. It needs a real terminal to read commands from, so it works in
`odoo shell` but not in the containerised server process (chapter 6).

**Partner-Specific Instructions (`picking_warn_msg`)**: an Inventory setting
(`stock.group_warning_stock`) that adds *Instructions on the Stock Operations* to a
contact's Notes tab. Every transfer for that contact, or for one of its child addresses,
shows the text in a banner. Odoo 19 only displays it; nothing is blocked.

**patch (`@web/core/utils/patch`)**: the frontend's escape hatch for changing a core
class that publishes no registry slot. `patch(SomeClass.prototype, { method() { ... } })`
rewrites methods in place, keeping the previous implementation reachable through
`super` so several modules' patches stack in load order rather than clobbering each
other. **A patch is global and unconditional**: it applies to every instance of that
class everywhere in the web client, with no way to scope it at registration time, so
any narrowing (a `record.resModel` check, say) has to happen inside the method body.
Prefer a registry entry wherever Odoo publishes one (chapter 40).

**picking (`stock.picking`)**: one transfer, a batch of `stock.move` lines sharing a
source, a destination and a `picking_type_id`. A multi-step route (chapter 25) is a chain
of pickings, and later legs are created only once the ones before them are done, not all
at once.

**pivot view**: a view type describing a table of aggregated data: `row`/`col`
fields group records, `measure` fields are summed per group, via `read_group`.

**Point of Sale (`pos.session` / `pos.order`)**: a real OWL SPA (`/pos/ui/...`),
offline-first: it runs against an in-browser IndexedDB and syncs to the server as
connectivity allows, a different bootstrap from the backend web client's
`web.assets_backend` or the website's `web.assets_frontend`. A session moves through
`opening_control` → `opened` → `closing_control` → `closed`; closing it posts one
consolidated sales entry for every order in the session (`session.move_id`), plus one
settlement entry per payment method clearing that receivable into the account the
method actually pays into. The Closing Register screen's Cash Count field defaults to
`0`, not to the expected total, which is the standard first-day gotcha (chapter 42).

**portal (customer portal, `portal.mixin`)**: the `/my/...` pages a non-employee
customer logs into to see their own records, `/my/orders`, `/my/invoices`, and
whatever a module adds (chapter 37's `/my/service-orders`). `portal.mixin` gives a
model `access_token` (a random UUID for share links) and `access_url` (which every
model using the mixin must override, the default is the literal string `'#'`).
`CustomerPortal._document_check_access()` is what actually authorizes a request: a
normal record-rule read first, an `access_token` match as the fallback for a
logged-out visitor with a share link.

**prefetch**: the ORM's automatic batching of related-field reads across one
recordset. Iterate records that came from a single `search()` and touch a related
field on each, and the ORM fetches the whole batch in a handful of queries rather
than one per record. A fresh `search()` called inside a loop starts a new,
unbatched recordset every time, defeating this entirely, the real mechanism behind
the N+1 query trap (chapter 53).

**price-included tax (`price_include`)**: a tax treated as already inside the price you
type, so 100.00 at 15% is 86.96 of revenue plus 13.04 of tax rather than 115.00. In Odoo
19 `price_include` is *computed* from the tax's `price_include_override` falling back to
the company's `account_price_include`, which locks once the database has journal entries
(chapter 29).

**pricelist (`product.pricelist`)**: an optional, feature-flagged bag of
`product.pricelist.item` rules that override a product's own price on an order. Each rule
declares an `applied_on` scope whose numeric prefix (`0_product_variant` through
`3_global`) **is** the specificity sort key, so the most specific applicable rule wins and
rules never stack (chapter 23).

**primary view**: a standalone view competing for the default slot of its model and
type. With `inherit_id` plus `mode="primary"` it becomes a patched *copy* of another
view instead of a patch on it.

**privilege**: `res.groups.privilege`, new in Odoo 19: the row that gathers related
groups ("Workshop" holding User and Manager) on the user form. Replaces the direct
group-to-category link older versions used.

**procurement (stock)**: a *need*: this much of this product is wanted in this location
by this date. Confirming a sales order, a reordering rule firing, or a rule with
**Trigger Another Rule** all create one; Odoo answers it by finding a rule whose
destination is that location and running it (a transfer, a purchase order, a
manufacturing order). Nothing is stored for the need itself, only what the rule created.

**product attribute**: a `product.attribute` (Colour, Axle) whose values, when its
variant mode is "Instantly", make Odoo generate one `product.product` per combination
on save. An attribute with a single value multiplies nothing (chapter 21).

**product template / product variant**: the two halves of an Odoo product.
`product.template` is the product as a person names it ("Brake Pad Set");
`product.product` is a specific sellable, stockable thing ("Brake Pad Set (Front)").
A template with no attributes still has exactly one variant, and core code asking for
`product_id` always means the variant.

**product.value**: the history of manual value changes in Odoo 19: every change of a product's cost, and every Adjust Valuation on a move. It is what lets Inventory at Date value stock as it was (Inventory chapter 12).

**prototype inheritance**: `_inherit` *plus* a new `_name`. Creates a new model
and table pre-filled with copies of the parent's field definitions. The two are
unrelated from then on, and it is the rarest of the three in practice.

**Production (location)**: the virtual location a manufacturing order's stock moves
run through. Components arrive there positive (consumed from stock); the finished good
leaves from there negative (produced into stock). The same two-sided move pattern as
every other stock transfer, applied to a transformation rather than a delivery
(chapter 26).

**PSC**: Project Steering Committee, the maintainers governing one OCA repository.

**pull rule / push rule**: the two directions a stock rule works in. A **pull** (`action
= pull`) fires when goods are *needed* at its destination and creates a transfer to fetch
them from its source, working backwards from the customer; a **push** (`action = push`)
fires when a transfer *into* its source is validated and carries the goods on to its
destination, working forwards from the dock. Odoo 19's generated routes pull once (out of
stock) and push the rest (Storage, Pack, Delivery Orders). **Buy** and **Manufacture**
are pulls that create a purchase or manufacturing order instead of a transfer.

**Put in Pack**: the transfer button that puts move lines into a package, a new one or
an existing one. With **Set Package Type** on the operation type it asks for the type;
without, it uses the packaging's package type. When every line already has a package, it
packs the packages into a container.

**putaway rule (`stock.putaway.rule`)**: *when this arrives in that location, store it
here instead*. It matches on product, product category or package type, applies only to
transfers into its exact **When product arrives in** location, and its **Sublocation**
(No, Last Used, Closest Location) decides how far it searches. The most specific matching
rule wins: package type, then product, then category. It never splits a line.

**quant (`stock.quant`)**: one row saying *this product, in this location, this many*
(plus optional labels: lot, package, owner). The quant table is what Odoo means by
"stock": every On Hand figure is a sum over quants, and quants only change when a
transfer is validated. Vendor and customer locations keep quants too, which is why a
receipt leaves `Vendors` at a negative quantity (Inventory deep dive, chapter 1).

**QWeb**: Odoo's XML templating engine, used both server-side (PDF reports, website
pages) and client-side (OWL component templates).

**QWeb report (`ir.actions.report`)**: a printable document, built from two QWeb
templates: a wrapper that calls `web.html_container` once and loops over the
selected records, and a document template, called once per record, that wraps its
content in `web.external_layout` for the header and footer and in
`<div class="page">` so several records print as several pages in one PDF. Binds to
a model's Print menu the same way chapter 35's server action bound to an Action
menu, `binding_model_id` plus `binding_type = "report"` (chapter 36). Rendered
through `report.paperformat` (margins, paper size) and `wkhtmltopdf`.

**read_group / formatted_read_group**: the ORM's aggregation call, one `GROUP BY` in
Postgres instead of fetching every record and counting in Python or JavaScript. Odoo 19
renamed `read_group` to `formatted_read_group` (`orm.formattedReadGroup` in JS) and made
aggregates their own argument: `(domain, groupby, ["__count", "margin:sum"])`. Results
are keyed by the exact aggregate string you asked for, and each group carries a
`__domain` reproducing it. **Grouping by a many2many double-counts on purpose**, since a
record belongs to every group it is a member of, so the groups never sum to the record
count (chapter 41).

**rank (`customer_rank` / `supplier_rank`)**: integer counters on `res.partner` that
rise as a partner appears on sales or purchase documents. Odoo has no customer *type*
and no supplier table: being both at once is just both counters above zero.

**reception report**: the **Reception Report** setting (`stock.group_reception_report`): an **Allocation** button on receipts that lists the orders waiting for what arrived, so it can be set aside for them (Inventory chapter 11).

**reconciliation (`account.partial.reconcile`)**: the act of declaring that a debit and a
credit cancel out, and the record that stores it. Two instalments against one invoice
create two partial reconciliations whose amounts sum to the total. This, not
`payment_state`, is where "paid" actually lives (chapter 28).

**record rule**: an `ir.rule` filtering *which records* of a model a group may
touch, via a domain ("only orders assigned to you"). The per-record layer on top of
access rights, which are model-wide. LibreFleet's first one lands in chapter 12.

**repartition line (`account.tax.repartition.line`)**: the child record deciding where a
piece of a tax goes, shown as the **Distribution** tables on a tax. Four per plain tax
(base and tax, for invoices and refunds), and more than one "of tax" line is how a single
tax produces several journal lines on different accounts (chapter 29).

**reverse charge**: a tax whose distribution carries a +100% and a -100% "of tax" line, so
both sides are recorded and `amount_tax` nets to zero. The reason `amount_tax == 0` does
not mean no tax happened (chapter 29).

**reward (loyalty)**: what a claimed coupon, code or promotion adds to an order, and it
arrives as **its own order line with a negative `price_unit`**, not as an edit to the
product line and not as the `discount` field. From `sale_loyalty`, which also brings
`loyalty.program` and its eight programme types (chapter 23).

**RFQ / purchase order**: the same `purchase.order` record before and after
confirmation. `state` runs `draft` (RFQ), `sent`, `to approve`, `purchase`, `cancel`, and
confirming is what spawns the incoming transfer (chapter 24).

**removal strategy (`removal_strategy_id`)**: which quants a reservation takes first:
First In First Out (the default, oldest arrival), Last In First Out (newest arrival),
Closest Location (first by full location name, not by distance), Least Packages (as few
packages as possible), or First Expiry First Out. Odoo looks at the product category's
**Force Removal Strategy** first, then the location, then its parents, then falls back to
FIFO; quants with a lot come before quants without.

**reordering rule (`stock.warehouse.orderpoint`)**: a minimum and maximum for one
product at one location. Creating one is a promise, not an action: it does nothing until
a scheduled action checks whether forecast has fallen below the minimum (chapter 25,
chapter 35). Its **Trigger** is Auto (the scheduler orders) or Manual (the line waits in
the Replenishment report). When the forecast at today plus the lead time plus the
horizon is below Min, it orders Max minus that forecast, rounded up to its Multiple.

**Replenishments (`replenish_location`)**: the location box marking a location the
Replenishment report watches, together with all its children. Each warehouse's stock
location has it; a location and its parent or child cannot both have it.

**Replenish on Order (MTO)**: the global route (`stock.route_warehouse0_mto`, archived
until the setting of the same name is ticked) whose one rule has Supply Method **Trigger
Another Rule** (`procure_method = make_to_order`). Put it on a product and every sale
creates a dedicated chain upstream (a purchase through the Buy rule, or a manufacturing
order) instead of taking from the shelf. "MTO" is make to order.

**replenishment horizon (`horizon_days`)**: extra look-ahead, on top of the lead time,
for every reordering rule's forecast: a company setting, 365 days by default (Inventory
settings, Advanced Scheduling). At 365 any demand confirmed for the next year counts
today; at 0 Odoo orders just in time. The HORIZON box in the Replenishment side panel
changes it for that screen only.

**Replenishment report**: Inventory → Operations → Replenishment, the list of reordering
rules with their forecast and To Order. Opening it creates a Manual rule named
*Replenishment Report* (by OdooBot, Min and Max 0) for each storable product with a
negative forecast and no rule, and deletes such a rule again once it is ordered and
nothing is left to order. Its line buttons are Order, Automate and Snooze.

**reservation (stock)**: a promise written on a quant: `reserved_quantity` goes up, the
move gets its move lines and turns Available, and **Free to Use** (`free_qty`) shrinks,
while On Hand does not change. When it happens is the operation type's **Reservation
Method**: At Confirmation, Manually (Check Availability) or Before scheduled date.
Unreserve gives the promise back.

**resupply route (Resupply From)**: the route a warehouse gets for each warehouse ticked
in its **Resupply From** field, named like *Service Van: Supply Product from LibreFleet
Depot*. Its pull rules take the goods through the supplying warehouse's own delivery
steps into the transit location, then through the supplied warehouse's receipt. It is
selectable on products, categories, warehouses and reordering rules.

**return (stock)**: a transfer in the opposite direction, created from a done transfer's
Return button through the `stock.return.picking` wizard. It uses the operation type named
as **Returns Type** on the original's type, carries *Return of ...* as its source
document, and each move points at the move it undoes (`origin_returned_move_id`).

**reusable package (tote)**: a package whose type has Package Use **Reusable Box**. It
is never kept as a destination package: the next transfer takes its goods out, and the
empty tote goes back to be used again. Community stores the field but only the Barcode app
shows it on the form.

**recordset**: the value every ORM operation returns: an ordered collection of records
of one model, which may hold zero, one, or many. Methods called on it apply to all of
them.

**route (`stock.route`)**: a named list of stock rules plus the places where it may apply
(*Applicable On*: products, product categories, package types, warehouses, sales order
lines, shipping methods). The warehouse generates its own from the step settings
("Deliver in 3 steps (pick + pack + ship)"); **Buy**, **Manufacture** and **Replenish on
Order (MTO)** are global ones. When a need appears, Odoo gathers the routes of the product,
its category and the warehouse, and takes the first rule whose destination matches.

**rule (`stock.rule`)**: one instruction inside a route: an **Action** (Pull From, Push To,
Buy, Manufacture), a source and destination location, the **Operation Type** of the
transfer it creates, a **Supply Method** for pulls (Take From Stock, Trigger Another Rule,
or the first falling back to the second), a Lead Time, Cancel Next Move
(`propagate_cancel`), and for pushes **Automatic Move** and an applicability filter. Its
form writes the rule out as a sentence (`rule_message`), the fastest way to read one.

**routing (`reception_steps` / `delivery_steps`)**: how many transfers a warehouse
makes goods pass through on the way in or out: directly (1 step), via Input/Output
(2 steps), or via Input/Output plus Quality Control (3 steps). Confirming a document
under a multi-step route creates only the first transfer; later legs appear only once
the one before completes (chapter 25).

**registry**: the in-memory catalog of all models a server process builds at startup
by importing every installed module's Python. `env["librefleet.vehicle"]` is a
registry lookup. Rebuilt on restart; the database schema only changes at
install/upgrade.

**related field**: a computed field the framework writes for you from a path:
`related="vehicle_id.owner_id"` mirrors the value at the end of the path and
updates when it changes. Storable like any computed field.

**ribbon**: the `web_ribbon` widget, a diagonal corner banner on a form (core uses it
for "Archived" and "Paid"). Placed with `<widget name="web_ribbon" title="..."
bg_color="..." invisible="...">` right after the sheet's button box; the `invisible`
expression decides when it shows, most often over `active` (chapter 17).

**Runboat**: OCA infrastructure that spins up a throwaway live Odoo instance for every
pull request, so reviewers can click through changes.

**`search_default_<name>`**: an action context key that pre-checks the search view
filter of the same `name` when the view loads. Nothing validates the match; a typo
fails silently.

**scheduler (Procurement: run scheduler)**: the daily scheduled action that orders for
every **Auto** reordering rule whose forecast is below its Min, retries the reservation of
waiting moves, and tidies quants. In developer mode it is a menu item under Inventory →
Operations. A rule it cannot fulfil gets an Exception activity on the product, for the
product's Responsible, instead of an error.

**scrap (`stock.scrap`)**: taking a quantity of a product out of a location into an
Inventory Loss location, with optional reason tags and a **Replenish Quantities** box that
asks the replenishment rules to reorder it. Not a transfer, but it creates an ordinary
`stock.move`. Odoo 19 has no dedicated Scrap location; the scrap goes to the company's
first `usage = inventory` location, `Inventory adjustment` in a fresh database.

**Selection field**: a field storing one key from a closed list of
`(key, "Label")` pairs, a `varchar` in Postgres. LibreFleet's order `stage` is one;
chapter 17 dresses it as a statusbar.

**sequence (ir.sequence)**: a named, concurrency-safe counter with a prefix, padding
and optional per-period reset, read with `next_by_code("code")`. Non-transactional by
design, so drawn numbers survive rollbacks and the counter has gaps. Powers order and
invoice references (chapter 14).

**server action (`ir.actions.server`)**: a stored, runnable piece of server-side
logic (`state='code'` for inline Python, plus non-code states for things like
sending an email or creating a record). `records` and `model` are the eval-context
names for whatever it runs against: `records` is only populated when the action runs
bound to a selection, so a server action meant to work both from a menu and from a
cron (which passes no selection) needs a fallback, `records or model.search([])`.
Also what a cron and an automated action both are underneath (chapter 35).

**shipping policy (`move_type`)**: on a transfer's Additional Info tab. **As soon as
possible** (`direct`) makes the transfer Ready when at least one move has stock reserved;
**When all products are ready** (`one`) waits until every move is fully reserved. The
same partially reserved transfer is Ready under the first and Waiting under the second.

**singleton**: a recordset holding exactly one record. Scalar fields can only be read
on singletons; violating that raises `Expected singleton`. `self.ensure_one()` asserts
it explicitly at the top of single-record methods.

**smart button**: the stat buttons at the top of a form view linking to related
records ("3 Orders", "2 Deliveries"). You'll build one in chapter 17.

**snippet (`website.s_*`)**: a draggable content block in the website builder, one
`ir.ui.view` per block, 191 of them shipped by core. Dragging a snippet onto a page
copies its QWeb arch into that page's own `arch_db` rather than linking to the shared
template, which is why editing one page's copy never touches another page that
dragged in the same block (chapter 42).

**snooze (reordering rule)**: hiding a line of the Replenishment report until a date (1
day, 1 week, 1 month or a custom date), stored in the rule's `snoozed_until`. The **Not
Snoozed** filter does the hiding; nothing else about the rule changes.

**statusbar**: the widget rendering a Selection field as the stage bar in a form's
header. With the clickable option users can change stage by clicking; it enforces no
workflow rules by itself.

**stock move (`stock.move`)**: one line of a transfer: a product, a quantity, a source
location and a destination location. Validating the transfer turns each move into quant
changes at both ends. `product_uom_qty` is the Demand column (what was planned),
`quantity` is what was actually moved. In Odoo 19 a move has no `name` field.

**stock variation account**: the counterpart of the stock valuation account in a periodic closing entry: the change in stock value for the period. Set on the stock valuation account as its Variation Account (Inventory chapter 12).

**`stock.reference`**: Odoo 19's link between the documents of one flow (a sale, its transfers), which replaced procurement groups. A move holds several in `reference_ids` (Inventory chapter 13).

**storage category (`stock.storage.category`)**: what a location may hold: a **Max
Weight** (0 refuses anything that has a weight), **Allow New Product** (only if empty,
only the same product, or mixed) and capacities per product or per package type. Putaway
rules with Closest Location use only locations of the category they name.

**subcontracting**: buying a product that a partner builds from your components. A bill of materials of type **Subcontracting** names the subcontractors; buying from one creates a **Resupply** transfer to the Subcontracting location and a hidden production that the receipt finishes (Inventory chapter 11).

**sudo()**: derives a recordset with the superuser bit (`env.su`) on: access rights
and record rules stop applying, while `env.user` stays unchanged. Bypasses spread to
records reached through the sudo'd set, so scope it to the smallest operation.

**superuser**: uid 1 (`__system__`), the internal account that bypasses access
rights and record rules entirely. `odoo shell` runs as it, `sudo()` switches to it.
Not the same thing as the `admin` login, which is an ordinary user with powerful
groups.

**Take From Stock, if unavailable, Trigger Another Rule (`mts_else_mto`)**: a rule's Supply Method that takes what its source location holds and runs a new procurement at that location for the rest, so another rule can bring it there. LibreFleet's Workshop route uses it to try the van before the depot (Inventory chapter 13).

**target="new"**: an action attribute that opens the action as a popup instead of
navigating away from the current record. What makes a wizard a wizard, visually.

**tax (`account.tax`)**: a rate (`amount`, `amount_type`) plus a routing table (its
*repartition line* children), scoped to sales or purchases by `type_tax_use`. Odoo has no
separate "tax amount" table: what a tax does is produce lines on an `account.move`
(chapter 29).

**tax group (`account.tax.group`)**: groups taxes for display in a document's totals block
and carries the receivable/payable accounts the period-end tax closing uses. It takes no
part in computing an amount (chapter 29).

**tax rounding (`tax_calculation_rounding_method`)**: whether Odoo rounds the tax once per
line (`round_per_line`) or once per tax over the whole document (`round_globally`, labelled
**Round per Tax**). Odoo 19 defaults to the latter, Odoo 18 to the former, which is why the
same three lines can total 34.85 or 34.86 (chapter 29).

**technical name**: a module's directory name (`librefleet`), as opposed to its
display `name` ("LibreFleet"). Used by `-i`/`-u`, `depends`, XML ids and table
prefixes; effectively immutable once a module ships.

**three-way match**: the practice of tracking ordered, received and billed quantities
separately (`product_qty`, `qty_received`, `qty_invoiced` on a purchase line, summarised by
`receipt_status` and `invoice_status`). They are *allowed* to disagree, and that visible
disagreement is the point: it is how an over-billing supplier gets caught (chapter 24).

**tracking (`tracking=True`)**: a field attribute that posts a chatter message with
the old and new value whenever an ORM write changes it, no method required. Fires
only on a real database write, and only becomes visible after the transaction
commits, since the message itself is built by a precommit hook (chapter 33).

**tracking (product, lots and serials)**: a stock product's *Track Inventory* choice, By
Quantity, By Lots or By Unique Serial Number (`product.template.tracking`, needs the Lots &
Serial Numbers setting). Every move line of a tracked product carries a lot. Switching it
on for a product already in stock leaves that stock without lots; Odoo warns, and a
Physical Inventory count gives the stock its numbers.

**Traceability report**: the list of every done move of one lot or serial number, newest
first, from its receipt to its delivery, return or scrap; opened from the lot's
Traceability button or a done transfer's. The first tool of any recall.

**tracking reference (`carrier_tracking_ref`)**: the carrier's number for a parcel, on the transfer's Additional Info tab. With a Tracking Link containing `<shipmenttrackingnumber>`, the transfer shows a **Tracking** button (Inventory chapter 11).

**TransactionCase / HttpCase**: Odoo's base test classes. `TransactionCase` wraps
each test method in a database transaction rolled back at the end, no cleanup code
needed; `HttpCase` (itself a `TransactionCase`) additionally starts a real HTTP
client, so `self.url_open(path)` genuinely round-trips through `@http.route`'s own
auth and routing, not a mocked call. `@tagged("post_install", "-at_install")` is the
usual pairing, `-` removes the default `at_install` tag rather than adding a second
one (chapter 38).

**transit location**: a location of type *Transit* where goods wait between two
warehouses (*Inter-warehouse transit*, one per company, switched on by the first resupply
route) or two companies (*Inter-company transit*). Transit stock belongs to no warehouse
and is left out of every on-hand total; Reporting → Locations shows it with the Transit
Locations filter.

**uid**: the current logged-in user's id, substituted by the web client wherever it
appears inside a domain or context string written in XML. Not a Python variable.

**Unit Cost History (`stock.avco.report`)**: the list of every cost change of a product and the average after it, opened by clicking a Unit Cost in Inventory → Reporting → Stock. It replays the moves as AVCO, and FIFO products have none (Inventory chapter 12).

**unit of measure (`uom.uom`)**: the unit a quantity is expressed in. In Odoo 19 each
unit declares `relative_factor` against a `relative_uom_id` (Dozens is 12 Units),
forming a tree whose absolute `factor` is computed recursively. The pre-19 model of unit
*categories* with a reference unit and a `uom_type` is gone (chapter 21).

**useState**: the OWL hook that makes a component's data reactive. It returns a Proxy
around the object you pass: reading a key during a render subscribes that render to the
key, and assigning to the key schedules a re-render. Assigning to a plain instance
property instead (`this.count = 5` rather than `this.state.count = 5`) updates the value
and changes nothing on screen, with no error, which is OWL's classic beginner bug
(chapter 39).

**valued move (`is_valued`)**: whether a `stock.move` changes what the company owns.
True only when the goods cross the company boundary, since locations with a `usage` of
`internal` or `transit` count as inside it. Moving stock between your own shelves is
valued at zero on purpose, because nothing economic happened (chapter 30).

**vacuum**: the scheduled process that deletes old transient records automatically,
so a wizard's table never accumulates forever. Configurable per model via
`_transient_max_hours`.

**ValidationError**: the exception (`from odoo.exceptions import ValidationError`) a
Python constraint raises to reject a write. Odoo rolls the transaction back and shows
its message to the user (chapter 14).

**view priority**: the tie-breaker among primary views: lowest number wins the
default slot (base views sit at 16). Views with high priorities are only shown when
an action requests them via `view_id`.

**warehouse (`stock.warehouse`)**: one site (a building, a yard, a van). Creating or
renaming one generates its locations, operation types, numbering sequences and routes.
Its *Short Name* (`code`, five characters at most) is the prefix of every location path
and transfer number under it (`LFD/Stock`, `LFD/IN/00001`), so choose it before the first
receipt. A second warehouse switches on the *Multiple Warehouses* group, and each
warehouse's **Resupply** section says where its stock comes from: Buy, Manufacture, or
another warehouse.

**Weblate**: the OCA's translation platform. Contributors translate strings there,
never by editing a module's `.po` files directly in a PR; edits made straight to
`.po` get overwritten on the next sync (chapter 45).

**WorkContext**: the object OCA's component system hands you from
`backend.work_on(model_name)`, carrying the model, the collection and anything else the
components in one work session need to share (an open API client, say). Components look
each other up through it with `work.component(usage=...)` (appendix on components).

**wave transfer**: a batch made of move lines picked from several transfers, split by
product, product category or location (Actions → Add to wave, or the operation type's
Wave Grouping).

**widget**: an attribute on a view field picking an alternative renderer for the
same data (`widget="many2many_tags"` shows chips instead of a table). Chapter 17
tours the built-ins; chapter 40 builds one. The attribute's value is a lookup into
the `fields` registry, where each name maps to a descriptor object
(`{ component, supportedTypes, ... }`) pointing at an OWL component. The component
reads its own value as `props.record.data[props.name]`, which is why one widget can
serve many fields on many models.

**window action**: an `ir.actions.act_window` record saying what to open: the
model (`res_model`) and the view types in order (`view_mode="list,form"`). The glue
between a menu click and the views that render.

**with_user()**: derives a recordset acting as another user, with that user's groups,
access rights and record rules. The standard way to test security from the shell.

**wizard**: a `TransientModel`, a popup form used for a confirmation step,
extra input, or validation before a write that a raw field change or button click
can't provide on its own. Same fields and methods as a regular model, different
lifecycle.

**XML id (external id)**: the stable handle a data record is registered under
(`librefleet.group_librefleet_user`), used by `ref()` in XML, `env.ref()` in Python,
and CSV reference columns. Resolves against the database, which is why a missing one
only fails where the record was never loaded (fresh installs). Chapter 34 goes
deeper.

**ZPL**: Zebra Programming Language, the text format thermal label printers read. Every
Inventory label with a ZPL variant (product, lot, package, operation type) prints as ZPL
text instead of a PDF.
