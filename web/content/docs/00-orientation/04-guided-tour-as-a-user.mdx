---
title: "4. Guided Tour as a User"
description: Run Odoo with demo data and click through it; you can't develop a product you've never used.
---

**Goal:** spend an hour inside Odoo as a user, then switch on developer mode and peek
behind the curtain. · **Time:** ~1.5 h · **Checkpoint:** none, but your Odoo runs!

## Why this matters

You cannot develop a product you've never used. Every model you'll build starting in
chapter 8 (customers, orders, stages) is a concept Odoo's own apps already express,
and once you've clicked through them, the framework's vocabulary stops being abstract.
Developers who skip this stage write modules that fight the platform; developers who
know the product write modules that feel native.

## Hands-on

<Steps>

<Step>
### Start Odoo (on trust, for now)

The next chapter explains this setup line by line; today, just run it. You need
[Docker](https://docs.docker.com/get-docker/) installed.

Open **[odoolings-starter](https://github.com/ronitjadhav/odoolings-starter)** and
click the green **Use this template** button. Name the new repository whatever you like
(`librefleet` is a fine choice), then clone it and start the environment:

```console
$ git clone https://github.com/<you>/librefleet.git
$ cd librefleet
$ docker compose up
```

That repository is **yours**, from its first commit. Your own GitHub, your own history.
From chapter 8 your LibreFleet code grows in its `addons/` directory, and chapter 7 puts
the git side of it on a professional footing. You never clone this tutorial's repository
to work inside it.

<Callout type="info" title="Why a template and not a fork">
  A fork stays tied to somebody else's project. Using a template gives you an independent
  repository with a clean history, which is what your own module deserves and what a
  client project looks like. Forking is a different tool for a different job, and chapter
  45 uses it properly when you contribute to OCA.
</Callout>

Wait for the log to settle, then open [http://localhost:8069](http://localhost:8069).
You'll land on the **database manager**.
</Step>

<Step>
### Create a database, with demo data

![The database creation form, with a random master password already suggested in the field](/screens/ch04-database-manager-generated-password.jpg)

Notice the **Master Password** field already has something in it: a random string the
page generated for you and printed in the yellow banner above the form. Ignore it.
Fill the form like this:

- **Master Password:** clear the suggested value, type `admin` instead
- **Database Name:** `tour`
- **Email** and **Password:** whatever you like, this becomes your admin login
- **Demo Data:** check it

<Callout type="warn" title="That suggested password is not decorative">
  Our `odoo.conf` ships with `admin_passwd = admin`, a known-insecure value chosen on
  purpose for a local dev box. Odoo notices, and nudges you to do better by generating a
  random replacement and pre-filling the field with it.

  Here is the catch. The field does not check what you type against the old password:
  whatever you submit **becomes** the master password for the rest of this container's
  life. Accept the suggestion without reading it, and yours is now a random string you
  never wrote down. Nothing is broken forever, since restarting the container reloads
  `admin_passwd` from the file and resets it, but until then you are stuck the moment you
  actually need it, say to drop a database.

  Typing `admin` yourself keeps it exactly what it already was. Nothing to write down.
</Callout>

<Callout type="warn" title="Demo data is a birth decision">
  <Term k="demo data">Demo data</Term> fills the database with a fictional company (customers, products, open
  orders), which is exactly what makes clicking around instructive. It also gets loaded
  at creation or never: there's no switch to flip later. If you forgot the checkbox, drop
  the database in the manager and create it again.
  (From the command line, Odoo 19 creates databases **without** demo unless you pass
  `--with-demo`. That default changed over the years, so old tutorials disagree.)
</Callout>
</Step>

<Step>
### Install two apps

You land in the **Apps** menu. Install **CRM**, then **Sales**. Watch what happens to
the app switcher (the grid icon, top left) after each install: entire sections of the
product appear. That's the modularity from chapter 3, live. Each install loaded a
module's models, views and menus into *this* database.

![The app switcher after installing CRM and Sales: Discuss, Calendar, Contacts, CRM, Sales, Dashboards, Invoicing, Apps, Settings](/screens/ch04-apps-menu-after-crm-sales.jpg)

Notice **Dashboards** and **Invoicing** appeared too, and you never touched their
Activate buttons. Sales depends on them (a quotation needs somewhere to post an invoice
to, and a dashboard to summarize revenue on), so Odoo installed both automatically:
installing one app can bring several along. Chapter 8 shows exactly why, from the other
side, when LibreFleet's own manifest lists what it depends on.
</Step>

<Step>
### Be a salesperson for 20 minutes

No checklist pressure. The goal is exposure, not mastery:

![CRM's Pipeline: a kanban view grouped by stage (New, Qualified, Proposition, Won), demo opportunities as cards](/screens/ch04-crm-pipeline-kanban.jpg)

- **CRM → My Pipeline.** This is a *<Term k="kanban view">kanban view</Term>* grouped by stage. Drag an opportunity
  to another column. Open one: the trail of messages and events attached to the record
  is the **<Term k="chatter">chatter</Term>**, which you'll add to your own models in chapter 33.
- Create a new opportunity, schedule an activity on it, mark it won.
- **Sales → Orders → Quotations.** Open one, note the workflow buttons (Send, Confirm)
  and the status bar. States and state-driven buttons are chapter 17 material.

  ![A quotation, still editable: Send / Print / Confirm / Cancel buttons, and a status bar reading Quotation, Quotation Sent, Sales Order](/screens/ch04-sales-quotation-workflow.jpg)

- Create a quotation for any demo customer, add products, confirm it, and notice the
  smart buttons that appear linking to related documents.
- **Settings → Users & Companies → Users**, then open a user (Mitchell Admin, or your
  own). The list itself only shows a Role column; open a record for the **Access
  Rights** tab, grouped section by section per app (Sales, Accounting, Productivity,
  Marketing...). That's the security model of chapter 10 seen from the admin side.

  ![Mitchell Admin's Access Rights tab, sections grouped by app: Master Data, Sales, Accounting, Productivity, Marketing](/screens/ch04-user-access-rights.jpg)

![An opportunity form, chatter open on the right: planned activity, message thread, Send message / Log note / Activity buttons](/screens/ch04-crm-opportunity-chatter.jpg)

<Callout type="info" title="The chatter moves, it does not disappear">
  Whether the chatter sits beside the form or below it depends on one thing only: your
  browser window's width. Odoo switches at **1400px**: wide enough (most desktops,
  screen maximized) and it takes the right-hand side, like the screenshot above;
  narrower (a laptop with the sidebar open, a window that is not maximized) and the
  exact same panel, same buttons, same thread, moves below the form instead. If yours
  looks different from the screenshot, this is why, not a sign anything is wrong.
</Callout>
</Step>

<Step>
### Switch on developer mode

Go to **Settings → General Settings**, scroll to the bottom, and under *Developer
Tools* click **Activate the developer mode**. (The shortcut you'll actually use daily:
append `?debug=1` to any backend URL.)

Three things just changed now that <Term k="developer mode">developer mode</Term> is on:

- A 🐞 icon appeared in the top bar: the developer tools menu.
- **Settings** grew a **Technical** section, the database's guts: views, actions,
  models, scheduled jobs, all browsable as ordinary records.
- Form fields now reveal their internals: open any customer, hover the little **?**
  next to a field's label, and a tooltip shows its technical name, the model it lives
  on, its type, and its widget.

![Hovering the Tax ID field's help icon in debug mode: Label, Field (vat), Model (res.partner), Type (char), Widget](/screens/ch04-field-debug-tooltip.jpg)
</Step>

<Step>
### Peek behind one field

With developer mode on, open **Settings → Technical → Database Structure → Models**
and find `crm.lead`. Every field of the opportunity form you used ten minutes ago is a
row here, 116 of them. Now the circle closes: *the UI you clicked is described by data
you can browse*. By chapter 9, rows in this list will be yours.

![The crm.lead model's Fields tab: 116 rows, Field Name, Field Label, Field Type, Required, Readonly, Indexed](/screens/ch04-model-crm-lead-fields.jpg)
</Step>

</Steps>

## Verify

Your database should show it all happened. From your workspace:

```console
$ docker compose exec db psql -U odoo -d tour -c "select count(*) from crm_lead;"
 count
-------
    45
(1 row)
```

Dozens of demo opportunities plus the ones you created (the demo set gave us 44 on a
fresh install; your exact number will differ). If the count is near zero, the demo
checkbox was missed. Recreate the database.

## Gotchas

- **Developer mode is per session, not per server.** It follows your login session;
  activating it doesn't affect other users, and `?debug=0` turns it off.
- **`debug=assets` exists too.** It serves unminified JS/CSS. You'll want it in
  chapter 39 on when debugging OWL; it makes everything slower, so don't leave it on.
- **Demo data is not sample data for production.** It exists for training, tests, and
  Runboat-style throwaway instances. Client projects always start without it.
- **Don't study Enterprise-only apps yet.** If you see apps in the list that ask for a
  subscription code (Studio, some Accounting features), skip them. Everything in this
  tutorial runs on Community.

## Exercises

1. ⭐ Install **Inventory** and trace what your confirmed sales order created there
   (hint: the smart button on the order).
2. ⭐⭐ With developer mode on, find which module defined the `expected_revenue` field on
   `crm.lead`, using only the UI.
3. ⭐⭐ In the Technical menu, find the *form view* of `crm.lead` and skim its XML in the
   Architecture tab. You already recognize more of it than you'd expect after
   chapter 3.
