**Goal:** run the pipeline from lead to confirmed sales order, then find out why pressing
Confirm created a delivery you never asked for. · **Time:** ~2 h ·
**Checkpoint:** none, this part continues in the `functional` demo database

## Why this matters

`sale.order` is the model you will be asked to change most often in your career. "Add a
field to the quotation", "block confirmation when the customer is over their credit
limit", "put our reference on the delivery note": all of it lands here.

Chapter 32 is where you make those changes. This chapter is where you learn what you are
changing, and the single most useful thing it teaches is not the Sales app at all. It is
that **pressing Confirm runs a method whose body in `sale` is empty**, and that the
delivery order which appears is created by a different module extending it. Once you
have seen that, the golden rule ("never modify core, always extend") stops being advice
you were told and becomes a pattern you watched core use on itself.

## Concepts

### The pipeline is one model with a flag

CRM looks like two things, <Term k="lead / opportunity">leads and opportunities</Term>, and it is one. `crm.lead` has a
`type` field with exactly two values, `lead` and `opportunity`, and "converting" a lead
flips that field on the record you already had. No copy, no second table, no new id.

This should feel familiar. Chapter 21 showed `res.partner` doing the same trick with
`customer_rank` and `supplier_rank`: what looks like a type in the interface is a field
on a shared model. Odoo does this constantly, and recognising it saves you from
inventing models that core already has.

Stages are separate records (`crm.stage`), which is why a pipeline is configurable
without code. The demo database ships four: New, Qualified, Proposition, Won.

### `sale.order.state` is smaller than you expect

Four values, and that is the whole machine:

| `state` | Label |
|---|---|
| `draft` | Quotation |
| `sent` | Quotation Sent |
| `sale` | Sales Order |
| `cancel` | Cancelled |

<Callout type="info" title="On Odoo 18 this differs">
  Older Odoo had a fifth state, `done`, reached by a "Lock" button and shown as Locked.
  In Odoo 19 locking is a separate boolean field, `locked`, so an order can be a
  confirmed *and* locked sales order without leaving the `sale` state. Any code that
  tests `state == 'done'` to mean locked is dead code on 19, exactly like chapter 21's
  `type == 'product'`.
</Callout>

<Term k="invoice_status">`invoice_status`</Term> is a second, independent field tracking the billing side: `no`
(Nothing to Invoice), `to invoice` (To Invoice), `invoiced` (Fully Invoiced), and
`upselling` (an ordered quantity was exceeded by what was delivered). Keeping it apart
from `state` is deliberate: an order's commercial state and its billing state move at
different speeds.

### The invoice policy lives on the product, not the order

This one causes real confusion, so it is worth stating flatly. Whether a confirmed order
can be invoiced immediately is decided by **each product's** <Term k="invoice policy (`invoice_policy`)">`invoice_policy`</Term>:

| `invoice_policy` | Meaning |
|---|---|
| `order` | Ordered quantities. Invoiceable the moment the order is confirmed. |
| `delivery` | Delivered quantities. Nothing to invoice until goods actually ship. |

Both settings are perfectly normal, and a single order can mix them. The company-level
default is a setting in Sales configuration, which is why two products in the same
database can behave differently, as you are about to see.

### What Confirm actually runs

The button calls `action_confirm`, which does the bookkeeping and then calls
`_action_confirm`. In the `sale` module, that second method looks like this in full:

```python
def _action_confirm(self):
    """ Implementation of additional mechanism of Sales Order confirmation.
        This method should be extended when the confirmation should generated
        other documents. In this method, the SO are in 'sale' state (not yet 'done').
    """
```

A docstring and nothing else. It is a deliberate, empty extension point, and the
docstring tells you so. Every module that needs confirmation to produce another document
overrides it and calls `super()`. In a stock-aware database, `sale_stock` is the one that
creates your delivery, in two lines:

```python
def _action_confirm(self):
    self.order_line._action_launch_stock_rule()
    return super(SaleOrder, self)._action_confirm()
```

That is the whole mechanism behind "confirming a sale creates a delivery order".

## Hands-on

Same two movements as chapter 21. This continues in the `functional` database, and it
uses the Brake Pad Set you created there.

### Movement 1: run the flow

#### 1. Snapshot first

```console
$ python3 odoolings.py snapshot --db functional

```

#### 2. Take a lead through the pipeline

CRM ships with the **Leads** feature off by default, which skips straight to creating
an opportunity and hides the conversion step this chapter is about. Turn it on first:
**CRM → Configuration → Settings**, tick **Leads** ("Add a qualification step before
the creation of an opportunity"), **Save**. A new **Leads** menu appears in the top bar.

In **CRM → Leads → New**, create a lead called `Fleet brake refresh` and set a
customer on it.

![A CRM lead form: title field, Probability, Company Name, Contact Name, and a Convert to Opportunity button top left](/screens/ch22-lead-convert-to-opportunity.jpg)

Then use **Convert to Opportunity**. Watch the breadcrumb: you are still on the same
record.

#### 3. Quote four brake pads

In **Sales → Orders → Quotations → New**:

1. **Customer**: the same partner you used on the lead.
2. Add an order line for **Brake Pad Set (Front)**, quantity **4**.
3. Save, but do not confirm yet.

#### 4. Confirm it

Press **Confirm**. Two things happen that you did not ask for: a **Delivery** smart
button appears at the top of the order, and the order's status changes.

![The confirmed sales order S00025: a Delivery smart button reading 1 and an Invoices smart button reading 1, top right, with the statusbar past Quotation and Quotation Sent, at Sales Order](/screens/ch22-confirmed-order-delivery.jpg)

### Movement 2: read what it did

#### 5. The quotation, as the database saw it

Running `diff` after step 3 (before confirming) gives you the lead conversion and the

#### 8. Prove the invoice policy claim yourself

```console
$ docker compose exec odoo odoo shell -c /etc/odoo/odoo.conf -d functional --no-http
```

```python

...     t = env["product.template"].search([("name", "=", name)], limit=1)
...     print(name, t.invoice_policy, t.type)
...

Office Chair delivery consu
```

Same product type, opposite billing behaviour. Now look at your order line:

```python
>>> so = env["sale.order"].search([("state", "=", "sale")], order="id desc", limit=1)
>>> l = so.order_line[0]
>>> l.product_uom_qty, l.qty_delivered, l.qty_to_invoice
(4.0, 0.0, 4.0)
```

Nothing has shipped, and it is already fully invoiceable, because this product bills on
ordered quantities. Had you quoted the Office Chair instead, `qty_to_invoice` would be
`0.0` and trying to invoice would refuse with a message telling you to deliver first.
Chapter 28 does the invoicing properly.

## Gotchas

- **The Leads feature is off by default.** Without it, CRM's "New" button creates an
  opportunity directly, no lead, no Convert button, and this chapter's whole point
  (conversion reuses the record) has nothing to show. Turn it on in CRM →
  Configuration → Settings first.
- **`sale._action_confirm` is empty, so searching it for the delivery logic finds
  nothing.** The document-creating code lives in whichever bridge module is installed,
  most often `sale_stock`. When you need to know what confirmation does *in this
  database*, list the overrides rather than reading `sale` alone.
- **There is no `done` state in Odoo 19.** Locking is the separate `locked` boolean.
  Code carried over from 18 that tests `state == 'done'` never fires, and fails silently.
- **`invoice_status` is not a mirror of `state`.** A confirmed order can be
  `to invoice`, `no`, or already `invoiced`, and the value depends on each line's
  product policy plus what has shipped. Do not compute one from the other.
- **The invoice policy is a product field, not an order field.** Two lines on the same
  order can bill on different triggers, which is why "why can't I invoice this order"
  usually has to be answered line by line.
- **Converting a lead does not create a record.** It flips `type` on the existing
  `crm.lead`. Reports that count leads and opportunities separately need to filter on
  `type`, not join two tables, and code that "creates the opportunity" on conversion is
  duplicating rows that already exist.
