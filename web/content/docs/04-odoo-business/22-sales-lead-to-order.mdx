**Goal:** run the pipeline from lead to confirmed sales order, then find out why pressing
Confirm created a delivery you never asked for. · **Time:** ~2 h ·
**Checkpoint:** none, this part continues in the `functional` demo database

## Why this matters

`sale.order` is the model you will be asked to change most often in your career. "Add a
field to the quotation", "block confirmation when the customer is over their credit
limit", "put our reference on the delivery note": all of it lands here.

Chapter 32 is where you make those changes. This chapter is where you learn what you are
changing, and the single most useful thing it teaches is not the Sales app at all. It is
that **pressing Confirm runs a method whose body in `sale` is empty**, and that the
delivery order which appears is created by a different module extending it. Once you
have seen that, the golden rule ("never modify core, always extend") stops being advice
you were told and becomes a pattern you watched core use on itself.

## Concepts

### The pipeline is one model with a flag

CRM looks like two things, <Term k="lead / opportunity">leads and opportunities</Term>, and it is one. A **lead** is an
unqualified sniff of interest; an **opportunity** is one you have decided is worth
chasing. `crm.lead` has a `type` field with exactly two values, `lead` and
`opportunity`, and "converting" a lead just flips that field on the record you already
had. No copy, no second table, no new id.

This should feel familiar. Chapter 21 showed `res.partner` doing the same trick with
`customer_rank` and `supplier_rank`: what looks like a type in the interface is a field
on a shared model. Odoo does this constantly, and recognising it saves you from
inventing models that core already has.

Stages are separate records (`crm.stage`), which is why a pipeline is configurable
without code. The demo database ships four: New, Qualified, Proposition, Won.

### `sale.order.state` is smaller than you expect

Four values, and that is the whole machine:

| `state` | Label |
|---|---|
| `draft` | Quotation |
| `sent` | Quotation Sent |
| `sale` | Sales Order |
| `cancel` | Cancelled |

<Callout type="info" title="On Odoo 18 this differs">
  Older Odoo had a fifth state, `done`, reached by a "Lock" button and shown as Locked.
  In Odoo 19 locking is a separate boolean field, `locked`, so an order can be a
  confirmed *and* locked sales order without leaving the `sale` state. Any code that
  tests `state == 'done'` to mean locked is dead code on 19, exactly like chapter 21's
  `type == 'product'`.
</Callout>

<Term k="invoice_status">`invoice_status`</Term> is a second, independent field tracking the billing side: `no`
(Nothing to Invoice), `to invoice` (To Invoice), `invoiced` (Fully Invoiced), and
`upselling` (an ordered quantity was exceeded by what was delivered). Keeping it apart
from `state` is deliberate: an order's commercial state and its billing state move at
different speeds.

### The invoice policy lives on the product, not the order

This one causes real confusion, so here it is flatly. Whether a confirmed order can be
invoiced immediately is decided by **each product's** <Term k="invoice policy (`invoice_policy`)">`invoice_policy`</Term>, the rule saying
what you are allowed to bill for:

| `invoice_policy` | Meaning |
|---|---|
| `order` | Ordered quantities. Invoiceable the moment the order is confirmed. |
| `delivery` | Delivered quantities. Nothing to invoice until goods actually ship. |

Both settings are perfectly normal, and a single order can mix them. The company-level
default is a setting in Sales configuration, which is why two products in the same
database can behave differently, as you are about to see.

### What Confirm actually runs

The **Confirm** button is wired to a method called `action_confirm`, and that method does
the visible work itself. It refuses to run unless the order is still `draft` or `sent`,
then writes `state` to `sale` and stamps `date_order` with the current time. Only then
does it call a second method, `_action_confirm`.

So the status change you see does *not* come from the method below. Keep the two names
apart: that difference is the whole point of this section.

The leading underscore is Odoo's convention for "internal": a method meant to be called
from other Python code, not wired to a button or reachable over RPC. In the `sale`
module, that second method looks like this in full:

```python
def _action_confirm(self):
    """ Implementation of additional mechanism of Sales Order confirmation.
        This method should be extended when the confirmation should generated
        other documents. In this method, the SO are in 'sale' state (not yet 'done').
    """
```

A docstring and nothing else. It is a deliberate, empty extension point, and the
docstring tells you so. Ignore its `not yet 'done'` aside: that is core's own leftover
from the Odoo 18 state machine described above, never cleaned up after `done` was
removed. Comments rot, field definitions do not.

*Override* is the word for what happens next, so here is what it means. Another module
declares a class for the same model and defines a method with the same name. From then
on, that module's version is the one that runs when anything calls `_action_confirm`.

Inside it, `super()` runs whichever version was there before, exactly as it did in
chapter 15 when you overrode `create` on your own model. That is what lets several
modules extend the same method and **stack**, each doing its bit, instead of the last one
loaded wiping out the rest.

Every module that needs confirmation to produce another document works this way. In a
stock-aware database, `sale_stock` is the one that creates your delivery, in two lines:

```python
def _action_confirm(self):
    self.order_line._action_launch_stock_rule()
    return super(SaleOrder, self)._action_confirm()
```

Two lines, and the first one carries the whole mechanism behind "confirming a sale
creates a delivery order". `_action_launch_stock_rule` is a method `sale_stock` adds to
`sale.order.line`; it does not exist in `sale` at all.

Its own docstring says what it does: it launches **procurement** for each line, Odoo's
word for "somebody needs this quantity, go and satisfy it". What that produces depends on
the rules attached to the product, and the docstring names the three possibilities:

- `_run_pull`: take it out of the warehouse, so a delivery order
- `_run_buy`: order it from a vendor, so a purchase order
- `_run_manufacture`: build it, so a manufacturing order

Chapter 25 follows that machinery properly.

The second line calls `super()`, handing control back to the `_action_confirm` that was
there before `sale_stock` loaded, so every other module that overrode the same method
still gets its turn.

### Take a lead through the pipeline

CRM ships with the **Leads** feature off by default, which skips straight to creating
an opportunity and hides the conversion step this chapter is about. Turn it on first:
**CRM → Configuration → Settings**, tick **Leads** ("Add a qualification step before
the creation of an opportunity"), **Save**. A new **Leads** menu appears in the top bar.

In **CRM → Leads → New**, fill in two things:

- The big title field at the top of the form: `Fleet brake refresh`.
- **Company Name**: `Acme Corporation`, the demo company you looked at in chapter 21.

You will go looking for a **Customer** field and not find one. That is deliberate, not a
missing app: while a record's `type` is still `lead`, Odoo hides that field unless it
already holds a partner, on the reasoning that an unqualified lead usually has nobody
attached yet. The next click is where the partner arrives. Save the lead.

![A CRM lead form: title field, Probability, Company Name, Contact Name, and a Convert to Opportunity button top left](/screens/ch22-lead-convert-to-opportunity.jpg)

Now press **Convert to Opportunity**. Rather than converting on the spot it opens a
dialog, which asks you two things:

- **Conversion Action**: leave it on **Convert to opportunity**. (The other choice,
  **Merge with existing opportunities**, folds this lead into one you already have.)
- A second pair of radio buttons, **Create a new customer** and **Link to an existing
  customer**. Choose **Link to an existing customer**, and pick `Acme Corporation` in
  the **Customer** box that appears beside it. Reusing a partner that already exists is
  what keeps the opportunity and the quotation you are about to write pointing at the
  same `res.partner`.

Press **Create Opportunity**. Watch the breadcrumb: you are still on the same record.

Two lines, and the shape is worth naming. Open the top of that file and you will find
`class SaleOrder(models.Model)` with `_inherit = "sale.order"` and no `_name` of its
own. That combination means "I am not declaring a new model, I am adding to the
`sale.order` that already exists": the fields and methods in this class merge into the
same model, the same database table and the same override chain that `sale` defined.
Chapter 31 gives this pattern its name and introduces its two siblings. For now, the
thing to notice is that core is using it on its own model, and that it is the shape your
chapter 32 work will take.

One detail in that snippet: `super(SaleOrder, self)` is just the older, longer spelling
of the bare `super()` you wrote in chapter 15. It means the same thing here, run the
`_action_confirm` that existed before this module was loaded, and you will meet both
forms in core.

## Gotchas

- **The Leads feature is off by default.** Without it, CRM's "New" button creates an
  opportunity directly, no lead, no Convert button, and this chapter's whole point
  (conversion reuses the record) has nothing to show. Turn it on in CRM →
  Configuration → Settings first.
- **`sale._action_confirm` is empty, so searching it for the delivery logic finds
  nothing.** The document-creating code lives in whichever bridge module is installed,
  most often `sale_stock`. When you need to know what confirmation does *in this
  database*, list the overrides rather than reading `sale` alone.
- **There is no `done` state in Odoo 19.** Locking is the separate `locked` boolean.
  Code carried over from 18 that tests `state == 'done'` never fires, and fails silently.
- **`invoice_status` is not a mirror of `state`.** A confirmed order can be
  `to invoice`, `no`, or already `invoiced`, and the value depends on each line's
  product policy plus what has shipped. Do not compute one from the other.
- **The invoice policy is a product field, not an order field.** Two lines on the same
  order can bill on different triggers, which is why "why can't I invoice this order"
  usually has to be answered line by line.
- **Converting a lead does not create a record.** It flips `type` on the existing
  `crm.lead`. Reports that count leads and opportunities separately need to filter on
  `type`, not join two tables, and code that "creates the opportunity" on conversion is
  duplicating rows that already exist.
