**Goal:** learn every route by which a line's price stops being the product's price, so you
can diagnose a wrong one. · **Time:** ~2 h ·
**Checkpoint:** none, this part continues in the `functional` demo database

## Why this matters

"The price on this quote is wrong" is one of the most common tickets an Odoo developer
receives, and one of the most annoying, because the price in front of you could have come
from at least three unrelated mechanisms. Until you can name all of them and tell which
one fired, you are guessing.

That is this chapter's whole job. By the end you will have made one product's price change
three different ways, and you will be able to tell from the database alone which mechanism
did it.

## Concepts

### Pricelists are optional, and off by default

Start from the baseline, because it is easy to forget it exists. In a fresh database with
the Sales app installed there are **no pricelists at all**, and a line's `price_unit` is
simply the product's own sales price.

A <Term k="pricelist (`product.pricelist`)">pricelist</Term> is a named set of rules for charging some customers a different price. It
sits behind a feature flag, and in Odoo a feature flag is just a group: this one is
`product.group_product_pricelist`.

Ticking **Pricelists** in the Sales settings adds your user to that group, and three
things follow from that single membership:

- A **Pricelists** menu appears under Sales → Products, because the menu item is
  restricted to that group.
- A **Pricelist** field appears on the quotation form, for the same reason.
- The save handler runs core code that creates a Default pricelist per company, so the
  new field has something to point at.

None of it exists until you tick the box, which is why a database can look like it has
"no pricelist feature" at all.

Worth knowing before you debug anything: if `pricelist_id` on the order is empty, no
pricelist rule can possibly be responsible for the price.

### A pricelist is a bag of rules, and specificity decides

A <Term k="pricelist (`product.pricelist`)">`product.pricelist`</Term> holds `product.pricelist.item` rules. Each says **what it applies to**
and **how it computes a price**:

| `applied_on` | Scope |
|---|---|
| `0_product_variant` | one specific variant |
| `1_product` | one template, so all its variants |
| `2_product_category` | a product category |
| `3_global` | everything |

Look at those values again. The numeric prefixes are not decoration, **they are the sort
key**. Odoo orders candidate rules by that string, so `0_product_variant` is considered
before `3_global` and the most specific applicable rule wins. Once you see that, resolution
order stops being folklore you have to memorise.

How a rule computes is a separate axis, `compute_price`: `fixed` (a flat price),
`percentage` (a discount off a base), or `formula` (a margin calculation with rounding and
limits). A rule can also carry a `min_quantity` and a date window, which is how volume and
seasonal pricing are expressed without code.

### Three different things all called "the discount"

Here is the part that makes tickets hard. All three of these change what a customer pays,
and they leave different traces.

One field name to have straight before the table: `lst_price` is a variant's own Sales
Price, the figure you see on the product form. It is the template's `list_price` plus
whatever price extra that variant's attributes add. That is where a line's price starts
when nothing else interferes.

| Mechanism | What it touches | How you spot it |
|---|---|---|
| **Pricelist rule** | `price_unit` on the product line | line price differs from the product's `lst_price`, and the order has a `pricelist_id` |
| **Discount field** | `discount` percent on the line | `price_unit` still equals the product price, `discount` is non-zero |
| **Promotion / reward** | adds a **new line** with a negative `price_unit` | an extra line you did not add, priced below zero |

The middle one has a catch worth knowing before you go hunting for it. The `discount`
column is behind its own setting, **Grant discounts on sales order lines**, in the same
Sales → Pricing block you are about to visit, and it is switched off here. The field
still exists on `sale.order.line` either way: only the view hides it. That is why step 7
can read `discount` from the shell even though no such column appears on your quotation.

The third one surprises people. A claimed <Term k="reward (loyalty)">reward</Term> (the discount or free item a
promotion grants) does not edit your product line and does not touch the discount field.
It appends its own line, and the order total falls because that line is negative.

So "the 10% is missing from the line" and "the 10% is a separate line" can both be
accurate descriptions of different mechanisms.

### Promotions are a separate app, and claiming is two steps

Coupons, discount codes, loyalty cards and "buy X get Y" all come from `sale_loyalty`,
which is not installed by default. It brings `loyalty.program`, and Odoo 19 offers eight
programme types: coupons, gift cards, loyalty cards, promotions, eWallets, discount codes,
buy X get Y, and next-order coupons.

Applying a code is **two operations**, and knowing that saves confusion if you automate it.
`_try_apply_code` *validates* the code and returns what could be claimed; it does not
change the order. Claiming is a second call. Fire only the first and nothing happens,
silently.

## Hands-on

Continuing in `functional`.

<Steps>

<Step>
### Confirm the baseline before changing anything

```console
$ docker compose exec odoo odoo shell -c /etc/odoo/odoo.conf -d functional --no-http
```

```python
>>> env["product.pricelist"].search_count([])
0
>>> so = env["sale.order"].search([("state", "=", "sale")], order="id desc", limit=1)
>>> l = so.order_line[0]
>>> so.pricelist_id.name, l.price_unit, l.product_id.lst_price
(False, 79.0, 79.0)
```

No pricelists exist, the order has none, and the line price is exactly the product price.
That is the "no mechanism fired" state, and it is what you compare against.

</Step>

<Step>
### Turn pricelists on

**Settings → Sales**, under the **Pricing** section, tick **Pricelists**, save.

![The Sales app's Pricing settings section: Discounts unchecked, Promotions/Loyalty & Gift Card checked, Pricelists checked with a link to manage them, Margins unchecked](/screens/ch23-sales-pricing-settings.jpg)

Now go back to the shell you left open in step 1, and do **not** just re-run the count: it
will still report the old number. A shell session holds one long-running database
transaction, and Postgres fixed that transaction's view of the data at your first query,
before the browser saved anything. Anything committed since then is invisible to it. End
the transaction to get a fresh view, then look again:

```python
>>> env.cr.rollback()
>>> env["product.pricelist"].search_count([])
3
```

Three, not one: this demo database has three companies, and switching the feature on runs
core code that creates a Default pricelist for each of them.

That `env.cr.rollback()` is the same one you have used since chapter 14 to undo an
experiment. It also throws away the ORM's in-memory cache, which is what you want here.
Expect to need it every time you change something in the browser and then read it back
from a shell that was already open.

Hold on to the three, because it changes how you read the rest of the chapter. The shell
does not apply the company filter the interface does. It runs as the superuser, skipping
record rules entirely, so a bare `search([])` returns all three companies' pricelists
while the same list in the browser shows only the active company's.

So whenever you go looking for "the" pricelist from a script, say which company you mean.
That is what step 6 does with `("company_id", "=", env.company.id)`, and chapter 27 comes
back to the problem properly.

</Step>

<Step>
### Add two rules that compete

Ticking the setting also added a menu: **Sales → Products → Pricelists**. Open it and you
will see exactly one row, the Default pricelist for your own company.

That is the multi-company visibility rule from the last step again, now in the browser
instead of the shell. All three Default pricelists exist (the 3 you just counted), one
per company, but the list view only shows the one tied to your active company, named in
the top bar. Open it.

On its **Sales Prices** tab, click **Add a line**. The dialog never asks you for
`applied_on`, which catches people out: that field is hidden, and Odoo works it out from
*which* product fields you fill in.

- Leave them empty and you get `3_global`.
- Name a product and you get `1_product`.
- Name a product and one of its variants and you get `0_product_variant`.

So the first rule, the global one:

- **Apply To**: leave it on **Product**.
- **Product**: leave it **empty**. It shows "All products" as a placeholder. That empty
  field is the whole reason this rule counts as global.
- **Price Type**: **Discount**.
- **Discount**: **10** %.

Save it, then **Add a line** again for the second rule, the specific one:

- **Apply To**: **Product**.
- **Product**: `Brake Pad Set`.
- **Variant**: a Variant field appears once you pick that template, because it has two
  variants. Set it to `Brake Pad Set (Front)`. Filling it in is what makes this a variant
  rule rather than a template rule.
- **Price Type**: **Fixed Price**.
- **Fixed Price**: **60.00**.

Save the pricelist. In the rules list, the **Apply on** column now reads "All Products"
for the first and "Variant: Brake Pad Set (Front)" for the second. That column is Odoo
telling you back the `applied_on` it derived.

![The Default pricelist's two rules: Variant Brake Pad Set (Front) at $60.00, and All Products at 10% discount on sales price](/screens/ch23-pricelist-two-rules.jpg)

</Step>

<Step>
### Quote it and watch the price

Snapshot first, so that the `diff` in step 7 shows this quotation and nothing else.
`diff` always compares against the last snapshot you took, so without this it either
reports that no snapshot exists or reports everything that has changed since chapter 22:

```console
$ python3 odoolings.py snapshot --db functional
```

Then, in **Sales → Orders → Quotations → New**:

1. **Customer**: any customer will do.
2. **Pricelist**: the Default you just edited. Set this **before** you add any line. A
   line takes its price at the moment it is created, so a line added first keeps 79.00
   and changing the pricelist underneath it afterwards does not move it.
3. Add an order line for **Brake Pad Set (Front)**, quantity **2**.
4. Save. The unit price reads 60.00, not 79.00.

Leave it as a draft quotation. Nothing in this chapter needs it confirmed.

</Step>

<Step>
### Apply a promotion

First install the promotions machinery, from the same screen you used in step 2. Go to
**Settings → Sales**, and in the **Pricing** section tick **Promotions, Loyalty & Gift
Card**, then **Save**. That installs the `loyalty` module, and `sale_loyalty` (the bridge
that teaches `sale.order` about rewards) comes along on its own, because its manifest
marks it `auto_install` and both of the modules it depends on are now present.

Do not go looking for either of them in Apps. Neither declares itself an application, and
the Apps list filters to applications by default, so a search for `sale_loyalty` there
finds nothing at all.

Now snapshot again, so step 8's `diff` isolates what the promotion did rather than
re-reporting the quotation you already looked at:

```console
$ python3 odoolings.py snapshot --db functional
```

The demo data includes a discount-code programme called *Code for 10% on orders*, whose
code is `10pc`. On your quotation, click the **Coupon Code** button below the order lines,
enter that code in the "Enter Promotion or Coupon Code" dialog, and **Apply**.

![The quotation after both mechanisms: Brake Pad Set (Front) at the pricelist's $60.00 unit price, and a separate "10% on your order" line at -$12.00, total $124.20](/screens/ch23-quotation-pricelist-and-reward.jpg)

</Step>

<Step>
### Specificity, proved

```python
>>> pl = env["product.pricelist"].search([("company_id", "=", env.company.id)], limit=1)
>>> for it in pl.item_ids:
...     print(it.applied_on, it.compute_price, it.fixed_price or it.percent_price,
...           it.product_id.display_name or "(any)")
...
0_product_variant fixed 60.0 Brake Pad Set (Front)
3_global percentage 10.0 (any)
```

Two rules, both applicable to the brake pads. Now ask the pricelist for prices, once for a
product that has a specific rule and once for a product that does not:

```python
>>> front = env["product.product"].search([("product_tmpl_id.name", "=", "Brake Pad Set")], limit=1)
>>> other = env["product.product"].search([("product_tmpl_id.name", "=", "Office Chair")], limit=1)
>>> front.lst_price, pl._get_product_price(front, 1)
(79.0, 60.0)
>>> other.lst_price, pl._get_product_price(other, 1)
(70.0, 63.0)
```

The brake pads land on 60.00, the flat variant price. The chair has no rule of its own, so
it falls through to the global 10% and lands on 63.00. That is the whole resolution order,
in two lines of output.

<Callout type="warn" title="Gotcha">
  `_get_product_price` works in the shell but is **private**, so RPC refuses it, exactly
  like `sale.order._create_invoices` in chapter 28. There is no public "what would this
  cost" call, which is why this chapter's odoolings check inspects the rule and a quoted
  line rather than asking the pricelist directly.
</Callout>

</Step>

<Step>
### What the quotation took

```console
$ python3 odoolings.py diff --db functional
sale.order          +1
      new   S00026                   state=draft  amount_untaxed=120.0  amount_total=138.0  invoice_status=no
sale.order.line     +1
      new   Brake Pad Set (Front)    product_uom_qty=2.0  price_unit=60.0
```

`price_unit=60.0` against a 79.00 product. Note what is **not** here: the `discount` field
is untouched.

```python
>>> l = so.order_line[0]
>>> l.price_unit, l.discount, l.product_id.lst_price
(60.0, 0.0, 79.0)
```

A pricelist rule rewrites the price. It does not populate the discount column, so a
customer reading this quote sees 60.00 with no visible reduction. Whether that is what your
client wants is a configuration question, and it is a common source of "where did our
discount go".

</Step>

<Step>
### What the promotion did, which is different

```console
$ python3 odoolings.py diff --db functional
sale.order          ~
      chg   S00026                   amount_untaxed: 120.0 -> 108.0
      chg   S00026                   amount_total: 138.0 -> 124.2
sale.order.line     +1
      new   10% on your order        product_uom_qty=1.0  price_unit=-12.0
```

**A new line, priced at minus 12.00.** The product line is untouched at 60.00; the total
fell because a negative line joined the order.

```python
>>> for l in so.order_line:
...     print(l.product_id.display_name[:32], l.price_unit, l.price_subtotal)
...
Brake Pad Set (Front) 60.0 120.0
10% on your order -12.0 -12.0
```

Ten percent of 120.00 is 12.00, and it arrived as its own row. If you were hunting for a
missing discount on the product line, you would never have found it.

</Step>

<Step>
### The two-step claim, seen once

Worth doing once so you recognise it later, but do it on a **different** order. Make a
second draft quotation in the browser with the same product on it and no code applied,
then point `so` at it:

```python
>>> env.cr.rollback()
>>> so = env["sale.order"].search([("state", "=", "draft")], order="id desc", limit=1)
```

The `rollback` is the stale-transaction problem from step 2 again: your shell cannot see a
record the browser created after your last query. The `order="id desc", limit=1` picks the
newest draft, which is the quotation you just made.

Why a fresh order? Because `_try_apply_code` checks first whether that code is already on
this order, and if it is, it returns an error dict saying the promo code is already applied
instead of the mapping below. Run it on the quotation from step 5 and you meet the refusal,
not the mechanism.

With a clean order in hand: validating a code is not applying it.

```python
>>> so._try_apply_code("10pc")
defaultdict(<function ...>, {loyalty.card(1,): loyalty.reward(2,)})
```

That return value is a mapping of *claimable* rewards, and the order has not changed. The
second step is what appends the line:

```python
>>> claimable = so._try_apply_code("10pc")
>>> for coupon, rewards in claimable.items():
...     so._apply_program_reward(rewards[0], coupon)
```

Call only the first and nothing happens, with no error to tell you why.
</Step>

## Gotchas

- **No pricelist on the order means no pricelist rule can be to blame.** Check
  `pricelist_id` first when diagnosing a price. It is the cheapest possible test and it
  rules out a whole mechanism.
- **A line takes its price when it is created.** Editing a pricelist rule does not reprice
  quotations that already exist. "I fixed the rule and the quote still shows the old price"
  is this, and the fix is to re-add the line or use the order's price-recompute action, not
  to hunt for a caching bug.
- **A pricelist rule and the `discount` field are different features.** A rule rewrites
  `price_unit` and leaves `discount` at zero, so the reduction is invisible on the printed
  quote. If the client wants the discount *shown*, that is a configuration decision, not a
  bug in the pricelist.
- **A reward is a new line, not an edit.** Look for a negative `price_unit` before
  concluding a promotion did not apply. Totals that are right while lines "look wrong" are
  usually this.
- **`_try_apply_code` validates, it does not apply.** It returns claimable rewards and
  changes nothing. Automating promotions with only that call produces silent no-ops.
