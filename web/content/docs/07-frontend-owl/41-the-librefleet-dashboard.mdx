**Goal:** build a Workshop Load dashboard as a client action, grouping open service
orders per technician with `formattedReadGroup`, and make each number click through to
the records behind it. · **Time:** ~2 h · **Checkpoint:** `code/checkpoints/ch41`

## Why this matters

Chapter 39 put a component in the systray and chapter 40 changed how an existing screen
behaves. Both were decorations on screens Odoo already provided. A dashboard is the
first time you own the whole screen: no list, no form, no view engine, just a menu item
that opens your component and whatever you decide to draw.

That freedom comes with the question every dashboard eventually gets wrong, which is
not "how do I draw a table" but **where the arithmetic happens**. Fetching every record
and counting in JavaScript works beautifully on your two demo orders and collapses on a
client with forty thousand. The database already knows how to group and sum; the job is
to ask it once and render the answer.

This chapter also walks straight into a counting trap that is genuinely easy to ship,
and the finished dashboard displays the contradiction on its own face.

## Concepts

### A client action is a database record plus a registry entry

```xml
<record id="action_librefleet_dashboard" model="ir.actions.client">
    <field name="name">Workshop Load</field>
    <field name="tag">librefleet_dashboard</field>
</record>
```

```js
registry.category("actions").add("librefleet_dashboard", LibreFleetDashboard);
```

The `tag` is the *only* connection between those two halves. A menu item points at the
`ir.actions.client` record, the web client reads its tag, and looks that string up in
the `actions` registry. This is the same shape as chapter 40's field widget
(`widget="..."` looking up the `fields` registry), and it fails the same way: a typo in
either half is a string mismatch nothing validates at install time.

<Mermaid label="A menu item opens an ir.actions.client record, whose tag string is looked up in the actions registry to find the OWL component that renders the screen." chart={`flowchart LR
    Menu["menuitem"] --> Action["ir.actions.client<br/>tag = librefleet_dashboard"]
    Action -->|"tag looked up in"| Reg["actions registry"]
    Reg --> Comp["LibreFleetDashboard<br/>(OWL component)"]
    Comp -->|"orm.formattedReadGroup"| DB[("Postgres<br/>GROUP BY")]
`} />

Your component gets the action record itself as a prop, so spreading
`standardActionServiceProps` is required for the same reason chapter 40 spread
`standardFieldProps`: OWL rejects props the component never declared.

### `formattedReadGroup`: let Postgres do the counting

```js
const groups = await this.orm.formattedReadGroup(
    "librefleet.service.order",
    [["stage", "in", OPEN_STAGES]],   // domain
    ["technician_ids"],               // groupby
    ["__count", "margin:sum"]         // aggregates
);
```

One round trip, one `GROUP BY` in the database, and back comes one object per group:

```text
{'technician_ids': (5, 'Tina Technician'), '__extra_domain': [('technician_ids', '=', 5)], '__count': 1, 'margin:sum': 139.1}
{'technician_ids': False, '__extra_domain': [('technician_ids', 'not any', [])], '__count': 1, 'margin:sum': 120.0}
```

Three things to read off that output. Aggregates come back keyed by the exact string
you asked for, so `group["margin:sum"]`, not `group.margin`. A grouped many2many yields
an `[id, name]` pair, exactly like a many2one. And records with nobody assigned group
under `False`, which is why the component maps that to a readable "Unassigned" rather
than printing `false` at a workshop manager.

<Callout type="warn" title="On Odoo 18 this differs">
  This method was `read_group` (and `orm.readGroup` in JavaScript) up to Odoo 18. Odoo
  19 replaced it with `formatted_read_group` / `formattedReadGroup`, with a different
  signature: aggregates are their own argument (`["__count", "margin:sum"]`) rather
  than being mixed into the fields list. There is no `orm.readGroup` to fall back on,
  so older tutorials and Stack Overflow answers will not run as written.
</Callout>

### Every group carries the domain that produced it

`__domain` comes back on each group: the exact domain that selected those records.
That matters for drill-down. The tempting move is to rebuild the filter by hand:

```js
domain: [["technician_ids", "=", group.technician_ids[0]]],   // don't
```

That happens to work here and quietly breaks the moment the dashboard's own domain
grows a condition, or the group is the `False` one (whose real domain is
`[("technician_ids", "not any", [])]`, not anything you would have guessed). Passing
`group.__domain` straight through means the list a user opens can never disagree with
the number they clicked.

<Step>
### Write the component

```js title="addons/librefleet/static/src/dashboard/dashboard.js"
import { Component, onWillStart, useState } from "@odoo/owl";
import { registry } from "@web/core/registry";
import { standardActionServiceProps } from "@web/webclient/actions/action_service";
import { useService } from "@web/core/utils/hooks";

const OPEN_STAGES = ["draft", "confirmed", "in_progress"];

export class LibreFleetDashboard extends Component {
    static template = "librefleet.Dashboard";
    // A client action receives the action record itself as a prop, plus a few
    // the action service adds. Spread these or OWL rejects the render.
    static props = { ...standardActionServiceProps };

    setup() {
        this.orm = useService("orm");
        this.action = useService("action");
        this.state = useState({ technicians: [], openCount: 0, loading: true });
        onWillStart(async () => {
            await this.load();
        });
    }

    async load() {
        const domain = [["stage", "in", OPEN_STAGES]];
        // One round trip that groups and aggregates in Postgres, instead of
        // fetching every order and counting in JavaScript. On a real fleet
        // that difference is the whole chapter.
        const groups = await this.orm.formattedReadGroup(
            "librefleet.service.order",
            domain,
            ["technician_ids"],
            ["__count", "margin:sum"]
        );
        this.state.technicians = groups.map((group) => ({
            // Grouping by a many2many yields [id, name] per group, or false
            // for the records that have nobody assigned.
            id: group.technician_ids ? group.technician_ids[0] : false,
            name: group.technician_ids ? group.technician_ids[1] : "Unassigned",
            count: group.__count,
            margin: group["margin:sum"] || 0,
            domain: group.__domain,
        }));
        this.state.openCount = await this.orm.searchCount(
            "librefleet.service.order", domain);
        this.state.loading = false;
    }

    // Every group carries the domain that produced it, so "show me these
    // records" needs no domain rebuilt by hand and cannot drift from the
    // number the reader just clicked.
    openGroup(technician) {
        this.action.doAction({
            type: "ir.actions.act_window",
            name: `Open orders: ${technician.name}`,
            res_model: "librefleet.service.order",
            domain: technician.domain,
            views: [[false, "list"], [false, "form"]],
        });
    }
}

registry.category("actions").add("librefleet_dashboard", LibreFleetDashboard);
```

`useService("action")` is the counterpart to `useService("orm")`: where the ORM service
reads data, the action service opens things. `doAction` takes an action *description*
here rather than a database record, which is how a component opens a filtered list
without an `ir.actions.act_window` record existing for it.
</Step>

### Write the template

```xml title="addons/librefleet/static/src/dashboard/dashboard.xml"
<?xml version="1.0" encoding="UTF-8"?>
<templates xml:space="preserve">

    <t t-name="librefleet.Dashboard">
        <div class="o_librefleet_dashboard p-4">
            <h2>Workshop load</h2>

            <div t-if="state.loading" class="text-muted">Loading...</div>

            <div t-else="">
                <p class="text-muted">
                    <span t-out="state.openCount"/> open order(s) across
                    <span t-out="state.technicians.length"/> group(s).
                </p>

                <table class="table table-sm w-auto">
                    <thead>
                        <tr>
                            <th>Technician</th>
                            <th class="text-end">Open orders</th>
                            <th class="text-end">Margin</th>
                        </tr>
                    </thead>
                    <tbody>
                        <tr t-foreach="state.technicians" t-as="tech" t-key="tech.id">
                            <td t-out="tech.name"/>
                            <td class="text-end">
                                <button class="btn btn-link p-0"
                                        t-on-click="() => this.openGroup(tech)">
                                    <span t-out="tech.count"/>
                                </button>
                            </td>
                            <td class="text-end" t-out="tech.margin.toFixed(2)"/>
                        </tr>
                    </tbody>
                </table>
            </div>
        </div>
    </t>

</templates>
```

`t-key` on a `t-foreach` is not optional in OWL: it tells the renderer which DOM node
belongs to which item so a re-render patches rather than rebuilds. The arrow function in
`t-on-click` is how you pass an argument to a handler, since `t-on-click="openGroup"`
would call it with the DOM event instead.
</Step>

### Read the numbers, then distrust them

![The Workshop load dashboard: a line reading 3 open order(s) across 2 group(s), above a table with Administrator at 2 open orders and 408.00 margin, and Tina Technician at 2 open orders and 469.00 margin](/screens/ch41-dashboard-workshop-load.jpg)

Look at that screen closely. It says **3 open orders**, and the Open orders column reads
2 and 2. Two plus two is four.

Neither number is wrong. `searchCount` counted three distinct orders, and each group
genuinely contains two, because the order you gave two technicians is a member of both
groups. **Grouping by a many2many double-counts by design**, and any "total" you compute
by summing the groups will overstate reality by exactly the amount of shared work.

Confirm it from the shell rather than taking the screen's word for it:

```console
>>> domain = [("stage", "in", ["draft", "confirmed", "in_progress"])]
>>> Order.search_count(domain)
3
>>> res = Order.formatted_read_group(domain=domain, groupby=["technician_ids"], aggregates=["__count", "margin:sum"])
>>> [(r["technician_ids"], r["__count"]) for r in res]
[((2, 'Administrator'), 2), ((5, 'Tina Technician'), 2)]
>>> sum(r["__count"] for r in res)
4
```

This is worth internalising before you build a dashboard anyone makes decisions from. A
"jobs per technician" table is a legitimate answer to "who is busy". A "total jobs"
figure derived by adding that column up is simply wrong, and nothing in the framework
will warn you.

Now click one of the counts. The breadcrumb becomes "Workshop Load / Open orders: Tina
Technician" and the list holds exactly two records, one of which visibly carries both
technicians as tags. The count and the list agree because both came from the same
`__domain`.
</Step>

Change the tag on the `ir.actions.client` record to `librefleet_dashbord`, then upgrade:

```console
$ docker compose exec odoo odoo -c /etc/odoo/odoo.conf -d tutorial -u librefleet --stop-after-init
```

Open the Dashboard menu **in a new browser tab**. You get an "Oops!" dialog, and the
console carries the real reason:

```text
KeyNotFoundError: Cannot find key "librefleet_dashbord" in the "actions" registry
    at Registry.get (.../web.assets_web.min.js:3754:76)
    at _executeClientAction (.../web.assets_web.min.js:10698:87)
    at doAction (.../web.assets_web.min.js:10715:192)
```

The new tab matters. A tab that already had the dashboard open keeps rendering it
perfectly, because the web client caches action definitions it has already loaded, so
the stale tab is running the old tag against a component that still exists. That is a
genuinely confusing debugging situation: the change is live in the database, one tab is
broken, another is fine, and neither the server log nor the upgrade said anything. When
a client action misbehaves, open a fresh tab before you believe anything.

Put the tag back and upgrade:


## Gotchas

- **Grouping by a many2many double-counts.** An order with two technicians is in both
  groups, so the column never sums to the number of records. Get your totals from a
  separate `searchCount`, never by adding the groups up.
- **Aggregates are keyed by the string you asked for.** `group["margin:sum"]`, not
  `group.margin`. Reading the wrong key gives `undefined`, which renders as blank rather
  than erroring.
- **The `tag` is an unvalidated string in two places.** A mismatch between the
  `ir.actions.client` record and the `actions` registry throws `KeyNotFoundError` in the
  browser and nothing anywhere else.
- **The web client caches actions per tab.** After changing an action record, an open
  tab may keep showing the old behaviour indefinitely. Test client actions in a fresh
  tab.
- **Data file order is load order.** A `menuitem` whose `parent` is defined in another
  file needs that file listed first in the manifest, or the upgrade fails on a missing
  external id.
