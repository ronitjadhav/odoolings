**Goal:** write a `librefleet_margin` field widget that colours profit and loss, then
patch core's `FormController` to warn on saving a losing order, and understand why
those two techniques are not interchangeable. · **Time:** ~2 h ·
**Checkpoint:** `code/checkpoints/ch40`

## Why this matters

Chapter 39's systray component was additive: nothing in Odoo had to change for it to
appear, because the systray is a registry and adding to a registry is what registries
are for. Real tickets are rarely that polite. "Make the margin red when we're losing
money" means changing how an existing field renders. "Warn me before I save this"
means changing what an existing controller does.

Odoo gives you two tools for that, and choosing between them is the actual skill this
chapter teaches. **Registries** are the front door: Odoo publishes a named slot, you
add an entry, and nothing else in the system is affected. **Patching** is the fire
escape: you reach into a core class and rewrite its methods in place, for every user of
that class, everywhere. Both are legitimate. Only one of them is safe by default.

## Concepts

### A field widget is a component plus a descriptor plus a registry entry

The `widget="..."` attribute you have been writing since chapter 11 (`many2many_tags`,
`statusbar`, `badge`, `daterange`) is a registry lookup. Each name maps to a
**descriptor object**, and the descriptor points at an OWL component:

```js
export const marginField = {
    component: MarginField,
    displayName: _t("Workshop Margin"),
    supportedTypes: ["float", "monetary"],
};

registry.category("fields").add("librefleet_margin", marginField);
```

The component itself receives a fixed set of props from the view engine, declared by
spreading `standardFieldProps`:

```js
static props = { ...standardFieldProps };
```

That gives you `name`, `record`, `readonly` and `id`. The important pair is `record`
and `name`: a widget never hardcodes which field it displays, it reads
`this.props.record.data[this.props.name]`. That indirection is exactly why one widget
can serve many fields on many models.

`supportedTypes` is not decoration. It is what makes Odoo refuse the widget on a field
type it cannot render, instead of letting someone put `widget="librefleet_margin"` on a
Char field and getting nonsense at runtime.

### Patching: the escape hatch, and why it needs a guard

Some things have no registry slot. `FormController.onWillSaveRecord` is a hook that
runs before every form save, and there is no "add a save hook" registry to append to.
For that, Odoo ships `patch`:

```js
import { patch } from "@web/core/utils/patch";
import { FormController } from "@web/views/form/form_controller";

patch(FormController.prototype, {
    async onWillSaveRecord(record) {
        const result = await super.onWillSaveRecord(...arguments);
        // ...
        return result;
    },
});
```

Two mechanics worth naming. `super` works inside a patch even though this is a plain
object literal, because `patch` stores the original method on a skeleton object and
wires the prototype chain so `super` resolves to whatever was there before, including
another module's patch. That is what makes patches stack rather than clobber.

And the part that bites: **a patch is global and unconditional.** There is no way to
register a patch "only for this model" or "only in my app". The code above runs on
every form view in the entire web client, in Sales, in Invoicing, in Settings, for
every model. The only scoping available is a check inside the method body:

```js
if (record.resModel !== "librefleet.service.order") {
    return result;
}
```

Forget that line and you have quietly changed how the whole client behaves.

## Hands-on

<Steps>

<Step>
### Build the margin widget

```js title="addons/librefleet/static/src/margin_field/margin_field.js"
import { Component } from "@odoo/owl";
import { _t } from "@web/core/l10n/translation";
import { registry } from "@web/core/registry";
import { formatFloat } from "@web/views/fields/formatters";
import { standardFieldProps } from "@web/views/fields/standard_field_props";

export class MarginField extends Component {
    static template = "librefleet.MarginField";
    // Spreading standardFieldProps is not optional: the view engine always
    // passes name/record/readonly/id, and OWL's prop validation rejects any
    // prop the component did not declare.
    static props = { ...standardFieldProps };

    get value() {
        // Every field widget reads its own value the same way: the record is
        // handed to it as a prop, and props.name says which field it is bound
        // to. That indirection is what lets one widget serve many fields.
        return this.props.record.data[this.props.name];
    }

    get formattedValue() {
        return formatFloat(this.value, {
            field: this.props.record.fields[this.props.name],
        });
    }

    get isLoss() {
        return this.value < 0;
    }

    get cssClass() {
        return this.isLoss ? "text-danger fw-bold" : "text-success";
    }

    get iconClass() {
        return this.isLoss ? "fa-arrow-down" : "fa-arrow-up";
    }
}

export const marginField = {
    component: MarginField,
    displayName: _t("Workshop Margin"),
    // Declaring the types this widget understands is what makes Odoo refuse
    // it on, say, a Char field, instead of rendering something broken.
    supportedTypes: ["float", "monetary"],
};

registry.category("fields").add("librefleet_margin", marginField);
```

`formatFloat` from core is doing real work here: it applies the user's language
settings (decimal separator, thousands separator) and the field's own `digits`
precision. Formatting a number by hand with `toFixed` would look right in English and
wrong in half the world.

```xml title="addons/librefleet/static/src/margin_field/margin_field.xml"
<?xml version="1.0" encoding="UTF-8"?>
<templates xml:space="preserve">

    <t t-name="librefleet.MarginField">
        <span t-att-class="cssClass">
            <i class="fa" t-att-class="iconClass"/>
            <span t-out="formattedValue"/>
        </span>
    </t>

</templates>
```

<Step>
### Patch the form controller

```js title="addons/librefleet/static/src/form_controller/service_order_save_warning.js"
import { _t } from "@web/core/l10n/translation";
import { patch } from "@web/core/utils/patch";
import { useService } from "@web/core/utils/hooks";
import { FormController } from "@web/views/form/form_controller";

// A patch is GLOBAL and unconditional: this runs on every form view in the
// entire web client, for every model, in every app. There is no way to scope
// a patch at registration time, so the scoping has to happen inside the
// method (the resModel guard below). Forget it and you have changed how
// Sales, Invoicing and Settings behave too.
patch(FormController.prototype, {
    setup() {
        super.setup(...arguments);
        this.notification = useService("notification");
    },

    async onWillSaveRecord(record) {
        const result = await super.onWillSaveRecord(...arguments);
        if (record.resModel === "librefleet.service.order" && record.data.margin < 0) {
            this.notification.add(
                _t("This order is being saved at a loss of %s.", record.data.margin.toFixed(2)),
                { type: "warning", title: _t("Negative margin") }
            );
        }
        // Returning false from this hook cancels the save. We deliberately do
        // not: chapter 20's wizard is where the hard block lives, and a UI
        // patch is the wrong place to enforce a business rule (an import or
        // an RPC call would bypass it entirely).
        return result;
    },
});
```

Patching `setup` to add a service is the standard way to give a patched class
something it did not have. `useService` is a hook, so it has to run inside `setup`,
which is exactly where the patched version puts it.

Upgrade, then create a service order that loses money (a part whose `standard_cost`
exceeds what you charge for it), edit any field, and save. A warning toast appears at
the top right reading "Negative margin: This order is being saved at a loss of
-401.00", and the save still goes through.

That last detail is the design decision worth arguing about, so the code says why in a
comment: this hook *can* block the save by returning `false`, and it deliberately does
not. A rule enforced only in the browser is not enforced. Chapter 20's wizard, running
on the server, is what actually stops a losing order being completed; this patch is a
convenience for the person clicking, not a control.
</Step>

<Step>
### Break-it lab: remove the guard

Delete the `record.resModel === "librefleet.service.order" &&` half of the condition,
upgrade, reload, and go edit a record in a completely different app: a contact under
Settings > Users & Companies > Contacts, say. Save it.

Nothing visibly breaks, which is the point. `record.data.margin` is `undefined` on a
partner, `undefined < 0` is `false`, and the notification stays quiet. Your patch is
now running on every save of every record in the database and *happening* to be
harmless because of a JavaScript coercion rule.

Change the condition to something that is truthy on other models (`record.data.id`,
for instance) and save that contact again to watch a LibreFleet warning appear on a
screen that has nothing to do with LibreFleet. Then put the guard back. The lesson is
not "this particular patch was dangerous", it is that **the blast radius of a patch is
the whole client and nothing warns you**.
</Step>

the stack will ever tell you about.

## Gotchas

- **Registering a widget does not apply it.** The registry entry and the view's
  `widget="..."` attribute are two separate halves, and only the second one puts it on
  a screen.
- **`static props` must spread `standardFieldProps`.** The view engine passes
  `record`, `name`, `readonly` and `id` regardless; OWL's prop validation rejects
  anything undeclared, so the widget fails to render with a props error.
- **A patch applies to every instance of the class, everywhere.** There is no
  per-model or per-app registration. The guard goes inside the method body, and
  forgetting it is silent.
- **Don't enforce business rules in a patch.** Anything the browser enforces is
  bypassed by an import, an RPC call, or the shell. Warn in the client, block on the
  server.
- **`formatFloat` over `toFixed`.** Core's formatter respects the user's language
  separators and the field's own precision; hand formatting is a localisation bug
  waiting for its first non-English user.
